# Решение и граница

Владелец предлагает дополнительный browser-local storage **только** для новых Projects, созданных явно выбранным registered-transfer import. Архитектура AD-31 допускает это направление при условиях ниже: оно изолирует эти Projects от обычных путей **проверенных** старых Web/PWA builds, которые обращаются только к прежним именам хранилищ. Прежние browser Project DB и assets DB, их имена, schema, данные, import/export, обычные команды и history не переписываются и не мигрируются. Новый storage — не Telegram scope, не изменение старой DB version, не сервер и не авторизация. Одни имена IndexedDB не являются границей защиты от другого кода того же origin, общей origin eviction/clear или исчерпания общей квоты.

Это отдельное архитектурное изменение. PRD FR-45/57 и SPEC CAP-10/§1.4 приняли scoped identity и правила нового browser namespace; UX определил общий список, library, частичную недоступность и поведение старой PWA. Эти source decisions задают локальную реализацию, но не являются proof готового runtime, release или physical transfer. Roadmap/stories ссылаются на CAP/FR/NFR и AD-31; применимый readiness, implementation и evidence остаются отдельными, никакой waiver не подразумевается.

Источник для реализации: [FR-45/57](../../prds/prd-InteriorsEditor-2026-07-26/prd.md), [SPEC Project/Backup §1.4](../../../specs/spec-interiors-editor-alpha/project-and-backup-contract.md) и [UX directory/library](../../ux-designs/ux-InteriorsEditor-2026-07-26/EXPERIENCE.md). Принятое решение об ID ниже заменяет прежний открытый вопрос глобальной raw-ID уникальности; его нельзя заново вводить как prerequisite. Прежние browser DB остаются неизменными, FR-44/57/58 сохраняются. Implementation/story owners выполняют действующий проектный gate и фиксируют AD-31; ранее разрешённый S3 local path не является автоматическим подтверждением rollout, physical acceptance или release.

# Substrate и atomic ownership

Предпочтительный минимальный substrate — **одна новая** browser IDB с собственным постоянным именем `interiors-editor-browser-registered` и schema v1; внутри неё отдельные stores для Project pointers, immutable Revisions, staging/attempts, writer fences, publication receipts/journal, pin/GC roots, exact resource bytes и scoped library. Это позволяет новой операции проверять свои predicates в общей транзакционной области, не открывая старые DB для mutation. Если фактическая реализация разделяет этот bundle на несколько IDB, она до первой writable операции обязана доказать эквивалентный recoverable cross-store journal и conditional cleanup по AD-4; одна только разница DB names недостаточна. Browser namespace и его local lock/owner identity выбирает доверенная browser composition, не содержимое файла, user flag или Telegram identity. Domain `Project`, wire и резервный файл не получают storage routing metadata.

Новая browser storage identity — самостоятельный typed local context. Нельзя создавать фиктивный `VerifiedTelegramScope`, подставлять Telegram signed launch, ослаблять `TelegramScopeStore`/AD-26 или использовать `tma-v1:` namespace/lock. Можно выделить и совместно использовать только действительно host-neutral алгоритм через узкие ports, с отдельным browser adapter, собственными predicates и полным отдельным proof; текущие Telegram-specific classes и их прежний GREEN не являются автоматически доказательством browser path. При таком extraction обязательны прежняя действующая Telegram composition и полные существующие TMA storage/runtime/identity и race suites с фактическими Telegram adapters/IDB, без замены их mock-реализацией или ослабления проверок; существующие test-only scope fixtures сохраняются и не объявляются физическим signed-host evidence. Добавляются отдельные browser scoped tests. TMA signed identity, scope, lock/fence, journal/receipt, no-ABA и resource/history semantics остаются неизменными. Прежний `FencedProjectRepository.writeStaging` копированием не становится безопасным.

Новый owner использует те же domain validation, application use cases и обычную repository publication boundary, что и редактор, с отдельными безопасными browser adapters; не вводить параллельную упрощённую модель Project или обход domain/retention/FPC. Смена destination — только решение trusted composition. Адресация и полноценные существующие команды для новых Projects входят в этот scope, а прежние legacy call paths сохраняют своё поведение.

До первого import commit новый scope обязан обеспечить: bounded validated immutable candidate и exact resources; collision-safe `add` Project/Revision/attempt/lease; writer identity и текущий fence/base в той же защищённой transaction до stage/write/overwrite/delete; atomic pointer и durable attempt receipt; exact recovery при неизвестном commit; conditional no-publish cleanup; pins и current/recovery/staging/active undo/redo roots. Stale writer, takeover, cancel, crash и повтор не должны перезаписать или освободить чужие записи/bytes. Две вкладки нового browser runtime координируются по одной scope identity; недоступный обязательный lock, fence, storage capability или proof → новый scope read-only/отказ без fallback к legacy repository. Этот отказ не блокирует безопасные старые Projects. Web Locks и `durability: strict` можно применять лишь с явной проверкой поддержки и отдельной browser UX/readiness оценкой; старый insecure-origin browser не получает новых ограничений, но новый import нельзя объявить writable там, где его обязательные гарантии недоступны.

### Bounded fresh-v0 bootstrap и reopen

Ни обычное открытие Projects, ни directory/capability probe, ни выбор/отказ файла не создают новую DB. Чтение existing-only различает **фактически отсутствующую сейчас DB**, существующую валидную DB и existing/unknown unavailable; probe с `indexedDB.open` не должен оставлять новую пустую DB при её отсутствии: если срабатывает `onupgradeneeded` для `oldVersion=0`, он abort-ит эту transaction и закрывает поздний success. Отсутствие сейчас означает только `not-provisioned/история неизвестна`, не healthy empty и не доказательство, что пользователь ранее не имел здесь Projects. Listing показывает доступный legacy scope и честное состояние нового по согласованному UX.

Только после **явного выбора** registered import и успешных bounded source/schema/domain/resource checks, actual smoke, cancellation и pre-ID representability preflight разрешён bootstrap. Без долгих проверок файла, сетевых операций или пользовательского ввода внутри lock trusted browser composition получает **тот же** exclusive scope Web Lock, который применяют все новые contexts при write, bootstrap и reconciliation; `steal` и рекурсивный захват этого lock запрещены, сам lock не заменяет durable fence. Под lock повторно проверяет generation и актуальный DB state, затем versioned open: если `onupgradeneeded.oldVersion === 0` и попытка не revoked/abandoned, одна native versionchange transaction атомарно создаёт все зарегистрированные stores/keyPaths, browser identity/protocol marker и начальный counter. Это разрешённое создание **новой текущей области**, а не утверждение «раньше данных не было», восстановления данных или полного отсутствия старых snapshots. Если другая новая вкладка уже создала DB, текущая открывает и проверяет её по обычному existing path, не выполняя новый init.

При existing DB точно проверить ожидаемые version/schema, полный inventory stores/keyPaths/indexes, identity и неповреждённый counter; сохранить все их значения, выполнить согласованное recovery и лишь затем разрешать запись. Existing DB с missing/битым/чужим marker, missing/неверным counter, неожиданной schema, future version или неизвестным ownership → read-only/recovery/отказ, без `counter=0`, пересоздания, удаления, upgrade по догадке или fallback к старому repository. Если ранее подтверждённая DB/marker исчезла в живом context, это известная потеря/неопределённость → recovery, не fresh v0. Недоступный lock/IDB, blocked или доказанный abort/no-publish не создают Project; до подтверждённого commit нельзя заявлять `imported`. Cancel, timeout или exception **после** фактического commit и неустановленный исход не доказывают отсутствие публикации: сохранить roots и выполнить receipt-based reconciliation. Во всех случаях source/legacy data не меняются.

После подтверждённого v0 schema commit заново проверить текущий identity/counter, capability и все publication predicates; затем сформировать новый raw Project ID, выполнить exact сравнение с source и проверку обоих известных stores до принятия candidate, а destination атомарно создаёт Project/Revision по FR-45. **Absent** новая DB при подтверждённом v0 означает отсутствие текущих записей этого namespace, но не доказательство отсутствия прежних данных; ошибка открытия existing store не приравнивается к отсутствию. Если schema v0 уже атомарно создана, а import затем отклонён/отменён/не опубликован, она может остаться валидной служебной областью без Project; не удалять её, не заявлять `imported`, при новом явном import снова проверить metadata и все guards. Пустую служебную область разрешено назвать пустой только по успешному актуальному чтению её записей и без утверждения о прошлых данных.

Все новые contexts связывают операции с приватной browser runtime generation и проверенной identity; обработчик native `versionchange` синхронно отзывает допуск старого runtime и запрещает старым callbacks автоматически присвоить новую capability. Сам `db.close()` не отменяет ранее начатые transaction: каждую нужно abort-ить, если ещё возможно, либо дождаться подтверждённого commit/abort, удерживая lock до полного исхода и reconciliation; forced `close`/ошибку соединения также трактовать как revoke/unknown, а не успешное завершение. Все mutation/recovery используют тот же lock, fence, exact attempt и commit predicates. Отмена запроса lock после grant не считается автоматическим abort исполняемой IDB transaction: cancellation обрабатывает её отдельно; уже committed/неясный outcome разрешается через receipt без удаления roots. `onblocked`/timeout/revoke не отменяют `IDBOpenDBRequest` сами по себе: abandoned guard должен abort позднюю upgrade transaction и закрыть поздний `onsuccess`, а поздний callback не действует после утраты lock/generation. Обычные прочие IDB readwrite writes проверяют требуемую durable capability; для native versionchange нельзя выдумывать переданный приложением durability option — его atomicity и поведение проверяются отдельно. Это browser protocol, не Telegram identity.

Origin-wide clear/eviction, полная потеря всех markers либо восстановление snapshot **без этой DB** могут быть внешне неотличимы от `oldVersion=0`; новый v0 не подтверждает восстановление потерянных данных и не доказывает математическую невозможность повторного использования ID через такую внешнюю историю. Восстановленная старая **существующая** v1 DB может открыться без upgrade event с корректными, но устаревшими identity/counter: их одна локальная проверка не доказывает отсутствие rollback или живых старых attempts. Проверенная generation/versionchange/lock ограничивает **кооперирующиеся живые contexts в проверенной lifecycle модели**, не произвольный same-origin код и не недоставленное platform событие. До writable допуска нужно доказать, что stale capability/attempt из предыдущего экземпляра не может писать или очищать current scope; если механизм не способен подтвердить безопасный lifecycle в известной или обнаруженной ситуации, этот путь остаётся fail closed, даже если schema формально valid. При известной или наблюдаемой потере сохраняется read-only/recovery; при неразличимой полной потере или valid-present rollback UX и backup остаются честными, NFR-13 external-eviction risk и отдельный recovery evidence не скрываются. Это ограниченное S2-подобное правило initial bootstrap не утверждает глобальный never-reuse, physical compatibility или release readiness.

Release/startup handshake проверяет применимость manifest, schema/read/write capabilities и recovery **обоих** browser storage contexts до соответствующей writable операции и после update/rollback; текущий `ReleaseStartupCoordinator` подключён к legacy store и автоматически не охватывает новый. Недоступный или несовместимый новый scope не переводит legacy data в новый store и не разрешает молчаливый downgrade/schema reset; безопасный legacy path продолжает работу со своим handshake. Необходимые immutable assets и lazy chunks для directory, codec, editor и обоих путей сохраняются по AD-28; наличие shell/worker или одной исправной DB не доказывает готовность второй, offline path или физическую совместимость.

SPEC §1.4 и UX уточняют user-visible границу: обычное неизвестное состояние новой области не разрешает auto-create/reset; явный validated registered import может инициировать только описанное выше **фактическое** создание current v0. Known потеря metadata существовавшей DB и неизвестный existing state по-прежнему read-only/recovery; возникновение новой текущей области не доказывает, что старые данные отсутствовали или восстановлены.

# Общая directory и все операции

В новом браузере directory объединяет независимо прочитанные legacy и registered источники. Каждая карточка получает доверенный внутренний owner handle `(storage namespace, raw ProjectId)`; raw `Project.projectId`, Revision ID, host addresses и content backup остаются неизменными. Scope не выбирается по префиксу ID, hash, имени Project, полю импортируемого файла или правилу «первое совпадение». При одинаковых raw IDs обе карточки показываются различимо и маршрутизируются раздельно; операция с неподтверждённым owner явно запрещается. UX задаёт понятную метку области, различение совпадающих названий и частичную доступность; нельзя открыть/изменить/удалить другой Project.

Принятая последовательность FR-45 для нового browser registered import: после исходной validation и legacy-representability preflight, но до принятия candidate, сгенерировать raw Project ID и сравнить его с точным source Project ID **без нормализации**, даже когда source отсутствует в локальных stores; совпадение требует другого ID. Затем проверить candidate raw ID относительно существующих Projects **обоих** известных browser stores; совпадение требует другого ID, unavailable/unknown probe закрывает этот import, а не считается свободным. Прямое чтение соответствующего pointer/lookup учитывает и существующий нечитаемый Project; нельзя выводить «нет Project» из отфильтрованной directory. После выбора ID сформировать и вновь проверить exact immutable candidate и resource proof; в destination scope атомарно проверить отсутствие Project/Revision и выполнить no-overwrite `add`, сохраняя scoped no-ABA для Project/Revision/attempt/lease. Abort/конфликт не пишет Project и не освобождает чужие roots; безопасный retry с другим ID возможен в пределах проверенного profile, без бесконечного подбора или скрытого fallback. Текущий browser admission предполагает UUIDv4 и 36 ASCII chars: сохранять эти bounds до отдельного source-owned изменения.

Это **две независимые** IDB: проверка обоих известных stores до принятия не является глобальной атомарной блокировкой. Старый client может конкурентно или позднее создать тот же raw ID; обе записи остаются существующими и раздельными по `(namespace, raw ProjectId)`, без merge, overwrite, удаления или повторной глобальной проверки как условия дальнейшей работы. Нельзя требовать глобальной raw-ID уникальности или старого writer barrier, чтобы признать это принятое FR-45 поведение. Проверка destination внутри своей transaction и его no-ABA остаются обязательными. Если любой lookup не может достоверно определить наличие Project, соответствующий новый import fail closed; уже доступные Projects и другой store сохраняют безопасную работу.

Owner handle и generation/exclusive ownership сопровождают весь lifecycle: load/open, directory actions, rename, create/edit commands, writer lease/takeover, mutation, undo/redo и SessionRetention roots, pending/retry, recovery/repair/RecoveryChangeSet, resource hydration/renderer, pin journal, оба вида export, confirmed deletion и async callbacks. Switch/open другого Project, включая A→B→A с одинаковым raw ID, не позволяет старому async действию выбирать новый global current store. Текущие `ProjectSummary`, controller и resource ports передают только raw ProjectId/hash, а session retention сравнивает raw ProjectId: их необходимо безопасно связать с owner, а не только склеить списки. Import success/status и pending/retry/reopen получают trusted destination capability отдельно от Project/file; потеря owner → fail closed. UI keys, selection identity, эффекты, directory удаление и все фильтры используют composite handle: нельзя случайно удалить обе карточки или оставить старый renderer при переключении одинакового raw ID. Обычное создание/legacy import продолжает пользоваться старым контуром.

Каждый scope открывает собственные resource/library/pin/journal и cleanup, включая model placement и exact repair. Каталог Project показывает доступные ресурсы его области; cross-scope copy возможен только в явно предложенном и выбранном маршруте, без автоматического сведения по hash. Если пользователь выбирает для нового Project модель, имеющуюся только в legacy library, её копирование в новый scope требует проверенных original bytes/hash/length, собственных pin/root и feasibility до Durable mutation; ссылка на legacy browse cache или чужой lease не считается pin. Cross-scope copy не удаляет или автоматически перемещает исходник. Не вводится общий GC: до отдельного полного root-inventory protocol ни один cleanup не удаляет ресурсы другой области или активной undo/redo history.

Если одна IDB недоступна/повреждена/заблокирована, другая остаётся доступной при сохранении её правил, а объединённая directory явно сообщает неполноту/неизвестное состояние источника; это не `empty`, не массовая порча остальных Projects и не разрешение на auto-create/delete/repair. Нужны подходящие typed outcomes и отсутствие stale UI результатов. Две записи с совпавшими именами/IDs не сливаются. Режим ошибки не означает, что другой scope потерял данные.

# Backup, старые PWA и version matrix

Изоляция не делает старый browser exporter V1-wire writer и не ослабляет §1.4. Registered import по-прежнему допускает только exact legacy-backup-representable snapshot с действующими browser validation, FPC, security и limits; новый scope должен поддерживать **прежний** полный offline browser backup с точными данными и локально закреплёнными resource bytes для каждого своего non-corrupt Durable Project. Все последующие допустимые mutations/history должны сохранять эту гарантию; если требуются отдельные scoped checks, они действуют только в новом namespace и не меняют legacy policy. Для нового Project старое действие backup использует именно его scoped repository/resources и прежний codec; использование глобального legacy resource store по raw hash запрещено. Альтернатива — новый complete backup contract/расширение V1 acceptance — требует отдельного решения SPEC/PRD owner и доказательств, не выводится из AD-31. Дополнительный V1 transfer export по AD-30 также получает exact scoped snapshot/resources и не заменяет FR-44.

Старый установленный client, который знает только старые DB names, продолжает видеть и обрабатывать свои прежние Projects, но не показывает и не открывает как тот же локальный Project новый registered namespace. Импорт проверенного поддерживаемого legacy `.interiors` в старом client, если доступен, создаёт **отдельную копию** по обычным правилам, не синхронизирует Project или session history. Это предусмотренное PRD/SPEC/UX техническое следствие, не доказательство того, что старый build уже показывал предупреждение, или что old-PWA roundtrip выполнен. Реализация следует принятой UX: до потенциального rollback/работы старой PWA объяснить невидимость новых Projects и доступный проверенный путь файла, не называть Project удалённым и не обещать бесшовность; старый build нельзя заставить показать новое уведомление задним числом. Version/rollback matrix требует фактического corpus. Предыдущие legacy Projects/экспорт продолжают быть доступны по прежнему contract. Browser tab и iOS Home Screen contexts не предполагаются одной storage областью.

# Локальная реализация по срезам

1. Выделить общий host-neutral storage protocol/ports только там, где он действительно одинаков; оставить существующие Telegram adapter, signed scope/bootstrap, DB и lock identity как реальные Telegram зависимости. После каждого извлечения прогнать неизменённые TMA storage/runtime/identity и race suites с реальным adapter, прежде чем использовать общий слой в browser.
2. Добавить browser-owned IDB и lifecycle из раздела выше: непродуцирующий probe, явный fresh-v0, guarded reopen, metadata/counter, общий lock и generation, atomic fenced attempts/receipts/pins. Никакого изменения прежних DB или фиктивной Telegram identity. Проверить это отдельно до подключения новых Projects к editor.
3. В существующем registered ImportUseCase сохранить validation/profile и ввести trusted browser destination capability: source-representability preflight → bootstrap/reopen → allocation → exact source-ID и оба storage lookups → sealed candidate → собственные pin/atomic add/receipt. Передача owner в status/pending и fail-closed recovery обязательна; обычные legacy import и новые domain use cases не переписываются под другой формат.
