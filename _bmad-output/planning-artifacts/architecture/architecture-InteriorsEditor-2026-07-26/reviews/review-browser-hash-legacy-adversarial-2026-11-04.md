# Независимый adversarial review: browser hash guard и legacy backup

Проверены AD-30 в `ARCHITECTURE-SPINE.md`, разделы «Format-specific BackupFeasibility перед publication», «Browser admission при существующем exporter» и порядок проверок в `telegram-portable-v1-disposition-2026-11-04.md`, а также соответствующие текущие Web application paths. Это review документов и существующего кода, а не подтверждение реализации предложенного guard. Канонические документы не изменялись.

Вывод: **до закрытия указанных ниже условий нельзя считать изменение готовым к включению для registered Web ingress или доказательством полной backup readiness.** Документы правильно сохраняют Telegram alias semantics, запрещают history bypass и оговаривают незавершённость roundtrip; тем не менее несколько условий пока не превращены в проверяемый admission/rollout contract. Наблюдение о неготовности полного roundtrip не является доказательством, что каждый из приведённых ниже случаев уже был воспроизведён на UI или устройстве.

- **Lowercase не исключает записываемый, но неэквивалентный legacy backup.** Disposition §122–132 разрешает registered Web ingress после проверки SHA, одновременно признавая, что старый `serializeProjectCanonically` через `JSON.stringify` превращает `-0` в `0`. Значение допускается V1-wire и `copyProject` его сохраняет, тогда как проверка существующей default feasibility над `Revision.serializedProject` уже не видит различия. Если допустимая геометрия с `-0` и lowercase hashes станет Durable, старый exporter может выдать `ready`, но обратный импорт не вернёт исходное значение. Уточнить, где до Durable проверяется сохранение необходимой семантики всем реально доступным Web backup/reimport путём, либо заблокировать затронутый registered ingress до доказанного решения. Оговорка «проверка pending» сама не является admission barrier.
- **Own-undefined имеет отдельный механизм потери.** V1-wire различает отсутствующее optional property и собственное свойство со значением `undefined`, а старый JSON exporter последнее опускает. Проверка только отрицательного нуля или только ресурсов не закрывает этот случай; покрыть marker на каждом поддерживаемом optional pointer с own-property сравнением после реального export/import и reopen либо явно отказать до Durable. Числовое равенство или обычное JSON-сравнение недостаточны.
- **V1String с непарным surrogate может пройти wire и попасть в поздний отказ browser default.** Разрешённый `V1String` восстанавливается как JS code units, а старый JSON serializer записывает escape; текущий default `assessBackupFeasibility` затем запускает PPJ AST-R1 для internal Revision, где scalar rejection действует. Ранний browser predicate, проверяющий лишь hash, не гарантирует отказ до staging для такого файла, особенно без ресурсов. Требуется явное решение: либо показать отдельный поддерживаемый путь, либо проверить применимые browser-only ограничения на неизменяемом candidate до побочных эффектов и сохранить порядок ошибок.
- **Не определён полный browser representability predicate.** Disposition требует повторить hash predicate и сохранить остальные проверки, но не определяет соответствие исходного V1 snapshot фактическому выводу старого exporter и его импорту: структура, разрешённые optional поля и exact values должны анализироваться вместе с domain/resource условиями. Проверка только `revision.serializedProject` не может обнаружить различия, уже уничтоженные сериализацией. Нужен исполняемый oracle, основанный на реальных browser writer/reader и определённом сравнении сохраняемых значений, или доказанно эквивалентная консервативная спецификация; само перечисление примеров не охватывает остальные различия.
- **Положение раннего hash rejection в общем порядке неоднозначно.** §126 говорит «после предусмотренных проверок входного файла», а §136 перечисляет schema, policy, domain и exact resource/hash validation, не размещая новый browser refusal относительно каждой из них. При одновременных uppercase, повреждённом checksum/GLB, неподходящей геометрии или превышении 25 MiB разные реализации могут вернуть разные outcomes. Зафиксировать точную стадию и обязательные комбинационные проверки, включая cancel, и не переносить проверку перед checksum или иными ранее обязательными проверками ради раннего выхода.
- **Результат policy отказа не содержит различимого основания.** §126 допускает общий `PROJECT_BACKUP_ENVELOPE_EXCEEDED`, но тот же код уже обозначает размеры и другие feasibility отказы. Без типизированного подоснования либо другого надёжного контекста UI не может одновременно точно объяснить именно несовместимость регистра и не приписать её размеру или повреждению ресурса; поздний отказ репозитория также должен отличаться от обычного retryable persistence failure. Зафиксировать совместимый контракт распространения причины для раннего и окончательного отказа, включая публичный UI, а не только расширение union type.
- **Повторная проверка относится к тому же snapshot только при явном владении данными.** §126 требует immutable candidate на final boundary, но текущий `SessionRetentionProjectRepository.withAdmission` делает `copyProject` лишь при переданной custom policy; browser default использует входной объект непосредственно. Между ранним анализом, асинхронными чтениями resources и publication допускается изменение candidate, если просто добавить predicate в текущий код. Зафиксировать получение и владение одним exact snapshot до первого async действия, его применение в обеих проверках и атомарной publication, либо эквивалентную fence/identity проверку с отказом при несовпадении.
- **Граница обязательной проверки точных resource bytes у browser composition остаётся неявной.** Новый lowercase predicate обязан срабатывать и без optional resource port, но текущий `assessEnvelope` при отсутствии порта пропускает `hasExactPinnedResources`. Поэтому успешное прохождение нового predicate без порта не доказывает hash, длину и pin/readiness. Нужен явный invariant каждого пути publication: либо обязательные scope-correct resource ports и проверка на publication boundary, либо конкретный доверенный владелец с тем же доказательством и защитой от race; сохранить отдельно тест отказа uppercase без порта.
- **Блокировка rollout для несовместимого history не определяет полный охват состояний.** §128 правильно не разрешает bypass по history flag, но не определяет, как до активации новой browser policy обнаруживаются текущие и redo/undo roots во всех живых вкладках, версиях и одновременно открытых контекстах, включая переходы, начатые до обновления. `sessionRetentionRoots()` одного controller не является полной inventory. Нужны scope/контекст границы rollout и проверяемая координация либо запрет активации там, где охват нельзя доказать; иначе новый guard может начать отвергать ранее принятый undo/redo до обнаружения проблемы.
- **Текущий и history-only случай требуют разных проверяемых состояний.** Историческая uppercase Revision может находиться в undo, redo или быть current при lowercase candidate на противоположной стороне. Защита ресурсов от GC не доказывает, что каждый ранее разрешённый переход выполним или что получившийся current backup-ready; при этом запрет перехода по одному history flag тоже не решает AD-4. Доказательство rollout должно покрыть все позиции, направление каждого перехода, сохранность обоих стеков при отказе и случай перезапуска/смены writer. Если одновременно сохранить FR-44 и прежний переход нельзя, состояние остаётся заблокированным до source-owner решения, без неявного discard.
- **Late-rejection cleanup требует crash/retry disposition, а не только формулировки «очистить своё».** Существующий importer после `markForPublication` намеренно сохраняет lease и candidate при `persist-failed` для retry/export и reconciliation. Новый документ требует conditional cleanup, но не определяет, как достоверно различить policy refusal от неопределённого результата публикации, как обрабатывается crash между проверкой, отметкой и cleanup и кто проверяет root ownership. До разрушительных действий нужен доказанный no-publication/receipt и проверка всех owners; при неизвестном результате сохранять bytes и lease для безопасной reconciliation. Проверить повторную попытку и чужой pin без стирания source.
- **Доказательство старого export должно включать старый importer, а не только получение файла.** `ExportPortableBackupUseCase` выдаёт `ready` после сериализации и проверки ресурсов, не проверяя, что его собственный output снова проходит `decodeCanonicalProject`, PPJ AST и structural/domain checks с теми же значениями. Тест `lowercase import → прежний export/reimport` указан общо, но для admission нужны зафиксированные assertions exact Project semantics, всех referenced bytes, checksums, reopen и ожидаемо заменяемых при import ID/timestamps; отдельно проверять результаты `ready`, успешный системный handoff и подтверждённый повторный import.
- **Различие 25/50 MiB должно быть проверено в каждой затронутой комбинации, включая отказ до staging.** Текст сохраняет меньший custom admission cap, но отдельное указание границ ещё не показывает, какой outcome побеждает при uppercase hash и GLB >25 MiB, а также при existing-reference exact repair. Нужна таблица с route-specific precedence: registered Web new reference, Telegram new admission и exact repair; отсутствие доказанной применимости не должно превращать технический 50-MiB smoke в право на новую admission.
- **Защита «только browser» нуждается в проверке composition, а не только расположения predicate.** В текущем коде некоторые use cases вызывают feasibility непосредственно, а wrapper также выбирает default при отсутствии injected policy. Само размещение проверки вне общего envelope helper не доказывает, что Telegram create/import/history paths всегда получают свой зарегистрированный adapter и scope-correct resources. Нужны integration checks настоящих factory/composition путей, включая отсутствие adapter и resources: Telegram должен fail closed, а не незаметно получить browser default или пропустить проверку.

Проверенные опорные места текущего кода: `apps/web/src/application/backup-feasibility-policy.ts`, `session-retention-project-repository.ts`, `import-portable-backup.ts`, `export-portable-backup.ts`, `apps/web/src/domain/canonical-serialization.ts`, `copy-project.ts`, `project-json-transfer.ts`, `apps/web/src/app/shared-project-controller.ts` и `apps/web/src/adapters/portable-backup/registered-runtime-portable.ts`. Browser default exporter реально подключён через shared controller; выводы о семантических различиях опираются на непосредственную реализацию serializer и decoder. Доказательства пользовательских данных, физического устройства и завершённого rollout не заявляются.
