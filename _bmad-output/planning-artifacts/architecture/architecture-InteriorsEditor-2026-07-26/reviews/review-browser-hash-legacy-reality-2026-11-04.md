# Independent reality review — browser hash and legacy export

Date: 2026-11-04. Scope: updated AD-30 and `telegram-portable-v1-disposition-2026-11-04.md`, checked against the current browser implementation, SPEC companion §1.4, FR-44 and AD-4. No canonical artifact or application code was changed. The probe is synthetic; this review did not execute new tests or examine user data.

**Verdict: PASS WITH IMPLEMENTATION AND EVIDENCE PENDING for the revised architecture; NOT READY to enable the registered browser ingress.** The browser-only lowercase guard addresses the reproduced hash-case defect. The updated disposition now expressly blocks a candidate/path unless the entire candidate and its resources are proved exactly representable by the old browser exporter, and blocks rollout for incompatible history/current states until a safe source-owned route is proved. Neither proof nor the guard is implemented or verified by this review.

- The isolated `browser-alias-probe-exact.log` records `importRegisteredPortableBackup` returning `durable`, preservation of the uppercase key and real GLB bytes, and then `exportPortableBackup` returning `PORTABLE_BACKUP_RESOURCES_UNAVAILABLE`. `apps/web/src/application/export-portable-backup.ts:122` independently requires lowercase 64-hex and literal checksum equality. This is a demonstrated defect for that synthetic candidate, not evidence of affected user projects, a completed fix or device acceptance.

- The old browser serializer loses numeric `-0` and own-`undefined`: a candidate with no assets or only lowercase hashes can pass a hash-case predicate while exporting a different V1 state (`export-portable-backup.ts:62`; `domain/canonical-serialization.ts:3`). The revised disposition correctly requires exact representability of the whole candidate and resources before publication, closing the earlier specification gap. This is a release-blocking proof/implementation obligation, not evidence that such a check exists. Whether each distinction is semantically material to FR-44 should not be assumed without a source-owner decision.

- The proposed default guard is not implemented in the inspected `assessBackupFeasibility` (`backup-feasibility-policy.ts:53,82`): the optional resource-port path can be absent and the current shared resource check accepts SHA aliases by bit equality. Future implementation must check the raw lowercase grammar unconditionally in browser default policy and must not move the restriction into the envelope helper shared by trusted Telegram V1. Preserve independent resource pin, length, bytes, checksum and envelope checks.

- The final wrapper currently sends `publishNextRevision(..., intent="history")` through the same feasibility admission as ordinary publication (`session-retention-project-repository.ts:63–69,94–107`). Tightening that admission can reject a previously accepted uppercase undo/redo target. Bypassing it merely because the input says `history` can instead produce a current Durable Project that the old exporter cannot back up. The disposition appropriately blocks rollout for affected states until a source-owned, demonstrated reconciliation exists; preserve that gate and test both undo and redo, current/history roots, failed transition and reopen.

- SPEC companion §1.4 describes a history transition as not a new semantic Revision, while the implementation uses `publishNextRevision` and the architecture expressly forbids a bypass based only on a history flag. The semantic label does not establish an implementation or an FR-44 exception. Reconcile the wording so it cannot be read as authorization to republish an uppercase target without proving backup readiness, ownership and fencing.

- The proposed early failure is not representable by the current typed import result: `ImportPortableBackupResult.kind="rejected"` does not include `PROJECT_BACKUP_ENVELOPE_EXCEEDED` (`import-portable-backup.ts:44–64`). The disposition correctly identifies this as future work. The final contract must connect its chosen typed policy outcome through the controller and UI; in `AppShell.tsx:2956` only rejected outcomes reach reason-specific feedback, while `persist-failed` takes a generic error branch.

- A reusable envelope reason alone does not identify why a valid uppercase resource was refused: the same code covers envelope and resource failures. Provide a typed, testable distinction or equivalent unambiguous context so the UI can explain old-export incompatibility without claiming corruption or a missing asset; preserve established reason precedence for malformed archives, cancellation, limits and checksum failure.

- The present import stages resource bytes before its final repository publication (`import-portable-backup.ts:109–131,184–196`). A guard added only at that publication would generate a `persist-failed` status and deliberately retain the candidate/pins for retry. The architecture correctly calls for a browser-only early predicate before staging as well as a final check; tests must verify no stage, pin, candidate allocation, publication or source change for that early policy refusal.

- A late rejection, thrown publication, cancellation or unknown commit outcome cannot be treated as equivalent proof that bytes are unowned. The current importer intentionally retains staged pins on publication failure (`import-portable-backup.ts:192–196`). Conditional cleanup needs proved no-publication, attempt ownership, writer/fence and root predicates; otherwise retain the journal/bytes for reconciliation. Race tests must include shared pre-existing pins and ambiguous outcome, not only a simple pre-stage refusal.

- The disposition requires the final admission to assess an immutable candidate, but the inspected default wrapper copies the input only when an injected policy exists (`session-retention-project-repository.ts:85–102`). A browser-default implementation needs actual exclusive ownership or an exact recheck at the fenced publication boundary, including changes made while async resource verification is pending. Checking a mutable candidate once and then publishing a different state would defeat the guard.

- Lowercase alone also does not establish resource representability. The old exporter rejects repeated identical raw resource hashes (`export-portable-backup.ts:130–138`), while default feasibility coalesces same-length duplicates in a `Map` (`backup-feasibility-policy.ts:95–109`). The current V1 import shape validator rejects exact duplicate hashes, but `createCustomGlbFloorItem` and its wall counterpart check duplicate definition IDs rather than duplicate hashes. Whether another reachable publication path admits duplicate hashes is unproved; test that boundary or show the upstream invariant before claiming all browser default candidates are exportable.

- The revised AD-30 distinguishes preserving the previous browser checks and checksum from adding the lowercase feasibility guard. Verify that implementation retains those checks, decoder and exporter while changing admission; an all-purpose replacement policy or silent use of the registered V1 writer would exceed that boundary.

- The proposed lower-case success corpus must check the complete exported and reimported Project and exact referenced bytes, not only a `ready` result. Include old files and readable sole copies without automatic normalization, mixed-case aliases, missing/corrupt bytes, existing history, prior error precedence and the unchanged Telegram V1 path. Physical Web/PWA ↔ Telegram roundtrip and an accessible recovery path for ambiguous sole copies remain separately pending; neither this review nor the probe establishes FR-57 acceptance.
