# Независимая rubric/source-проверка: browser hash admission и legacy exporter

Дата: 2026-11-04. Объекты проверки: AD-30 в `ARCHITECTURE-SPINE.md` и разделы browser admission и V1 feasibility в `telegram-portable-v1-disposition-2026-11-04.md`. Сверены SPEC companions `project-and-backup-contract.md` §1.3–1.4 и `telegram-platform-and-compatibility-contract.md` о registered browser ingress, PRD FR-44/FR-57 и действующий код. Канонические источники этой проверкой не изменялись.

## Вердикт: PASS С НЕЗАКРЫТЫМИ IMPLEMENTATION И EVIDENCE

Предложенный browser-only guard обоснован как узкое предотвращение уже воспроизведённой потери backup-ready после новой публикации. Обновлённые архитектурные тексты согласованы с §1.4 по прежнему exporter, точным keys, изоляции Telegram V1 и сохранению истории. Первоначально найденное сужение gate замены exporter в AD-30 исправлено: теперь он охватывает все non-corrupt Durable Projects, включая состояния вне closed V1 grammar. Guard, безопасный переход по существующей истории и полноценная совместимость не доказаны текущей реализацией. Этот review не является implementation-readiness verdict, разрешением rollout или physical acceptance.

## Проверенные основания

FR-44 требует полный offline Portable Backup для каждого non-corrupt Durable Project в пределах действующей policy. FR-57 требует проверяемый обмен на обеих поверхностях, сохранение исходника и exact hashes; отказ от проблемного current-файла не закрывает затронутую совместимость. SPEC §1.4 предписывает browser-only проверку каждого исходного lowercase 64-hex key до новой semantic publication, без переноса guard в общую Telegram V1 feasibility и без автоматического изменения старых данных. SPEC отдельно требует сохранения уже существующих undo/redo entries и блокирует rollout для затронутого состояния до доказанного безопасного пути.

В `export-portable-backup.ts:122–150,163–170` прежний exporter требует lowercase key и raw equality результата SHA с key. В `backup-feasibility-policy.ts:55–70,139–169` default feasibility пока не содержит browser-only запрета uppercase, а ресурсная проверка сравнивает hash по 256 битам и принимает aliases. Изолированный probe `/tmp/interiors-tma-registered-transfer-xnkbxhq1/apps/web/reports/s3-registered-transfer/browser-alias-probe-exact.log` фиксирует один импорт uppercase GLB как `durable` и последующий отказ старого exporter `PORTABLE_BACKUP_RESOURCES_UNAVAILABLE`. Это evidence дефекта конкретного исполняемого сценария, не свидетельство исправления, работоспособности всех routes или device acceptance.

## Находки и незакрытые обязательства

- Текущая реализация ещё не реализует browser-only representability guard. Одной правки текста недостаточно: нужна проверка каждого raw key в default policy даже без optional resource port и повторное применение к фактическому candidate перед публикацией. Не вносить lowercase rule в общий `assessBackupEnvelopeFeasibility` или Telegram V1 adapter: иначе зарегистрированные case-sensitive aliases перестанут работать.
- Текущий `SessionRetentionProjectRepository.publishNextRevision` запускает общую feasibility и для `intent: "history"` (`session-retention-project-repository.ts:63–69,94–107`). Поэтому прямое добавление guard без отдельного доказательства сломает переходы к существующим uppercase entries. Один flag `history` не доказывает, что target — действительно принадлежащая активной undo/redo ветке Revision. Нужен source-owned безопасный путь с проверкой ownership, revision identity и содержимого, hashes/bytes, roots, expected base и fence; если он одновременно не обеспечивает применимую backup readiness, rollout для соответствующего состояния остаётся заблокированным. Автоматический discard или нормализация не являются решением.
- В текущем persistence delegate `publishNextRevision` не использует `history` как доказательство принадлежности и направляет candidate в общий staging/publication путь (`durable-project-repository.ts:77–83,109–132`). Следовательно, нельзя считать защиту history реализованной только потому, что controller передал этот intent, или считать наличие старой Revision разрешением обойти остальные проверки.
- Уточнённый disposition задаёт для registered browser route source checks и smoke до guard и staging, сохраняя legacy route; при недоказанной precedence rollout блокируется. Реализация пока требует проверки этого порядка: существующий `ImportPortableBackupUseCase` в одной ветке вызывает smoke до staging, а в другой — после (`import-portable-backup.ts:113–157`). Нужны проверки сочетаний uppercase с невалидным GLB, другой более ранней ошибкой и cancellation; перестановка вызова без доказательства может подменить причину отказа.
- `ImportPortableBackupResult` сейчас не допускает `PROJECT_BACKUP_ENVELOPE_EXCEEDED` как early `rejected` reason (`import-portable-backup.ts:44–53`), а поздний policy отказ превращается в `persist-failed` с candidate и удержанными ресурсами (`:185–196`). Требуется связать типизированный ранний policy outcome с понятным объяснением несовместимости прежнего browser export; не называть файл повреждённым и не обещать исправление повтором неизменённого импорта. Проверить отображение в controller/UI, а не только return type.
- При уже начатом staging нельзя выводить право на удаление лишь из отказа policy или утраты fence. Надо подтвердить fenced no-publication и conditional cleanup собственной попытки, сохранив чужие, current, recovery, staging, pin и обе history roots. Поведение при неопределённом исходе, конфликте существующих bytes, отмене, crash и takeover нуждается в исполняемом evidence; retention ресурса pending candidate нельзя автоматически считать безопасно удаляемым.
- Ранний predicate и финальная feasibility должны проверять один и тот же защищённый candidate: текущее копирование в `session-retention-project-repository.ts:85–93` условно включается для переданной policy, а не автоматически для browser default. Необходимо доказать отсутствие изменения candidate между проверкой и fenced publication либо проверять exact state на commit boundary. Это особенно важно, поскольку internal JSON checksum не различает все представимые V1 состояния.
- Lowercase guard устраняет конкретный подтверждённый hash-case дефект, но не доказывает полную экспортируемость каждого принимаемого V1 snapshot: disposition отдельно отмечает различия legacy serializer для `-0` и own-undefined. Нужны отдельные проверки exact semantics и решение для непредставимых состояний; успешный lowercase GLB roundtrip нельзя использовать как доказательство полного FR-44/FR-57.
- Даже корректный отказ uppercase зарегистрированного V1 файла остаётся ограничением переноса Telegram → Web/PWA. FR-57 и SPEC §1.4 не позволяют переименовать такой файл в corrupt или закрыть compatibility одним отказом. Нужны проверенный end-to-end путь с точными ресурсами либо отдельное решение владельца источника/продукта; заявлять work-around только после проверки соответствующих версий и реального пользовательского пути.
- Требования к будущим испытаниям в disposition присутствуют, но их выполнение не доказано этим review: нужны реальные GLB и SHA, uppercase/mixed-case и несколько aliases, lower-case import → прежний export/reimport, optional-port отсутствует, old browser outputs и PPJ regressions, Telegram V1 raw-key semantics, отказ без изменения source, все активные history roots, races/cancel и 25-MiB custom против 50-MiB portable boundary. Положительное browser evidence не заменяет реальные внешние файлы и физический обмен на целевых клиентах.
