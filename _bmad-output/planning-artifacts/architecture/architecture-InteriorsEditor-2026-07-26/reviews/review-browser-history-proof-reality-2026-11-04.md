# Independent reality review — browser history transition proof

Date: 2026-11-04. Scope: AD-4 and “Минимальный browser history transition” in `telegram-portable-v1-disposition-2026-11-04.md`, checked against browser controller, persistence, resource and policy code plus the Project/Backup companion. This review changes no canonical artifact or application code. It is source inspection, not an executed test or a readiness gate.

**Verdict: PASS WITH IMPLEMENTATION AND EVIDENCE PENDING for the revised design; NOT READY to enable it.** The existing-row-only transaction, trusted controller selection, full target identity and separate FR-44 gate address the principal gaps in the current browser path. The revised text now explicitly requires post-success protection against old staging and durable receipt-based or equivalent reconciliation after an ambiguous outcome. Old-build coordination, ABA, protected roots, the exact comparator and compatibility of existing uppercase history remain blocking proof obligations. None of the proposed new proof or required evidence is established by the inspected implementation.

- AD-4 now explicitly calls the fenced atomic existing-row-only browser transition a target, rather than a description of present implementation. Today `ProjectController.travelSessionHistory` calls `publishNextRevision(..., "history")` (`apps/web/src/app/project-controller.ts:3938–3980`), and browser `DurableProjectRepository` sends it through `publishCandidate` and `writeStaging` (`apps/web/src/adapters/persistence/durable-project-repository.ts:99–125`). Retain the disabled-for-unproved-scope gate; the normative target is not evidence of an already safe browser path.

- The disposition accurately identifies that `sessionRetentionRoots()` copies arrays, not their candidates, and may append `writerLeaseRecoveryCopy` to its `undo` roots (`project-controller.ts:708–721`). It is neither a capability nor proof of the top entry. Future implementation must bind the actual trusted direction, exact top target, current source and live session identity, protect the entire snapshot and serialize local history until completion; public `intent="history"` or any matching root is insufficient.

- The current controller checks the source and `publicationInFlight` after the asynchronous resource read, then marks publication active (`project-controller.ts:3947–3970`); its post-publication stack check compares target revision IDs only (`project-controller.ts:4027–4035`). Those steps are not the promised deep immutable ownership proof or a cross-context transaction. Tests must include non-top targets, recovery roots, stale sessions, mutation of a shared object and same-ID/different-content candidates.

- The existing IndexedDB `writeStaging` unconditionally executes `revisions.put` before pointer fence and base verification (`indexeddb-versioned-project-store.ts:146–164,191–239`); `discardStaging` can delete a non-current revision without proving it is not a retained history root (`:323–340`). The new route must not use this staging sequence for history and must protect rows against independently running old staging/recovery/cleanup. An outside-transaction read-and-compare does not close the race.

- A previously paused old `writeStaging` can resume after a successful pointer commit and overwrite the newly current target row. The revised disposition explicitly extends coordination through successful commit for current and history roots. Demonstrate that all old operations are drained, revoked or otherwise technically prevented from modifying protected revisions for as long as they can resume. Prove this for already-open old browser builds; a cooperative new-code mutex or new-code-only fence cannot by itself constrain them. If it cannot be proved, keep affected rollout blocked.

- Existing pointer CAS only compares a Revision ID (`indexeddb-versioned-project-store.ts:224–230`); A→B→A can therefore satisfy a stale base check. The disposition correctly requires a durable monotonic generation checked at commit or a proven equivalent cross-context serialization and fencing protocol. If generation is chosen, show that every writer, including compatible old builds, advances and preserves it; adding a field that an old `projects.put` drops is not a proof.

- A successful pointer commit followed by a lost response or crash before `completeHistoryTravel` can leave the live controller's source/target stacks unresolved (`project-controller.ts:3976–4002,4027–4050`). The revised disposition requires a receipt in the pointer transaction, or a proven equivalent, and committed/no-publication/unknown reconciliation. Prove that its attempt identity and generation remain unambiguous under ABA and later writes, that local completion occurs exactly once and that current/undo/redo roots remain protected while outcome is unknown. A restart ending a session is not evidence that an active controller handled an ambiguous result correctly.

- Exact Revision identity is stronger than current `isReadable`: it verifies a checksum of `serializedProject` and compares JSON-normalized values (`durable-project-repository.ts:267–305,328–342`), which do not distinguish `-0` from `0` or own-`undefined` from absence. The required independent comparison must include all structured candidate and Revision fields, array properties, UTF-16 values and resource-manifest identity without mutating the objects; verify the exact persisted row and its Project ownership inside the transaction. Fail closed when a source value cannot be represented or compared exactly.

- The transaction must bind its verified row, project pointer and lease to the same Project and exact base and recheck the current fence/expiry at commit. `ProjectPointerRecord` also stores `name` (`indexeddb-versioned-project-store.ts:27–30,234–238`); the revised disposition explicitly requires updating derived directory metadata from the target. Verify coherent metadata and receipt atomically with the pointer, and reject missing, cross-project or replaced rows without synthesizing them.

- Verified resource bytes and pinned roots live outside the Project pointer transaction; the browser custom asset store opens a separate IndexedDB database (`indexeddb-custom-asset-resource-store.ts:20,252–254`). A hash read before commit is not proof that cleanup cannot revoke or replace it later. The required cross-store journal, root accounting or equivalent coordination must protect exact bytes for current and both active branches through commit and reconciliation, including competing cleanup and stale writer operations; no remote fallback or silent resource replacement is implied.

- A previously durable or exact-owned uppercase target still fails the current browser exporter: `isCustomGlbDefinitionPortable` requires lowercase hex (`export-portable-backup.ts:122–168`). History ownership cannot override FR-44. The disposition correctly blocks such a target unless another source-owned solution establishes applicable complete backup readiness; it does not classify casing alone as corruption and does not authorize automatic `DiscardSessionHistory`. Preserve source, current pointer and roots on refusal.

- Existing `SessionRetentionPolicy` computes resource union across current, undo, redo and prospective candidate (`session-retention-policy.ts`); the browser default feasibility admission runs before this calculation (`session-retention-project-repository.ts:77–125`). The new history route must preserve these checks without accidentally treating the synthetic recovery root as a selectable stack target. It must also prove the whole old-export representation and exact resources, not just lowercase spelling or a previous admission.

- The design's required evidence must cover exact lowercase undo→redo, altered/non-top/foreign targets, own-`undefined`, `-0` and array properties with identical JSON checksums, lost/changed row, resource disappearance and protected pins, stale base, A→B→A, lease expiry/takeover, and both pre-commit and post-success old staging/cleanup. Include cancellation, crash, lost response, unknown outcome, concurrent old builds, identity reuse, all revision rows, foreign Project and pointer metadata. Run the real browser IndexedDB path and preserve existing Web/PWA tests; in-memory mock success is not cross-context evidence.
