# Независимая rubric/source-проверка browser history transition

Дата: 2026-11-04. Проверены новый текст AD-4 в `ARCHITECTURE-SPINE.md` и раздел «Минимальный browser history transition» в `telegram-portable-v1-disposition-2026-11-04.md` против SPEC `project-and-backup-contract.md` §1.3–1.4, PRD FR-44 и текущих browser controller/repository/IndexedDB adapters. Канонические документы этой проверкой не изменялись.

## Вердикт: PASS ДЛЯ АРХИТЕКТУРНЫХ УСЛОВИЙ; IMPLEMENTATION И EVIDENCE PENDING

Решение задаёт необходимые ограничения для возврата к существующей Revision без перезаписи, не превращает `history` в доверенную capability и не объявляет FR-44 выполненным для несовместимого uppercase target. Нет установленного противоречия проверенным источникам. Обновлённый текст также учитывает directory metadata и receipt для неопределённого результата. Это архитектурные условия, а не доказательство, что предложенный путь реализуем со старыми открытыми клиентами, реализован, готов к rollout или закрывает требования FR-44/FR-57 для такого target.

## Сверка источников и текущего кода

SPEC §1.4 запрещает ломать существующую active History, требует проверяемое trusted ownership, exact identity, resources, base и fence и запрещает считать intent или in-memory roots достаточным доказательством. FR-44 требует complete offline backup для non-corrupt Durable Project текущей policy; exact переход по старой Revision сам по себе не делает её backup-ready. AD-4 требует fenced transition, сохранение current/recovery/staging и history roots и отсутствие автоматического discard.

Текущий `ProjectController.sessionRetentionRoots()` делает копии массивов и может добавлять recovery copy в `undo` (`project-controller.ts:708–722`). `travelSessionHistory()` выбирает вершину stack, но существующее API далее передаёт строковый `"history"` (`:3938–3979`); `SessionRetentionProjectRepository` применяет общую feasibility ко всем `publishNextRevision` (`session-retention-project-repository.ts:63–69,94–107`). Следовательно, предлагаемый trusted selection и отдельный proof не существуют только из-за наличия этого флага.

Текущий `IndexedDbVersionedProjectStore.writeStaging` выполняет `revisions.put` до проверки base/fence (`indexeddb-versioned-project-store.ts:146–164`), а `discardStaging` может удалить Revision, отличающуюся от current pointer (`:323–341`). Обычный pointer record содержит и `name`, и current Revision ID (`:27–31,234–240`). Новый текст корректно требует отдельного existing-row-only механизма, защиты от старого staging/cleanup и атомарного обновления соответствующей metadata; текущее поведение не является доказательством этого механизма.

## Незакрытые обязательства и проверки

- Доказать непубличную привязку к активному controller, направлению и **точной вершине** соответствующей ветки, включая отмену и повтор: корень recovery, не-top entry, чужой Project, старый session token или один `intent` не должны давать право на специальный путь. Нужен test на конкурентное изменение history между выбором и завершением.
- Доказать, что глубокий immutable snapshot сохраняет полную identity и structured values хранимого candidate и Revision: raw IDs, checksum, serialized Project, manifest и дополнительные собственные свойства, `-0`, own-undefined, UTF-16 и array properties. Один checksum или JSON equality не обеспечивает такое равенство; неподдержанная форма должна давать сохранный отказ.
- Нужен настоящий existing-row-only transaction на фактической IDB row: source/current pointer, target ownership/identity и writer fence/base проверяются в той же atomic boundary, target row не пишется и не удаляется. Тестировать отсутствующую или изменённую row, чужой Project, conflict и отказ transaction без изменения pointer/roots.
- Поле `name` в текущем pointer record должно соответствовать проверенной target Revision после Undo/Redo переименования. Изменение только `currentRevisionId` оставило бы directory metadata устаревшей. Уточнённый архитектурный текст теперь требует атомарного обновления pointer и derived metadata; нужен исполняемый тест для rename/undo/redo и reload.
- Требование atomic transition не исчерпывается защитой во время одной IDB transaction: старый `writeStaging`, recovery или `discardStaging` могут позже затронуть новую current либо другие history roots. Доказать project-scoped координацию на всём заявленном интервале и со старым открытым browser build. Если старый клиент не участвует в барьере или его поведение нельзя безопасно ограничить, применимый rollout остаётся закрытым.
- Проверка base только по revision ID не защищает от A→B→A. Необходимы доказанные generation/serialization и fencing для всех взаимодействующих writer contexts и delayed async operations; новый guard нельзя считать готовым по одному тесту stale-base. Текущий pointer record не содержит durable generation (`indexeddb-versioned-project-store.ts:27–31`).
- Новый текст требует durable receipt операции в той же pointer transaction либо доказанного эквивалента. Необходимо реализовать уникальную связь с Project, source/target, generation и fence и доказать published/no-publication/unknown после потери ответа. При committed результате stack/current доводятся ровно один раз; при no-publication сохраняются source и stacks; при неопределённости нельзя безусловно откатить source, повторно двигать stack или освобождать roots. Нужны crash/retry tests до и после commit, включая ABA.
- Обновление history stacks в памяти и fenced pointer составляют один логический переход даже при сбое между commit и callback. Текущий `completeHistoryTravel` меняет stack после результата repository, а retry при stale-base восстанавливает source state (`project-controller.ts:3511–3546,4027–4050`); это не доказательство корректной reconciliation при потерянном ответе. Session-only history после полного restart не должна превращаться в обещание portable history; ресурсы и Durable current при этом остаются защищёнными.
- Target resource hashes, длины и exact pinned bytes, domain/envelope и `SessionRetentionPolicy` должны оставаться действительными до commit/reconciliation. Ресурсный store использует отдельную IndexedDB (`indexeddb-custom-asset-resource-store.ts:20–22,55–59`); одной транзакции pointer/Revision недостаточно, чтобы доказать неизменность bytes и отсутствие cleanup в другом store. Нужны проверяемые roots/coordination или соответствующий recoverable cross-store protocol согласно AD-4, включая конфликт repair/cleanup и failure с неопределённым исходом.
- На uppercase или ином target, который прежний browser exporter не может точно восстановить, ownership proof не отменяет FR-44. Требуется отдельное доказательство применимой backup readiness; до совместимого решения нельзя объявлять transition и rollout для затронутой сессии безопасными, автоматически менять keys, объявлять corruption или очищать history. Любая новая semantic publication также сохраняет проверку browser default policy.
- Нижняя граница доказательств: реальная IDB и resource stores, успешные lowercase undo/redo, отрицательные проверки exact identity и отсутствующего ресурса, rename metadata, concurrent старый staging/cleanup, expiring lease/takeover, ABA, отмена/crash/unknown outcome и сохранность других Projects/roots. Тесты не должны подменять отдельную проверку взаимодействия со старым build или единственную доступную пользователю копию.

## Метод и границы

Проверка выполнена чтением документов и статическим изучением кода; тесты в рамках этого review не запускались. Source reconciliation о Project name и неопределённом commit выполнена в обновлённом архитектурном тексте до финального вердикта. Остальные пункты — обязательства будущей реализации и evidence, а не утверждение об их выполнении.
