# Независимый adversarial review границы browser IDs

Проверены AD-30, раздел «Граница UUID, старого cleanup и возможного allocator» в `telegram-portable-v1-disposition-2026-11-04.md`, SPEC `project-and-backup-contract.md` §1.4 и текущие browser generator, Project validator, store и recovery. Канонические файлы не изменялись. Это review условий и кодовых путей; изложенные межконтекстные последовательности не выдаются за воспроизведённые инциденты.

Вывод: **документ правильно разделяет условный вероятностный риск, узкий atomic no-overwrite и непройденное требование SPEC к ранее выбранному cleanup. Неявного risk waiver не найдено.** Namespace/sentinel/counter остаются исследовательским кандидатом, а не доказанным способом допуска; обновлённая disposition уже называет условные `k_i`, отдельные Revision/lease риски и неразличимость корректного старого marker после rollback без внешней опоры. Registered ingress остаётся закрытым до applicable proof или явно оформленного и согласованного решения владельцев; отдельные Web export и Telegram не объявляются этим автоматически заблокированными.

- **Вероятность относится только к фиксированной модели выдачи.** Оценка `k/2^122` и union bound `n·k/2^122` корректны для заданного множества не более `k` различных UUIDv4 и независимых равномерных 122-bit выдач; это не оценка всех конфликтов ID, ресурса, lease или старого cleanup. Обновлённый текст уже требует при меняющемся множестве условную оценку `Σ k_i/2^122`; ей ещё нужны доказанные значения и границы, а зависимость, неравномерность, сбой генератора и отсутствие пределов выводят случай за доказанные предположения. Исходный текст правильно не заявляет нулевую вероятность; acceptance не должна превращать эту модель в доказательство универсального отсутствия гонок.
- **Два ID и другие идентификаторы требуют отдельного risk budget.** Новый Project ID, Revision ID и journal/lease/attempt ID участвуют в разных collision сценариях, причём только Project ID адресует рассматриваемый `discardStaging(Q)`. Одной оценки для ранее запомненного Q недостаточно для общего no-overwrite/roots claim. Обновлённая disposition уже выделяет Revision/lease и другие races; их модель генерации и отдельные ограничения ещё требуется доказать для каждого применимого множества; совпадение с текущим persisted row при этом по-прежнему должно давать детерминированный отказ атомарной transaction.
- **Исторические состояния и активные producers нельзя вывести из одной frozen сборки.** Текущий `browserRandomUuid` и проверенный build не характеризуют все старые версии, повреждённые/восстановленные stores или ещё выполняющиеся операции. Текущий structural Project validator принимает любую непустую строку до 256 UTF-16 units, а IDB lease APIs адресуются строкой непосредственно. До утверждения virgin namespace необходимо доказательство для всех поддерживаемых источников и состояний, в том числе удалённого staging, уже считанного в память recovery; простая проверка существующих строк БД недостаточна.
- **Исторический ущерб требуется описывать точно.** Если отложенный cleanup удаляет staging новой обычной команды и её ещё не опубликованную Revision, это не само по себе удаление Durable Project: запись должна отказать или остаться не подтверждённой. Если staging содержит уже существующую target Revision undo/redo, `discardStaging` способен удалить её row при другом current pointer и нарушить session history roots. Disposition правильно проводит различие; regression должен проверять обе ветки, фактические pointers и row, а не заявлять без дополнительного сценария, что уничтожен сам Project.
- **Резервный prefix не ограничивает будущие действия старого editor.** Даже если все старые allocator-generated IDs вне нового пространства, старый PWA может открыть созданный новый Q и позже использовать этот exact Q в своей обычной staging; старый recovery может увидеть и staging команды нового editor. Disposition прямо оставляет этот независимый history/fence risk открытым. Чтобы заявлять безусловную будущую защиту, потребовался бы отдельный совместимый протокол/ограничение writers; для более узкого ingress claim достаточно доказать только точно обозначенную границу и не переносить её на все последующие команды.
- **Sentinel длиной более 256 units пока не доказан недостижимым для старого store API.** Лимит 256 применён в текущем `isNonEmptyString` доменной проверки, но `writer-leases` принимает ключ `projectId` непосредственно, а acquire/takeover/delete выполняют по нему `get/put/delete`. Нужно проверить не только нормальный Project UI, но и все reachable old recovery/directory/direct paths, структуру старых stored rows и конфликт из повреждённого или несовместимого storage. Указание в disposition, что marker лишь кандидат, корректно; по одному валидатору выбирать ключ или писать его нельзя.
- **Валидный marker после rollback не распознаётся одной локальной проверкой.** Обновлённая disposition уже явно фиксирует, что восстановленная старая копия IDB может содержать синтаксически верный marker с меньшим counter. Она локально неотличима от настоящего предыдущего состояния, пока другая вкладка помнит уже выданный Q; после новой выдачи произойдёт повтор. Требование «rollback → fail closed» выполнимо только с доказанным внешним monotonic witness/lifecycle authority или barrier, исключающим старые действия, включая valid-present rollback, а не только отсутствие или повреждение marker. Случайная новая epoch заменяет гарантию вероятностной и не доказывает non-reuse.
- **First bootstrap должен быть авторизован и атомарно координирован.** Одно отсутствие metadata key не устанавливает virgin namespace после eviction, удаления записи или восстановления старой копии. Два независимых новых allocator могут также одновременно пройти предварительный bootstrap proof: победитель `add` создаёт marker, проигравший обязан заново прочитать и проверить актуальную запись, а не reset-ить её или выдавать ID из старого состояния. Необходимо доказать неизменность внешних bootstrap предположений на границе transaction и межконтекстное выделение отдельно для Project/Revision counters.
- **Commit counter должен предшествовать раскрытию ID и переживать все исходы.** Если allocator возвращает Q до подтверждения durable increment, crash/abort может повторить Q; при uncertain commit нельзя угадывать, был ли Q уже раскрыт. Нужно тестировать crash до/после counter transaction, quota, повторную попытку, конкурентные allocators, числовой overflow и явное Project deletion. Невозможность доказать результат означает отказ/ожидание без counter reset и без публикации candidate; session-only память не является durable anti-reuse witness.
- **Существующая admission привязана к UUIDv4 и 36 ASCII bytes.** `browser-backup-representability.ts` проверяет Project/Revision UUIDv4 и использует 36-byte оценку. Prefix или 36-character non-v4 пространство меняет не только генератор: нужны согласование SPEC/source, новые bounded pre-ID/post-ID representability и container calculations, проверка old reader/consumer и regression обычного Web/PWA. Disposition верно запрещает незаметную подмену этих условий; вариант не готов к включению без owner decision и applicable readiness.
- **Разные browser/Home Screen contexts требуют отдельного anti-rollback proof.** Контексты могут иметь отдельные IDB и старые независимые вкладки; marker в одной базе не подтверждает lifetime или отсутствующие in-flight операции в другой. Перенос/restore/eviction и старый build в каждом поддерживаемом контексте нужно рассматривать по фактическим storage boundaries; нельзя предполагать общий counter либо считать очистку одного context закрытием всех старых действий.
- **Граница owner decision должна оставаться явной.** Сужение утверждения до «наша transaction не перезаписала присутствующие rows» само по себе не отменяет SPEC §1.4, CAP-10, FR-45, FR-57 и AD-4. Если предлагается вероятностно принять риск ранее выбранного Q, требуется отдельное письменное source-owned решение с измеримыми assumptions, остаточным риском и согласованием SPEC/PRD/Architecture/readiness; текущий текст такого согласия не выдаёт. Пользовательское разрешение на отдельный export нельзя трактовать как waiver для ingress.
- **Доказательства должны включать reset и старый editor, а не только forced UUID collision.** Кроме принудительного Q collision и delayed cleanup, нужны restore валидной старой версии marker, отсутствующий/повреждённый marker, конкурентный bootstrap, old PWA, уже открывший новый prefixed Q, обычная команда и последующий stale recovery, writer lease marker conflict, quota/crash до/после counter commit и независимые storage contexts. Проверять pending, history Revision rows, чужие leases, protected resource roots и отсутствие ложного `durable`. Предложенный corpus пока не является выполненным evidence.

Опорные места: `apps/web/src/app/browser-ports.ts`, `apps/web/src/domain/project-json-transfer.ts`, `apps/web/src/application/browser-backup-representability.ts`, `apps/web/src/adapters/persistence/indexeddb-versioned-project-store.ts`, `durable-project-repository.ts`, `fenced-project-repository.ts`, `indexeddb-pin-staging-lease-journal.ts`, SPEC §1.4 и AD-4/AD-30. Доказательства владельческого waiver, production collision или физической совместимости в этом review не заявляются.
