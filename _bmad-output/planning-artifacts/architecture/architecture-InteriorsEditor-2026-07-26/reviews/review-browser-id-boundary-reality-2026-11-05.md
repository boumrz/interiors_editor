# Independent reality review — browser ID and allocator boundary

Date: 2026-11-05. Scope: AD-30, “Граница UUID, старого cleanup и возможного allocator” in the S3 disposition, and Project/Backup SPEC §1.4. Checked against the current browser generator, admission, DBv3 store and one retained frozen browser build. No application or canonical file was changed; no allocator, collision race, old-client regression or storage-reset test was executed.

**Verdict: PASS WITH IMPLEMENTATION AND EVIDENCE PENDING; affected ingress remains NOT READY.** The new text correctly separates a narrow atomic-add result, conditional UUID probabilities and the stronger required proof that old recovery did not already select Q. A reserved metadata key and durable allocator are explicitly hypotheses, not an implemented safe protocol. Bootstrap, historical namespace exclusion, storage rollback/reset and supported old-client coordination remain independent obligations.

- Current `browserRandomUuid` uses native `crypto.randomUUID` when available and otherwise `getRandomValues` with version-4 and variant bits (`apps/web/src/app/browser-ports.ts:16–44`). The retained `apps/web/dist/release-manifest.json` identifies `ccdd13662cdca379`; its precached `editor-app-1.741375125e2616d2.js`, named by `sw.js`, contains the same native/fallback scheme. This is evidence for that build, not every installed build, injected test port, broken RNG or pre-existing record.

- The stated 122-bit UUIDv4 collision estimate is conditional on independent, uniformly random CSPRNG output and a fixed set of distinct prior v4 IDs. It is a probability bound, not proof of zero collision, and provides no guarantee for forced IDs, unknown historical shapes or previously selected cleanup. An IDB snapshot cannot observe Project IDs retained in another context's local memory after a staging row disappears.

- Existing Project validation accepts any non-empty `projectId` of up to 256 UTF-16 code units (`apps/web/src/domain/project-json-transfer.ts:149–155,563–564`), while the observed creation and import use generated IDs. A syntactically non-v4 namespace is disjoint from the confirmed generator, but not automatically from all historical readable Project records, recovery/direct storage paths or other builds. The text correctly treats “virgin namespace” as a proof obligation and preserves unusual existing data rather than calling it corrupt.

- The current new-ingress admission requires lower-case UUIDv4 for both generated Project and Revision IDs (`browser-backup-representability.ts:47–48,166–180`), and its pre-ID budget assumes 36 ASCII ID characters (`:438–452`). A prefixed counter or alternate version nibble cannot simply be substituted: change the source-owned admission contract, exact size/AST/envelope bounds and tests, and verify actual old browser codec and old-PWA behavior. A different 36-character spelling preserves length only, not compatibility or past uniqueness.

- DBv3 `writer-leases` is keyed by `projectId` (`indexeddb-versioned-project-store.ts:100–116`). Current and inspected frozen-old code perform normal lease reads/writes/deletion using an exact Project ID, with no observed full-store enumeration of that store. This supports investigating a reserved record without creating a new object store; it does not establish a namespace reservation or invariant for all old versions or direct store consumers.

- A metadata key longer than 256 UTF-16 units cannot be a valid current Project ID under the cited Project validator. It can nevertheless be an IDB key, and the direct lease APIs accept string keys without enforcing that validator; acquire/takeover treat an encountered record as a lease and may overwrite it (`indexeddb-versioned-project-store.ts:403–435,459–475`). Existing malformed/foreign rows, unknown old builds and Project metadata pointers must be checked without destructive normalization. A typed marker, explicit non-project key proof and old-build regression are necessary, not already implemented facts.

- Current Project deletion removes `writer-leases[projectId]` when it has a lease (`indexeddb-versioned-project-store.ts:383–398`). A metadata counter must not be owned by or addressed as a deletable Project, and its two counter namespaces and collision behavior must be specified. One counter update must commit durably before an ID can escape an attempt; abort, crash, concurrent allocators and replay must not cause reuse of any disclosed ID. Resource pin/journal and Project publication still need separate collision-safe proof.

- Absence of a metadata marker cannot by itself distinguish the first allocator-enabled launch from storage eviction, deletion, restore of an older DB snapshot, rollback or prior counter damage. The disposition correctly blocks automatic initialization/reset in that ambiguity and requires independent lifetime/authority proof or a compatible barrier. A random fresh epoch lowers a collision probability but is not a deterministic no-reuse proof; test lost marker, rollback, stale open clients and distinct browser versus Home Screen storage contexts.

- A verified disjoint namespace can address only the proved set of past producers and states. Once an old installed client can open a newly created Q, it can perform ordinary work using Q and later recovery may select its staging; subsequent stale cleanup can affect that same Q without any fresh random collision. The disposition correctly separates that pre-existing broader legacy writer problem from the one-time new-ingress transaction. An allocator by itself does not fence old clients after publication.

- The SPEC owner now explicitly permits bounded in-memory validation plus recoverable pin staging for this one ingress when all AD-4 roots, fence and crash guarantees hold, while still requiring proof that old cleanup did not previously select Q (`project-and-backup-contract.md` §1.4). AD-30 preserves this gate and does not declare the current route safe. A proposed reduction to probabilistic risk requires a separate applicable written owner decision and readiness review; it must not be inferred from this architecture note.

- The practical proof matrix must include actual frozen-old DBv3 read/lease/delete with the proposed metadata key, direct and unexpected-key records, generated v4 and alternate-format IDs, Project and Revision collisions, concurrent counter transactions, prior deleted/recovered Q, old recovery selected before row removal, old client opening new Q, crash after allocation, marker missing/corrupt/rolled back, full storage replacement and no silent database deletion. Verify exact Project, Revision, pin and history preservation; no such test is claimed here.
