# Независимая rubric/source-проверка границы browser ID

Дата: 2026-11-05. Проверены AD-30 и раздел «Граница UUID, старого cleanup и возможного allocator» в `telegram-portable-v1-disposition-2026-11-04.md` против CAP-8/10, FR-45/57, AD-4 и актуального `project-and-backup-contract.md` §1.4. Статически сверены browser ID generation, representability admission и старые IDB recovery/staging методы. Канонические источники этим review не изменялись.

## Вердикт: PASS ДЛЯ ГРАНИЦЫ И ФОРМУЛИРОВКИ РИСКА; МЕХАНИЗМ И EVIDENCE PENDING

Новый раздел корректно отличает доказательство no-overwrite одной транзакции от доказательства отсутствия ранее выбранного старым recovery ID. Вероятностная оценка UUID обозначена как условная, не как выполнение SPEC или принятое владельцем исключение. Вопрос владельца не трактуется как product waiver. Затронутый ingress остаётся закрытым до доказанного механизма либо отдельного явно оформленного применимого решения; независимые Web export и Telegram работа не объявляются автоматически заблокированными.

SPEC owner уже условно разрешил protected in-memory validation и отдельный recoverable resource pin/journal без видимой старому recovery Project staging row (§1.4): при сохранении всех checks, roots, fence и crash/recovery AD-4. Это source applicability, а не свидетельство готовой или доказанной реализации. Review не является readiness verdict, исключением из продуктовой гарантии или разрешением release.

## Сверка требований и текущего состояния

- CAP-10 требует новый Project ID, protected staged validation и отсутствие перезаписи существующего Project; CAP-8 сохраняет active undo/redo roots. FR-45 требует атомарный commit, FR-57 — сохранение existing Projects и отсутствие опасных staging roots, AD-4 — fenced logical publication и recoverable cross-store journal. В этих требованиях не определён допустимый вероятностный порог потери данных.
- SPEC §1.4 требует доказать отсутствие ранее выбранного старым cleanup для нового Q; пустой `staging[Q]` и случайный ID сами этого не доказывают. Исключение произвольного будущего old-ID reuse из узкого transaction claim не является отменой этого требования или proof безопасности остальных old-client путей.
- Текущий `browserRandomUuid` использует UUIDv4 из `crypto.randomUUID` либо `getRandomValues` с установленными version/variant bits (`browser-ports.ts:21–44`). При корректном независимом равномерном CSPRNG это 122 случайных бита. Для заданных `k` различных запомненных v4 IDs и `n` независимых выдач оценка `n·k/2^122` — условная верхняя граница, не нулевая гарантия и не доказательство при неизвестных `k/n`, зависимости, принудительном ID, неисправном RNG или неизвестном поведении других версий.
- `DurableProjectRepository.recover()` читает staging records и позднее вызывает `discardStaging(projectId)`; этот метод заново читает staging по Q и может удалить его Revision. Если ранее выбранная запись Q исчезла из IDB, память старого процесса транзакцией нового ingress не наблюдается. Описана возможная гонка на основе кода, а не подтверждённая фактическая потеря Project.
- Пользовательский вопрос о вероятностной границе не является согласием на исключение. Если владелец отдельно выберет ослабление, необходимо конкретное письменное решение о затронутых инвариантах, условиях и остаточном риске, согласование SPEC/PRD/Architecture и применимый readiness; waiver на начало реализации сам по себе не доказывает product safety, FR-57 или physical/release acceptance.

## Незакрытые условия candidate allocator и evidence

- Предложенный allocator/namespace в `writer-leases` — кандидат для исследования. Он не объявлен выбранным protocol, исправлением или разрешённым автоматически изменением browser storage; нужны отдельные owner applicability и доказательства совместимости с сохранением старых clients и legacy History.
- Virgin namespace должен исключать не только **ныне существующие**, но и удалённые или запомненные в памяти идентификаторы всех поддерживаемых старых producers и восстановленных contexts. Browser Project structural validator допускает произвольную непустую строку длиной до 256 UTF-16 units (`project-json-transfer.ts:563–564`); один найденный UUID generator не доказывает полное историческое множество.
- Metadata key длиннее 256 units является гипотезой изоляции от обычного validator, не доказанной защитой от direct/recovery APIs или всех старых builds. `writer-leases` адресуется по `projectId`, а старые операции могут обращаться к тому же ключу. Требуются фактическая проверка всех доступных путей, конфликтных записей, Project deletion и независимый корпус совместимых builds.
- Атомарное `add` marker и durable monotonic counter должны предотвращать повтор уже раскрытого Project и Revision ID после abort, crash, конкурентных allocator calls и retry. Недействительный marker, overflow, rollback, потеря или неоднозначный исход требуют fail closed; случайная epoch не является deterministic доказательством non-reuse.
- Отсутствующий marker не различает честный первый bootstrap и утрату/откат данных после предыдущего использования, пока другой context может удерживать старые значения в памяти. Без доказанной внешней lifecycle authority либо совместимого barrier автоматический reset запрещён; восстановление старой DB, eviction и отдельные browser/Home Screen contexts требуют отдельных проверок.
- Текущая browser representability admission явно принимает только UUIDv4 для Project/Revision ID и резервирует 36 ASCII bytes (`browser-backup-representability.ts:47–48,175–180,441–452`). Новый prefix или иное 36-character подмножество требуют owner-controlled изменения admission, доказанных bounds, обратной совместимости codecs и тестов; нельзя предположить, что новый allocator совместим с имеющимся proof.
- Даже доказанная уникальность относительно прошлых IDs не останавливает нормальную будущую работу старой PWA с уже созданным новым Q. Отложенный cleanup после старой команды, takeover или последующей команды Q остаётся отдельным history/fence risk без новой UUID collision. Условный allocator не доказывает AD-4 для произвольной будущей old-client работы.
- У самого нового ingress остаются необходимыми collision-safe atomic Project/Revision publication, точная привязка capability к попытке, защищённые pin/journal roots, безопасная проверка writer lease и reconciliation unknown outcome. Project metadata и resource bytes находятся в разных IDB; один `add` или counter не доказывает cross-store integrity и не разрешает чужой cleanup.
- Независимые evidence должны включать forced ID/lease reuse, старый `recover()` с уже исчезнувшей строкой Q, delayed cleanup после новой команды, old-PWA доступ к новому Q, concurrent allocators, crash до/после раскрытия ID, потерю/rollback marker, restore, unsupported/corrupt metadata, pin/shared-resource races и неизменность других Projects/History. Ни одна из этих проверок не считается выполненной этим review.
- Если предложенный namespace и lifecycle proof невозможно обосновать для поддерживаемых старых клиентов, P1 нельзя закрыть одной статистикой или утверждением о новом префиксе. Соответствующий ingress остаётся закрытым до доказанного совместимого механизма или отдельного явно принятого и согласованного owner решения; на независимый Web export или Telegram scope blocker не распространяется автоматически.

## Метод и ограничения

Проведены чтение актуальных источников и статическая сверка кода; тесты, applications и fault injection в рамках review не запускались. Оценка UUID приведена только при указанных предположениях и не является принятой product policy или результатом измерения.
