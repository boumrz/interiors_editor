# Независимый adversarial review: browser registered ingress-only

Проверены AD-4, AD-30, `telegram-portable-v1-disposition-2026-11-04.md`, SPEC `project-and-backup-contract.md` §§1.3–1.4 и затронутые текущие Web application/composition/store paths. Это review контрактов и кода, а не свидетельство внедрения guard, физической совместимости или воспроизведения каждого сценария. Канонические файлы не изменялись.

Вердикт: **ingress-only является условно допустимым направлением для additive coexistence, но не готовым admission или доказательством FR-44/FR-57**. Условия для нового маршрута сформулированы существенно сильнее: полная representability, ранний отказ, сохранение old-PWA и scoped retry; обновлённая disposition отдельно закрывает rollout до доказательства no-overwrite при коллизии IDs. Остаются рассогласование SPEC, незакрытые гарантии уникальности/атомарности и обязательное доказательство отсутствия расширения прочих browser paths. Если они не выполнены, зарегистрированный Web ingress должен оставаться закрытым; текущий пробный код уже подключает его к browser composition и сам по себе этих условий не выполняет.

- **SPEC содержит устаревшее утверждение о решении AD-30.** §1.4 говорит, что текущий AD-30 ещё предписывает отменённые global guard/history transition и его согласование открыто, однако актуальные AD-4 и AD-30 уже описывают ingress-only и не выбирают новый browser history protocol. Это вводит исполнителя и readiness в заблуждение; владелец SPEC должен сверить и точечно обновить статус, не трактуя архитектурное решение как уже проверенную реализацию.
- **SPEC прямо не закрепляет все значимые условия архитектурного маршрута.** В §1.4 сказаны ранний preflight и действующие финальные проверки, но не зафиксированы явно повторная проверка фактического post-ID candidate до staging, exclusive ownership source/resources, привязка retry к прошедшему проверку snapshot и проверка неизменности прежних shared SHA paths. Disposition эти обязательства содержит; нужно подтвердить источником SPEC, что downstream не вправе выполнить лишь более слабое прочтение §1.4, и включить их в acceptance/evidence.
- **Общий побитовый SHA helper создаёт отдельную поверхность обхода.** Текущее `assessBackupFeasibility` принимает `sameSha256ResourceHashBits`, а `CreateCustomGlbFloorItemUseCase` и `RegisterCustomGlbLibraryAssetUseCase` сравнивают digest побитово и сохраняют исходное написание. При доступном uppercase asset, который попадает в browser Project, ingress gate не вызывается, а старый exporter требует точный lowercase key. Старый reality review описывает literal browser comparison; восстановить точный pre-S3 build и проверить все browser call sites, не только FPC. Это пока потенциальный кодовый путь, не доказанное поведение пользовательской сборки.
- **Local Project JSON может обойти предположение о resource-free маршруте.** `decodeLocalProjectJson` проверяет структурный Project через `isStructurallyValidProjectV1`, допускающий definitions и uppercase hash; `ImportLocalProjectJsonUseCase` публикует candidate через общий repository. Если точный uppercase resource key уже существует в этом store, текущий побитовый FPC потенциально допускает новый неэкспортируемый Project без registered ingress. Нужен исполняемый probe с реальным GLB и сравнением с прежней версией; отсутствие такого ключа в обычном UI не доказывает невозможность в данных существующих пользователей.
- **Hydration и library могут перенести pre-existing uppercase key в новую команду.** `AppShell` регистрирует hydrated Project assets в Custom library, а placement передаёт исходный `resourceHash`; validation definition допускает 64 hex в любом регистре. При успешной hydration и новом общем SHA behavior это потенциальный UI-маршрут мимо ingress gate. Проверить old/new default hydration, library registration и новую placement как единую цепочку; сохранить прежние browser outcomes, а не глобально запрещать или переписывать существующую запись.
- **Retry не должен превращать предварительное доказательство в незаверенную ссылку.** `ImportPortableBackupUseCase` возвращает pending candidate через status при `persist-failed`; `ProjectController.retry()` может вызвать `repository.publish(pending, ...)` непосредственно. Disposition требует exact binding или закрытия retry, но необходима проверяемая реализация без file/user flag и без одного checksum: trusted route identity, неизменяемые owned candidate/resources, сохранение origin при retry, повторные pin/fence checks и fault/cancel tests. Отдельно проверить попытку изменения `-0`, own-undefined, revision или resource bytes между preflight и retry.
- **No-overwrite при коллизии IDs остаётся отдельным gate, а не решённой гарантией.** Обновлённая disposition прямо требует доказать защиту от коллизий с учётом старых клиентов и закрывает rollout при отсутствии доказательства. Генерация browser UUID и допустимая длина важны для preflight, но не доказывают, что новый Project/Revision ID свободен при commit. Существующий `IndexedDbVersionedProjectStore.writeStaging` делает безусловные `revisions.put`/`staging.put` до проверки pointer/fence, а initial `publish` может не иметь expected base. Коллизия, созданная в тесте или другой вкладкой, способна затронуть чужую Revision/staging до отказа; вероятность случайной коллизии не является атомарной гарантией. Нужен проверенный no-overwrite protocol, совместимый с участниками, либо закрытие нового маршрута при невозможности обеспечить его; существование этого риска в старом Web не разрешает новому ingress повреждать другие Projects.
- **Early bounds должны учитывать фактические generated values и весь legacy container.** До вызова ID/clock preflight требует консервативной оценки для всех допустимых UUID и JS ISO дат, включая extended years и escaped Project strings, manifest, checksums, ZIP headers и точные размеры ресурсов. После назначения ID и времени необходимо повторить проверку именно фактического candidate до staging. Проверить верхнюю границу и на единицу больше, отсутствие/ошибку генератора и clocks; не заменять legacy STORE encoder расчётом другого V1 writer. Если допустимый диапазон генератора не ограничен доверенной composition, ранний proof не установлен.
- **Сравнение должно учитывать две разные операции import, не стирая остальные различия.** Новый Project ID и `updatedAt` намеренно создаются importer; будущий reimport backup создаст их повторно. Oracle обязан сравнивать на явно определённой границе с только разрешёнными заменами, сохраняя `createdAt`, все остальные поля, own-presence, `Object.is(-0)`, массивы, exact UTF-16, host addresses и bytes. Сравнение JSON, checksum либо только геометрии может пропустить потерю; не утверждать воспроизведение exact свойства, если actual legacy serializer/consumer его не сохраняет.
- **Доказательство формата должно использовать настоящего получателя прежнего экспорта.** `ExportPortableBackupUseCase` способен вернуть `ready`, не прогнав свой результат через старый bounded ZIP decoder и `decodeCanonicalProject`/PPJ AST. Lone surrogate и иные валидные V1 values могут оказаться непригодными у consumer. Preflight должен использовать реальные serializer, encoder, decoder, parser и сравнение либо доказанно эквивалентный bounded oracle, не мнимый новый V1 reader. Учитывать memory/cancel budgets: невозможность безопасно проверить — закрытый route, не успех.
- **Истечение pin/изменение bytes после preflight требует защиты до commit.** Предстейджинговая проверка incoming resource bytes не удостоверяет, что commit ссылается на те же bytes под теми же raw keys в нужном store. Нужны ownership snapshot до async, сверка существующих bytes и length без overwrite, защищённый pin и fenced publication/cleanup, а также повторная проверка на retry. При unknown outcome сохранять свои и чужие roots до достоверной reconciliation; не объявлять source corrupt из-за отсутствия proof.
- **Однократный приём representable candidate не доказывает closure будущих команд.** После registered import обычный новый или старый браузерный клиент может применить команды из общего core; V1 поддерживает различия, которые старый backup не хранит. Условия disposition правильно требуют эту проверку, но без корпуса переходов исходное FR-44 не установлено. Проверить допустимое подмножество под всеми изменёнными S3 producers, default commands и старым клиентом, включая resource registration, duplicates/recovery и history. Любой новый путь, не сохраняющий representability, остаётся закрытым или получает отдельно согласованную scoped проверку.
- **Old-PWA coexistence нельзя свести к отсутствию DB upgrade.** Новая запись может быть физически доступна старому открытому build в том же storage context; нужно проверить его чтение, редактирование, backup, конфликтные записи и исход после перезагрузки для реально допустимого подмножества. Отдельные browser и iOS Home Screen contexts могут иметь разное storage и проверяются по факту. Отсутствие barrier с незаблокированным старым writer и старый `writeStaging` остаются открытым source risk AD-4; новый ingress не должен объявлять их исправленными.
- **Политика отказа должна различать несовместимость и невозможность проверки.** `PROJECT_BACKUP_ENVELOPE_EXCEEDED` уже обозначает и другие feasibility failures; одна только строка reason не определяет, что UI должен объяснить конкретно. Disposition допускает fail closed при недоступности проверки и запрещает обвинять источник в порче. Требуются типизированные machine-readable варианты или доверенный scoped контекст, отдельные тесты исходов parser/smoke/policy/unavailable/cancel и неизменный precedence прежнего маршрута.

Опорные места текущей реализации: `apps/web/src/app/production-app.ts`, `browser-editor-app.tsx`, `shared-project-controller.ts`, `project-controller.ts`, `apps/web/src/ui/AppShell.tsx`, `apps/web/src/application/import-portable-backup.ts`, `import-local-project-json.ts`, `backup-feasibility-policy.ts`, `create-custom-glb-floor-item.ts`, `register-custom-glb-library-asset.ts`, `export-portable-backup.ts`, `apps/web/src/domain/project-json-transfer.ts`, `custom-glb-asset.ts`, и `apps/web/src/adapters/persistence/indexeddb-versioned-project-store.ts`. Pre-S3 behavior, production-user reachability, новый preflight corpus и physical iOS/Android acceptance в этой проверке не установлены.
