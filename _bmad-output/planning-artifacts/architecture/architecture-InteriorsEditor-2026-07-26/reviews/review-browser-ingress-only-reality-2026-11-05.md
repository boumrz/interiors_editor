# Independent reality review — browser registered ingress only

Date: 2026-11-05. Scope: ingress-only admission in the architecture disposition and AD-4/AD-30, checked against the refreshed SPEC companions and present browser composition, import, retry, export and storage code. This is read-only source inspection; no implementation, regression suite or physical handoff was run.

**Verdict: NEEDS WORK for source consistency; implementation and evidence remain pending.** The route-local boundary matches the current separation of importer instances and avoids imposing a new global policy on ordinary commands and history. The updated SPEC §1.4 still incorrectly says AD-30 requires the abandoned global guard and history transition, although inspected AD-30 has already been changed. The pre-ID bound, post-ID binding, retry proof and old browser SHA behavior are requirements to establish, not properties of the current code.

- `createSharedProjectController` constructs separate registered and ordinary `ImportPortableBackupUseCase` instances using different decoder/smoke ports but the same publication repository, resource store and serializer (`apps/web/src/app/shared-project-controller.ts:122–175,265–268`). This makes an explicitly injected browser-only preflight feasible; inserting it into the shared default feasibility helper or selecting it from file content would also affect ordinary browser or Telegram behavior.

- SPEC `project-and-backup-contract.md` §1.4 says the “current AD-30” still requires the abandoned global guard/history transition. The inspected AD-30 instead explicitly limits the check to registered Web ingress, leaves browser default and history unchanged, and keeps retry bound to that route (`ARCHITECTURE-SPINE.md`, AD-30). Remove or update this stale status through the SPEC owner; until reconciled the sources give contradictory instructions.

- The current registered importer has no legacy representability preflight: after decode and source/resource shape checks it stages resources, or in the `requiresPublicationContext` branch allocates a candidate first (`apps/web/src/application/import-portable-backup.ts:95–131,158–172`). The proposed ordering—registered validation, actual smoke and cancellation, read-only preflight, then IDs and staging—is future work. Preserve earlier archive, schema, domain, resource and security outcomes and explicitly test mixed-error/cancel precedence without changing the ordinary importer.

- The early result `PROJECT_BACKUP_ENVELOPE_EXCEEDED` is not currently accepted by `ImportPortableBackupResult.kind="rejected"` (`import-portable-backup.ts:44–64`), and the existing UI otherwise falls back to generic invalid-file text (`apps/web/src/ui/AppShell.tsx:877`). The requested typed route-specific outcome and explanatory feedback must be wired end to end. Verification unavailable, a proved valid but unrepresentable candidate, malformed input, cancellation and persistence failure must remain distinguishable; none should falsely assert resource corruption.

- The prior exporter requires lowercase unique raw resource hashes and exact byte length and literal SHA string equality (`apps/web/src/application/export-portable-backup.ts:122–168`). The targeted preflight must additionally prove the actual old Project serializer, manifest/ZIP envelope and the old consumer's parser/AST, limits, domain and resource handling. A lowercase regex or SHA success alone is insufficient; no automatic normalization, dropped alias, replaced bytes or source mutation is allowed.

- Exact Project comparison must preserve field values and optional own-property presence, `-0`, UTF-16 code units and array structure; JSON string equality cannot prove these. The legacy path's permitted import differences are the new `projectId` and `updatedAt`, while `createdAt`, geometry, hosts, metadata, ordinary absent/present optionals, finite `yawRadians` such as `0.5`, and exact resource bytes must survive. The old `decodeCanonicalProject` also invokes `parsePpjA1JsonBytes` (`import-portable-backup.ts:409–416`), so a JSON-only roundtrip is not sufficient for strings and parser capacity.

- A no-ID refusal requires a justified upper bound for the actual browser ID source, clock, JSON escaping, Project member, manifest and container, including limits at boundary values. Production presently uses UUID generation and `new Date().toISOString()` (`apps/web/src/app/browser-ports.ts:26–45`), while the shared injected `IdPort` does not itself guarantee these bounds. Prove bounds for the trusted browser composition or fail closed before allocation; a placeholder candidate of convenient length cannot establish the contract.

- The architecture additionally requires checking the actual candidate after allocating ID/time and before staging, plus ownership of the decoded source and resource bytes across awaits. The current `prepareImportedCandidate` allocates IDs and serializes the source but does not perform the new proof (`import-portable-backup.ts:214–218`). Tests must force an ID/time or size outside the established bound and mutate/delay snapshots; failure must preserve the original and never stage or publish an unchecked candidate.

- The exact source/candidate proof must remain coupled to the result through the final asynchronous publication boundary, including actual pinned resource bytes. A check against one object or a checksum of JSON that collapses `-0`/own-undefined cannot certify a later mutable candidate. The default wrapper copies the Project only under an injected feasibility policy, not in the default branch (`session-retention-project-repository.ts:85–102`); the proposed route cannot rely on that branch for exclusive ownership.

- On a publication failure the importer intentionally surfaces and retains a pending candidate (`import-portable-backup.ts:184–196`; `project-controller.ts:3690–3727`), and `ProjectController.retry()` invokes the repository directly (`project-controller.ts:3511–3560`). A guard only at import entry is therefore bypassable by retry. Carry trusted attempt/candidate/resource proof to each initial commit and retry, or explicitly close retry for this route while preserving the pending candidate and all other retry behavior. Do not rely on a mutable Project field or a file-selected flag.

- If a failure or cancellation follows staging, cleanup must be conditional on proved attempt ownership and no publication; a lost/ambiguous result cannot be treated as no-publication. The present browser history protocol writes a Revision before the pointer's fence/base check and its `discardStaging` may delete a non-current Revision (`indexeddb-versioned-project-store.ts:146–164,191–239,323–340`). AD-4 and the new disposition accurately identify this as a separate pre-existing risk; ingress-only admission is not a proof of its repair, safe cross-context cleanup or coexistence with old installed PWAs.

- “Preserve browser default” must be defined against the pre-S3 baseline as well as the current working tree. Current default feasibility and controller recovery paths use bitwise SHA comparison (`backup-feasibility-policy.ts:145–160`; `project-controller.ts:1694–1697`), while prior review recorded literal comparison on browser paths. Reproduce actual normal import, library hydration, placement, recovery and commands against the prior browser build and ensure no new uppercase nonexportable Project is admitted; otherwise isolate any V1 alias behavior or block the affected rollout. Source inspection here does not establish an affected user case or unchanged baseline behavior.

- The existing probe documents a synthetic uppercase registered import that became Durable before the old exporter rejected it; it proves neither the new guard nor the prevalence of affected real user Projects. Required evidence includes actual GLB and hashes, lowercase legacy export/reimport, uppercase/mixed aliases, pre/post-ID bounds, optional legacy fields, -0/undefined/Unicode, typed outcomes, early refusal without ID or writes, retry and cancellation races, protected other roots, unchanged default/browser/PWA behavior and unchanged Telegram aliases. FR-44 for all historical data and physical FR-57 roundtrips remain separately open.
