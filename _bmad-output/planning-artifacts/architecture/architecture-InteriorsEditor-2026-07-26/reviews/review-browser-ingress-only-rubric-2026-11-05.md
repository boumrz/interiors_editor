# Независимая rubric/source-проверка browser ingress-only disposition

Дата: 2026-11-05. Проверены AD-4, AD-30 и раздел browser registered-transfer admission в `telegram-portable-v1-disposition-2026-11-04.md` против SPEC `project-and-backup-contract.md` §1.3–1.4, `telegram-platform-and-compatibility-contract.md`, CAP-10 и PRD FR-44/FR-57. Сверены релевантные части текущего importer, default feasibility, legacy exporter и browser persistence. Канонические документы этим review не изменялись.

## Вердикт: SOURCE RECONCILIATION PENDING; IMPLEMENTATION И EVIDENCE PENDING

Обновлённые AD-4/AD-30 и disposition выражают additive ingress-only scope и оставляют действующую browser default policy и history protocol без нового общего guard. Они требуют полного доказательства совместимости с legacy backup и честно отделяют известный history risk от исправления. В актуальном SPEC companion остаётся устаревшее утверждение о содержании AD-30 и двусмысленное описание места дополнительной проверки; эти строки требуют исправления владельцем SPEC. Это не implementation-readiness verdict, свидетельство безопасности baseline или физической приёмки.

## Сверка источников и реализации

- `project-and-backup-contract.md:254–255` утверждает, что актуальный AD-30 всё ещё предписывает отменённые global guard/history transition, хотя `ARCHITECTURE-SPINE.md:858` уже ограничивает проверку явно выбранным registered Web ingress, сохраняет default и history и требует повторной проверки при retry. Устранить устаревшее утверждение после source-owner сверки; не считать ранее записанные исторические review и memlog свежим одобрением нового решения.
- `project-and-backup-contract.md:194–195` говорит, что browser default и composition сохраняются «с дополнительной проверкой представимости», не уточняя в этой фразе её принадлежность только новому ingress. §1.4, platform contract и AD-30 явно исключают global guard. Уточнить здесь ingress-only место проверки, чтобы не направить реализацию в default policy.
- FR-44 требует complete offline backup для non-corrupt Durable Projects текущей policy, а FR-57 — физически проверенный двусторонний перенос; source-preserving отказ неподходящего V1 не является успешным переносом. SPEC и AD-30 правильно не выводят полную совместимость из одного безопасного подмножества и сохраняют gate замены browser exporter для всех non-corrupt Durable Projects, включая состояния вне V1 grammar.
- Текущий `export-portable-backup.ts:122–150,163–170` требует lowercase raw key и literal SHA equality. Изолированный probe в `docs/progress/telegram-extension-2026-11-04/S3/registered-transfer/KNOWN-BROWSER-ROUNDTRIP-BLOCKER.md` подтверждает uppercase registered import как Durable и отказ прежнего exporter. Новый read-only preflight является предписанием, а не подтверждённым исправлением этого probe.
- AD-4:179–182 и disposition:136 правильно фиксируют отдельный pre-existing history/fence risk: текущий browser `writeStaging` выполняет `revisions.put` до base/fence, а `discardStaging` может удалить не-current staged Revision. Исторические existing-row/receipt reviews описывают возможную remediation, не реализованную и не выбранную в этом additive scope. Отказ от protocol upgrade не отменяет требований AD-4 и не доказывает старый baseline безопасным.

## Оставшиеся обязательства и риски допуска

- Новый route должен быть выбран trusted browser composition только после явного выбора пользователя; файл не должен включать policy, изменять route или вызывать permissive fallback. Обычные import/export, default feasibility, PPJ parser, browser DB и существующая History не получают общий guard.
- Поскольку legacy export проверяет не только SHA, корректный preflight должен охватывать actual serializer, exporter **и consumer**, exact bytes/resources, все обязательные limits/envelope, полный structured Project, `-0`, own-undefined, UTF-16 и host bindings. Нижний регистр key необходим, но недостаточен; plain JSON/checksum не доказывает exact identity.
- Ранний source preflight не знает будущего Project ID и `updatedAt`. Disposition:130 требует доказанных границ всех допустимых генерируемых ID/time до раннего допуска, а после генерации — оценки именно конечного immutable candidate до staging. Нужны граничные и зависимые от ID/time примеры; если bound отсутствует или post-ID проверка расходится, route закрыт без публикации.
- В текущем `ImportPortableBackupUseCase` candidate формируется с новым ID и временем (`import-portable-backup.ts:214–218`), а ветки smoke/staging имеют разный порядок (`:113–157`). Нужно проверить выбранный новый порядок source validation → smoke → cancellation → preflight до ID/pin/staging, сохраняя legacy route и source-owned precedence, в том числе valid uppercase вместе с malformed GLB или cancellation.
- Текущий `ImportPortableBackupResult` не содержит `PROJECT_BACKUP_ENVELOPE_EXCEEDED` среди ранних rejected reasons (`import-portable-backup.ts:44–53`). Нужна явная typed ветка и пользовательское объяснение несовместимости без ложного утверждения о повреждении файла; более ранние validation причины не подменяются.
- После `persist-failed` controller может повторить сохранение без повторного выполнения importer (`project-controller.ts:3511–3553`). Надо привязать каждый initial commit и retry к trusted доказательству для точного candidate и pinned bytes либо закрыть retry только этого route; нельзя полагаться на user/file flag, mutable Project field, один checksum или менять retry других команд.
- Проверенный snapshot и resource bytes должны оставаться неизменными до commit; retain/pin/backup feasibility, domain checks, fence и безопасная conditional cleanup действуют дополнительно к preflight. После неоднозначного исхода нельзя автоматически предполагать no-publication или освобождать чужие/current/undo/redo roots.
- Общий текущий `sameSha256ResourceHashBits` используется в browser feasibility, controller и custom registration/placement. Disposition:134 обоснованно требует сравнения с pre-S3 browser build и проверки потенциальных путей uppercase через library/Project: статическая находка сама по себе не доказывает пользовательский exploit, но rollout нельзя считать безопасным без выяснения, не расширили ли shared изменения старую семантику.
- `SessionRetentionPolicy` и защита ранее существующих undo/redo roots не устраняются под видом новой admission. Нужны regression и race tests для существующих browser contexts и old installed PWA; существующий `intent=history` или snapshot roots сам по себе не подтверждает безопасность staging/cleanup. Указанный pre-existing debt требует отдельного owner решения и не должен исчезнуть из readiness assessment.
- В доказательствах нужны actual GLB/SHA uppercase, mixed-case и alias pairs, valid lowercase legacy export/reimport, отрицательные и граничные structured/size cases, сохранение source, error/cancel/cleanup и initial/retry races, старые Web/PWA regressions и независимые Telegram V1 alias checks. Реальные `.interiors` и физические client pairs необходимы отдельно; implementation, safety и FR-57 не следует объявлять по одному файлу или документной проверке.

## Метод и ограничения

Выполнены чтение актуальных источников, статическая сверка кода и просмотр описания уже известного probe. Тесты или приложения в рамках этого review не запускались. Ни новый preflight, ни восстановление baseline history protocol, ни physical roundtrip этим отчётом не объявлены выполненными.
