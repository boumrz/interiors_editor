# Независимый adversarial review scoped browser no-overwrite

Проверены AD-30 и раздел «Scoped no-overwrite для нового browser ingress» в `telegram-portable-v1-disposition-2026-11-04.md`, с сопоставлением browser Project store, recovery, writer lease, pin journal и importer. Канонические документы не изменялись. Ни описанные гонки, ни предложенный протокол не выдаются за выполненное тестирование или подтверждённый пользовательский инцидент.

Вывод: **двухфазное предложение с `WeakSet` и двумя `add` недостаточно. Однотранзакционное направление с закрытым отказом корректно сужает проблему, но не является пока доказанной реализацией; старые отложенные операции, resources/journal и unknown outcome остаются gate для нового ingress.** Документ честно ограничивает утверждение об ответственности будущих old writers и не предписывает глобальный DB upgrade. Последние уточнения о ранее выбранном cleanup, conditional lease acquisition и SPEC-gate CAP-10/FR-45 учтены как существующие требования, требующие evidence.

- **Двухфазная гонка старого recovery описана по существующему коду верно, но остаётся невоспроизведённой.** Старый `recover()` сначала получает список candidate, затем по каждому отдельно вызывает `discardStaging(projectId)`. Если новый staging Q уже виден во время первого шага, после нового commit следующая обычная команда Q может создать staging другой Revision, которую отложенный discard удалит. Проверить последовательность на двух настоящих IDB connections с управляемыми паузами и сверить staging/Revision/стек и pointer; два `add` сами её не устраняют.
- **Одна transaction без нового staging не исключает ранее выбранный cleanup по тому же Project ID.** Старый recovery мог запомнить Q из более ранней staging-записи, которая исчезла до проверки нового commit; `projects.get(Q)` и `staging.get(Q)` тогда пусты, но отложенный `discardStaging(Q)` способен удалить следующую staging нового Project. Обновлённая disposition уже явно описывает этот сценарий и требует доказать отсутствие отложенного cleanup; проверка отсутствующих текущих записей не является таким доказательством. Нужен конкретный proof никогда не использованной для них совместимой области Project IDs, иной узкий механизм либо отказ для случая без доказательства.
- **Исторические references нельзя полностью заключить в текущее состояние записей без предположений.** Проверка всех pointers, revision owners, `staging[P]→R` и journals в одной защищённой области необходима и явно предусмотрена, но старый controller может удерживать pending/history/recovery в памяти после изменения БД. Нельзя объявить ID свободным для всех ранее выбранных old operations на основании одного snapshot IDB. Зафиксировать, какие существующие версии и producers участвуют, и доказать ограничение ID namespace или иное условие; при отсутствии полной информации закрыть только эту попытку, не удаляя данные.
- **Область единой transaction должна включать все записи, на которые опирается её proof.** `projects`, `revisions`, `staging` и `writer-leases` должны участвовать в общей transaction; если вывод об отсутствии чужих pin/journal roots зависит от `pin-staging-leases`, он также должен быть синхронизирован в той же Project DB или заменён доказанной консервативной схемой. Проверки вне transaction не защищены от старой concurrent записи. Bounded scan должен fail closed на непонятных/повреждённых записях и превышении бюджета; `ConstraintError` обязан abort-ить весь commit, а не оставлять Revision без pointer.
- **Writer lease может быть изменён до collision check.** Текущий `FencedProjectRepository.publish` вызывает `leaseFor(Q)` до delegate, а `acquireWriterLease` делает `writer-leases.put` при свободной, истёкшей или собственной lease. Следовательно, последующая атомарная проверка projects/revisions не предотвращает предшествующее изменение чужого lease/takeover state. Обновлённая disposition уже требует conditional acquisition без изменения чужого состояния; необходимо доказать её совместно с conflict decision или эквивалент и проверить expired lease, повторный owner, takeover и конфликт всех остальных записей.
- **Удаление видимого Project staging требует source-owner подтверждения staged validation.** Обновлённая disposition прямо относит замену in-memory validation и отдельным pin staging к SPEC reconciliation CAP-10/FR-45, без изменения требований AD-4. Это обязательный открытый gate: отсутствие Project staging нельзя считать уже соответствующим контракту только потому, что pointer и Revision коммитятся атомарно; нужны утверждённые crash/recovery outcomes и сохранность source.
- **Project и blob databases не образуют одну transaction.** Добавление Revision и pointer не доказывает, что проверенные resources останутся pinned по всем raw keys при commit. Pin journal `create()` использует `put`, а старый `isPublicationPublished` сравнивает только Project/Revision IDs: forced reuse может ложно связать чужой pointer с новой попыткой. Требуются collision-safe lease ownership, проверка exact bytes/length/hash и защитного root, безопасные правила старого reconcile и сохранение journal/bytes при неизвестном результате. Если точная причинная связь с попыткой недоказуема, не выполнять cleanup на основании одной пары IDs.
- **Порядок journal mark и старого reconcile нуждается в конкретном безопасном варианте.** Importer сейчас может вызвать `markForPublication` до Project commit. Старый reconcile, увидев совпадающие IDs чужого pointer, может преждевременно завершить именно этот lease, даже если новый `add` затем откажет. Проверить узкий протокол, который не раскрывает недоказанную publication старому reconcile до определённого commit либо имеет другой непротиворечивый proof; crash между pin, commit, mark и complete должен удерживать bytes. Консервативно сохранённый orphan не следует выдавать за уже удалённую утечку или успешное восстановление.
- **Capability не является данными candidate и не должна пропадать на обёртках.** `WeakSet` фиксирует только JS object identity; глубокие поля и буферы могут измениться, а structured clone/restart создаёт новую identity. Нужна приватная, привязанная к конкретной операции и immutable structured candidate/resource snapshot capability, установленная до первого async действия после создания snapshot, включая FPC и результат legacy-representability. Проверить все wrappers, pending/retry, clone и mutation; потеря capability не должна переводить вызов на старый безусловный publisher. Стандартный JSON checksum не заменяет `-0`/own-undefined/точные raw keys.
- **Отсутствие pointer не доказывает no-publication после потери ответа.** Успешная IDB transaction могла завершиться до потери результата, после чего pointer сменился или Project был явно удалён. Нужна доказуемая attempt identity/receipt либо консервативный outcome `unknown`, сохраняющий ресурсы и чужие roots без повторного publish или destructive cleanup. UI должен давать безопасный исход, не объявляя source повреждённым и не создавая незаметно дубликат по повторно выбранному файлу; обычное восстановление других Projects не должно быть заблокировано.
- **Поздние old writers не покрываются атомарностью новой операции.** Старый клиент способен позже выполнить unconditional `revisions.put`, а первоначальная публикация — `projects.put` после собственного stale/lease сценария; конфликт проверенных сейчас IDs возможен позже. Текст корректно не утверждает глобальную защиту. Для обещания «эта попытка не перезаписала существовавшие записи» нужны принудительные межконтекстные interleavings до/во время commit; для обещания защиты от всех будущих old writes требуются отдельное решение о совместимом барьере/протоколе или ограничении выпуска. Нельзя подменять первое вторым и нельзя требовать blanket barrier, если release заявляет только более узкую проверенную гарантию.
- **Случайный UUID не доказывает совместимую непересекающуюся область IDs.** Возможный узкий способ исключить старые delayed операции — namespace, который действительно не мог появиться у поддерживаемых old producers и их уже существующих roots, причём отдельно для Project и Revision. Это требует аудита всех поддерживаемых версий, импортов, хранимых и активных состояний и проверки старого reader с новыми IDs; допущение по одному текущему генератору недостаточно. При неизвестном происхождении существующих records нужен консервативный отказ либо иной доказанный способ, а не утверждение невозможности коллизии.
- **Не каждая ошибка после pin разрешает удаление ресурсов.** Между записью blobs и metadata commit старый consumer может закрепить или использовать тот же exact key. Даже collision/stale-base/no-publication для новой попытки не доказывает отсутствия других владельцев. Проверить условную очистку только собственных roots в blob DB после доказанного no-commit; при конкурирующем consumer, ошибке или неизвестности хранить bytes. Пользовательский cancel после фактического commit не должен выдаваться за откат.
- **Проверки должны охватывать реальные пути, а не лишь новый store helper.** Помимо forced Project/Revision/lease collisions и чужого dangling `staging[P]→R` проверить orphan revision с Q, dangling pointer на R, старый recovery scan как до нового staging, так и до прямого commit, отложенный discard после следующей команды, старый writer до/после commit, lost fence, mutable/клонированный candidate, полученный retry и все границы crash/unknown. Для каждого сценария сверить фактические Project pointers, rows, staging других попыток, leases, pins и bytes; повторить production composition и отсутствие изменений обычного Web history.

Опорные места: `apps/web/src/adapters/persistence/indexeddb-versioned-project-store.ts` (`writeStaging`, `publishCurrentPointer`, `discardStaging`, `acquireWriterLease`), `durable-project-repository.ts` (`publishCandidate`, `recover`), `fenced-project-repository.ts`, `indexeddb-pin-staging-lease-journal.ts`, `pin-staging-lease-coordinator.ts`, `indexeddb-custom-asset-resource-store.ts`, `apps/web/src/app/production-app.ts` (`isPublicationPublished`), `apps/web/src/application/import-portable-backup.ts` и `apps/web/src/app/project-controller.ts` (`retry`). Предложенные проверки и владельческие решения пока не выполнены.
