# Independent reality review — scoped browser ingress no-overwrite

Date: 2026-11-05. Scope: AD-30 and “Scoped no-overwrite для нового browser ingress” in the S3 disposition, checked against the current browser import, controller, wrappers, IndexedDB and pin journal. This is read-only code inspection; the described race has not been executed by this review, no user incident is asserted, and no canonical or application file was changed.

**Verdict: PASS WITH IMPLEMENTATION AND EVIDENCE PENDING for the scoped direction; NOT READY to enable it.** The old-recovery race follows from the inspected code, and a single Project-database transaction without a visible legacy Project staging row is a technically plausible way to eliminate that specific new-row exposure. It is not yet an implementation or a proof of collision-safe pins, lease acquisition, previously scheduled cleanup, old-client coexistence or crash outcomes. Release remains blocked where those obligations cannot be demonstrated.

- The described race is consistent with current behavior: `DurableProjectRepository.recover()` first materializes the full list of staged candidates and later calls `discardStaging` by Project ID (`durable-project-repository.ts:255–260`); `discardStaging` rereads whichever staging row exists at that later time and may delete its Revision (`indexeddb-versioned-project-store.ts:323–340`). Consequently an old recovery can remember Q, a new import can remove its stage, an ordinary later command can stage Q, and the delayed cleanup can delete the command's row. This requires no forced ID collision, but remains a code-path inference until a deterministic interleaving test reproduces it.

- The current publisher performs `revisions.put` and `staging.put` before it checks fence or base (`indexeddb-versioned-project-store.ts:146–164,191–239`; `durable-project-repository.ts:107–125`). Two individually protected no-overwrite stages would not cancel an already scheduled old `discardStaging(Q)`. The proposed single transaction should avoid making a new Project staging row visible to old recovery, perform prevalidated candidate checks and atomically add the Revision and Project pointer, with all applicable ownership/fence predicates inside the same transaction.

- No visible new staging row only removes the race attributable to that row. A pre-existing staging row for Q may already have been scanned by old recovery and subsequently disappeared before the new transaction, leaving an unobservable delayed cleanup. The revised disposition explicitly calls out that separate case and requires a proved never-before-used namespace or equivalent coordination. Prove that the chosen mechanism applies to all supported old clients and previously selected cleanup, or keep the affected scope closed; a fresh transaction snapshot alone cannot reveal all already queued old work.

- `revisions` uses a global Revision ID, whereas `staging` is keyed by Project ID. An old dangling `staging[P]` referring to the new R can cause `discardStaging(P)` to delete R even if `staging[Q]`, `revisions[R]` and `projects[Q]` were absent at a preliminary read (`indexeddb-versioned-project-store.ts:146–164,323–340`). The direction properly requires transactionally protected inventory of Project pointers, revision ownership/IDs, staging references and applicable roots. Existing code has no demonstrated bounded index for every cross-reference; show the actual inventory, memory/time bounds and fail-closed behavior rather than assuming three keyed gets are enough.

- For genuine no-overwrite, the absence checks and both writes must participate in one authoritative IDB `readwrite` transaction covering all participating Project-database stores and the selected exact candidate. Preserve IDB's transaction-wide abort for `add`/`ConstraintError`; do not cancel the request error or convert it to success, and observe transaction completion before returning Durable. A failed add must not invoke old unowned `discardStaging(projectId)`. Resource hashing and long external awaits belong outside the active transaction, followed by revalidation of all required predicates within it. The revised disposition also correctly requires SPEC-owner confirmation that in-memory validated staging plus recoverable resource staging satisfies CAP-10/FR-45 and AD-4 before eliminating the Project staging record.

- Current `FencedProjectRepository.leaseFor` obtains a lease before publishing, and `acquireWriterLease` can write/renew a lease by candidate Project ID (`fenced-project-repository.ts:267–281`; `indexeddb-versioned-project-store.ts:404–438`). A forced Q collision can therefore affect an existing writer before a later Project-pointer check. The revised disposition explicitly requires acquisition without mutating a foreign lease/takeover state on collision. Prove absent/new Project and lease ownership together within the atomic boundary or an equivalent protocol; a preflight read followed by existing lease acquisition is not an atomic proof.

- `BrowserRegisteredTransferDecoder` owns a private `WeakSet` of sealed, frozen candidates (`browser-registered-transfer-decoder.ts:32–33,95–115`), and `beforePublish` rechecks that object and protected resources. This proves neither IDB publication nor authorization after a copy/restart. `SessionRetentionProjectRepository` presently preserves object reference in its default branch but creates a new candidate when a feasibility adapter is injected (`session-retention-project-repository.ts:85–102`). Define a trusted, non-forgeable attempt capability bound to the exact candidate and resource proof through every wrapper; a missing marker, clone or invalid capability must not fall back to the old `put` publisher.

- `WeakSet` membership is process-local and cannot survive IDB structured clone, page restart or a different controller instance. Crash/retry needs its own authoritative attempt/outcome proof or conservative fail-closed handling; the legacy data row or mutable user/file metadata must not recreate the capability. Existing `persist-failed` pending handling and trusted route-specific retry behavior must be exercised, without changing unrelated browser history or general retry semantics.

- The current controller treats a pending candidate as `publicationInFlight` (`project-controller.ts:594–605`) while its route-specific retry policy blocks retry and the UI offers reselecting the input file (`project-controller.ts:3542–3557`; `AppShell.tsx:1518–1520`). A subsequent import goes through `executePortableBackupImport`, which returns `in-progress` when that pending state remains (`project-controller.ts:1880–1894`). The disposition appropriately requires a safe pending outcome; test and specify an actionable user path which does not silently discard a potentially published candidate or delete roots.

- Project metadata and binary resources are separate IDB databases. The existing pin coordinator stages/journals first, and `IndexedDbPinStagingLeaseJournal.create` uses `put` by lease ID (`indexeddb-pin-staging-lease-journal.ts:41–45`); `production-app.ts:55–60` considers a matching Project/Revision ID published without an attempt receipt or exact candidate proof. Forced lease and Project/Revision collisions can therefore misattribute another attempt. Require collision-safe root ownership and exact committed/no-publication/unknown evidence, or retain journal/bytes conservatively; neither a matching pair of IDs nor a timeout proves this attempt committed or failed.

- Existing `protectExistingResource` removes a previous staging owner's exclusive deletion right, but it is not a general proof of every current/history root or a cross-database atomic publication (`indexeddb-custom-asset-resource-store.ts:111–132`). Demonstrate exact protected bytes, safe ownership under shared hashes, no third-party cleanup, and release only after a proven outcome. One atomic Project transaction alone does not make pin and Project writes atomic across databases.

- The disposition correctly limits its guarantee: a new transaction's `add` protects existing records against that new operation at its linearization point. An old open build can later perform unconditional `put` or delayed cleanup using the same IDs; a WeakSet or lock observed only by new code cannot prohibit that. If the applicable acceptance condition requires protection against such future old-client operations, a separately approved compatibility barrier/protocol or rollout limitation is necessary; do not claim universal fencing from the narrow fix.

- Required evidence includes forced independent Project/Revision/lease collisions, old dangling `P→R` staging, orphan ownership/pointers, old recovery scanned before commit then an ordinary command, old writer before/during/after commit, lost fence/takeover, candidate mutation and marker loss across wrappers, request error/abort, quota/crash/cancel, ambiguous commit and pin-journal collisions. Run these against the actual browser IndexedDB stores and competing contexts, assert byte-for-byte preservation and no false Durable, and retain unchanged Web/PWA/history regression checks. None was run for this review.
