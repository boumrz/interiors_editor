# Независимая rubric/source-проверка browser no-overwrite

Дата: 2026-11-05. Проверены AD-30 и раздел «Scoped no-overwrite для нового browser ingress» в `telegram-portable-v1-disposition-2026-11-04.md` против AD-4, CAP-1/8/10, FR-45/57, `project-and-backup-contract.md` §1.4 и текущих browser persistence/pin adapters. Канонические источники этой проверкой не изменялись.

## Вердикт: SOURCE RECONCILIATION, IMPLEMENTATION И EVIDENCE PENDING

Диспозиция верно отвергает два видимых legacy staging этапа как достаточное решение и формулирует одну атомарную no-overwrite публикацию как **направление для проверки**, а не доказанную реализацию. Она отделяет безопасность этой операции от будущих действий старого PWA и сохраняет действующий browser History protocol. После первоначальной сверки AD-30 уточнён и disposition явно требует source-owner подтверждение: SPEC owner должен отдельно подтвердить применимость staged validation и recoverable pin/journal к публикации без видимого legacy Project staging. FR-45, CAP-10 и AD-4 нельзя считать ослабленными. Доказательства полного протокола и readiness отсутствуют.

## Сверка sources и кода

- FR-45 и CAP-10 требуют полный validation в staging, атомарный новый Project ID и отсутствие перезаписи существующего Project. `project-and-backup-contract.md` §1.4 пока фиксирует P1 no-overwrite как открытый proof. Нужно получить SPEC-owner disposition для различия между staging validation и конкретной записью в legacy IDB `staging`: защищённый validation snapshot и recoverable resource pin/journal не должны подменяться утверждением, что без Project staging все условия уже выполнены.
- AD-4:188–215 требует fenced logical publication и recoverable cross-store reconciliation, с защитой Project, Revision, History и pinned roots. Один metadata commit при независимой blob DB не является атомарным pin, точным ресурсом или proof о корректном cleanup. Узкий scope не отменяет нормативную гарантию и не исправляет legacy history.
- Текущий `IndexedDbVersionedProjectStore.writeStaging` записывает `revisions.put` и `staging.put` до pointer/base/fence; `discardStaging` удаляет staging по Project ID и может удалить не-current Revision. `DurableProjectRepository.recover()` предварительно собирает staging list и позднее очищает записи по Project ID. Описанный staged-scan → publish → новая команда → поздний cleanup возможен по управлению этих методов и требует исполняемого race evidence; это не установленный пользовательский инцидент.
- AD-30 после исправления говорит о существующей repository/composition boundary и проверенном для данного route publication path, не требуя вызова legacy `writeStaging`. Диспозиция прямо оставляет подтверждение эквивалентности staged validation за SPEC owner; это подтверждение ещё не получено и не заменяется архитектурным уточнением.

## Условия и незакрытые проверки

- Одна readwrite IDB transaction должна проверять фактическую защищаемую область и применять `revisions.add`/`projects.add` как один commit. Нельзя suppress `ConstraintError` или запускать безусловный legacy cleanup чужого Project после отказа; IDB abort и неуспех всех записей требуется проверить.
- Отсутствия `projects[Q]`, `revisions[R]`, `staging[Q]` недостаточно: старый dangling `staging[P]` может ссылаться на глобальный R, а Q — иметь orphan Revision, recovery, lease или другую root без current pointer. Нужен bounded полный inventory применимых IDB records/refs либо доказанный эквивалент; недоступный или неполный inventory даёт отказ без cleanup чужих records.
- Отдельно учитывать уже выбранный старым `recover()` Project ID: отсутствие видимой новой staging-записи убирает описанный путь, в котором новый ingress сам создаёт наблюдаемый старым recovery stage, но не отзывает ранее выбранную старую очистку при reuse ID. Без доказательства её отсутствия или безопасной координации нельзя объявлять fault/ID-reuse защищённым случаем.
- Обычная независимая старая операция по Project P с другими Project/Revision IDs не должна без нужды запрещать import Q. Это отдельная проверка от forced collision/reuse: если старый client позже использует тот же ID или выполняет ранее отложенный cleanup, новая transaction не может запретить его старые `put`/delete. Нельзя объявлять все старые клиенты fenced или считать очень малую вероятность UUID proof.
- Доверенная route capability должна связывать immutable exact candidate, IDs, resource roots и конкретную попытку до async. Один `WeakSet` не переживает copy/restart и не доказывает соответствие содержимого или принадлежности. Потеря capability, injected wrapper clone и retry должны fail closed либо пройти повторную проверку; fallback в обычный `put` запрещён.
- Browser pin journal и resource blobs находятся в разных IDB. Существующий `IndexedDbPinStagingLeaseJournal.create` делает `put` по lease ID ещё до Project commit; collision может заменить чужой root. Следует доказать collision-safe создание, ownership и сохранение exact pinned bytes до publication или сохранять bytes/journal при недоказанном результате; разрешение lease collision нельзя откладывать до конца Project transaction.
- `isPublicationPublished` в browser composition проверяет Project/Revision IDs; при их forced reuse это не доказывает результат **конкретной** попытки или exact candidate. Перед release нужна доказуемая связь с попыткой и manifest либо консервативное удержание roots. Отсутствие pointer после timeout или cancel не доказывает no-publication, а возможный уже совершённый commit нельзя повторять как новый по одним IDs.
- До генерации/использования нового Project Q нельзя безусловно перезаписать чужой writer lease или делать takeover. Fence, actual Project ownership и соответствующие lifecycle checks должны быть проверены в защищённой границе без нового пути, позволяющего stale writer публиковать или release root.
- Collision, cancel, quota, crash или unknown outcome не дают права удалять shared resource bytes, current/recovery/staging/pin или активные undo/redo roots. Необходимы проверяемая принадлежность cleanup, состояние обеих веток History и действующий exact repair policy; recovery импортом остаётся созданием отдельного Project, не overwrite.
- Нужны исполняемые negative tests для Project/Revision/lease collisions, dangling staging `P→R`, orphan/pointer/root, старого recovery scan до commit, последующей команды и отложенного cleanup; проверки старых transactions до/во время/после, stale fence/takeover, missing capability/clone, retry/unknown, quota/cancel/crash, всех revision rows и shared bytes. Дополнительно проверить обычные независимые old-PWA операции, legacy commands/history и неизменные DB names/version.
- Эти проверки доказывают только наблюдаемые границы. Пока нет допустимого решения по взаимодействию с произвольными будущими uncooperative old writers, нельзя считать AD-4 полностью доказанным для этой модели; соответствующий rollout остаётся закрытым либо требует отдельного source/owner решения. Отказ не доказывает, что реальные данные уже повреждены.

## Метод и ограничения

Выполнены чтение sources и статическая проверка `durable-project-repository.ts`, `indexeddb-versioned-project-store.ts`, pin coordinator и journal. Тесты, приложения и fault injection в рамках этого review не запускались. Предлагаемый commit, pin ownership и recovery не объявляются реализованными или готовыми к release.
