# Независимый adversarial review browser registered storage

Проверены AD-31 и `browser-registered-storage-disposition-2026-11-05.md`, с сопоставлением текущих browser Project/asset/journal adapters, controller, SessionRetention и startup composition. Канонические документы не изменялись. Отдельная storage architecture и её проверки пока не реализованы этим review; потенциальные сценарии не объявляются воспроизведёнными пользовательскими потерями.

Вывод: **AD-31 задаёт условное направление, а не доказанную изоляцию или разрешение включить ingress.** Решение честно оставляет source/readiness gates открытыми, различает raw Project ID и scoped address, сохраняет существующий backup contract и ограничивает обещания для старой PWA. Ниже — существенные условия и доказательства, необходимые для реализации; они не означают, что соответствующие требования отсутствуют в disposition.

- **Отдельное имя IDB изолирует только конкретные проверенные old paths.** В текущем дереве старые Project и asset adapters используют жёсткие разные DB names, но это не защита от произвольного JS того же origin, старого build с перечислением БД, тестового очистителя или origin-wide clear/eviction. Диспозиция уже называет эту границу; нужен inventory и исполняемая проверка каждого поддерживаемого build/worker/rollback, включая фактический namespace нового bundle. Не заявлять изоляцию для неизвестного клиента или как security/account boundary.
- **Composite handle не доказывает FR-45 raw-ID uniqueness.** Существующие [legacy и registered] карточки с одинаковым raw Project ID можно безопасно адресовать через `(namespace, id)`, но это не гарантирует, что import создал новый ID относительно конкурирующего old producer: две DB не дают общей атомарной проверки. Disposition верно открывает source-owned выбор; forced-collision test показывает маршрутизацию, но не доказывает универсальную непересекаемость future IDs. До допуска нужны доказанный disjoint producer namespace/совместимая межконтекстная координация либо согласованная владельцами новая семантика идентичности, а не лишь случайный UUID.
- **Route identity должна быть непубличной и неизменной на всей операции.** Текущий `ProjectController` и `ProjectSummary` передают raw `projectId`, а `SessionRetentionProjectRepository` различает boundary по raw ID. Если scope выбирается заново после async ожидания либо берётся из файла/имени/id-prefix, одинаковые IDs могут перенаправить `load`, rename, delete, retry, takeover, undo, repair или export. Нужно доказать захват trusted owner и generation до async с отказом stale continuation; проверить одинаковые IDs при switch, позднем результате и восстановлении pending, не только две строки списка.
- **Сводная directory должна сохранять частичную недоступность и подтверждённый owner.** При недоступной/blocked/corrupt одной DB нельзя возвращать общий `empty` или позволять destructive действия по неразрешённой карточке; другая DB должна оставаться доступной там, где её условия доказаны. Typed outcomes должны различать empty, partial и unknown; проверить повторное открытие, исчезновение scope между рендером и подтверждением удаления, одинаковые имена/IDs и поздние async результаты. Не трактовать отсутствие зарегистрированной DB после ошибки как доказанно пустую историю пользователя.
- **Нельзя переиспользовать старый asset или journal adapter под новым Project scope.** В текущем browser composition Project DB, assets DB и pin journal имеют жёсткие имена; старый journal использует старый `openVersionedProjectDatabase`, а old asset store допускает registration/repair/delete по raw hash. Любая утечка этих ports в новый route разрушает гарантию разделения, даже если pointer лежит в новом DB. Нужен scoped inventory фактических зависимостей всей цепочки hydration/3D, библиотека, placement, repair, V1/legacy export, staging и cleanup; проверить реальные production bindings.
- **Copy model между scopes — новая mutation с отдельным pin, а не разделяемый root.** Выбор модели из старой library для нового Project требует точных исходных bytes/hash/length, проверки конфликтующей записи destination, собственного корня/pin и feasibility до publication; старый resource нельзя удалить при отказе или cleanup. Конкурирующее изменение/удаление legacy resource между read и copy должно привести к безопасному отказу либо использованию уже проверенного immutable snapshot. Нужны тесты общей SHA с разными bytes и отложенного старого cleanup.
- **Отдельная база не устраняет гонки двух новых вкладок.** Копирование текущего `FencedProjectRepository`/`writeStaging` в другой DB оставит `revisions.put` до fence и небезопасное recovery. Диспозиция требует другой scoped protocol: atomic fence/base и ownership до каждого stage/write/delete, no-overwrite IDs, attempt receipt, conditional no-publish cleanup и roots для current/undo/redo. Проверить takeover и устаревшие writes в реальном browser с отдельными connections, включая старый Project с тем же raw ID; провал обязательного lock/fence закрывает только новый scoped write без fallback.
- **Project и resource stores остаются одним protocol даже при нескольких IDB.** Предпочтительная одна новая DB позволяет общую metadata/resource transaction, но наличие одной DB не доказывает автоматическую атомарность операций, если они всё равно разбиты по transactions. При нескольких DB нужны recoverable journal, exact attempt ownership и безопасный pending/unknown commit; `put` collision или ID-only receipt недостаточны. Проверить quota/crash после pin, до/после pointer commit, при повторе и при конкурентном потребителе; не удалять shared bytes по отсутствующему pointer.
- **No-GC обещание должно покрывать уже существующие точечные удаления.** Запрет вводить общий GC не предотвращает отдельные `delete`, cancel pin, `discardStaging`, recovery или confirmed Project deletion. Каждая такая операция должна иметь доказанный scoped ownership и сохранять current/recovery/active undo/redo roots других Projects и попыток. Отдельно проверить два новых Project с одним exact resource hash и разными history lifetimes; не переносить старый удаляющий код без scoped inventory.
- **Стартовый release/worker gate сейчас привязан к одному legacy store.** `createProductionRuntime` передаёт существующий Project store в `ReleaseStartupCoordinator` и reconciles только его pin journal. Новый DB не должен становиться writable лишь потому, что legacy manifest и старый store прошли handshake; нужны отдельная проверка новой schema/состояния и порядок recovery до её записи, сохраняя доступ к безопасному legacy scope. Проверить worker mismatch, retained chunks, offline cold start, rollback и повреждённый/более новый registered store.
- **Отсутствие нового store и valid-present rollback остаются различимы только при доказанной внешней опоре.** Browser может удалить весь origin storage, а валидный snapshot DB с ранее использованным counter может быть восстановлен; локальный marker не доказывает, что нет старых in-flight операций. Диспозиция оставляет first-use/previously-provisioned и anti-ABA protocol открытыми. Нужны конкретные recovery/UX решения и внешнее authority/barrier либо отказ от сильного non-reuse claim; случайный epoch не является детерминированным доказательством. Browser и iOS Home Screen contexts проверять по их фактической storage boundary.
- **FR-44 требует сохранения representability после каждого разрешённого перехода.** Входной §1.4 preflight не доказывает, что затем новый scoped edit, history, repair или model placement по-прежнему экспортируется старым browser codec. Необходимо scoped FPC/domain proof на каждом соответствующем Durable transition и real legacy export/consumer roundtrip с exact resources; registered V1 transfer не заменяет старый complete backup. Если это приводит к ограничениям новых команд, UX/SPEC owners должны их явно согласовать и проверить, не меняя legacy поведение.
- **Не все поля V1 представимы старым exporter, даже в полностью изолированном store.** `-0`, own-undefined и uppercase aliases относятся к wire/serializer и consumer grammar, а не к DB name. Успешный V1 writer или доступность bytes в новом scope не разрешают ослабить действующий registered Web ingress или объявить универсальный обратный импорт. Evidence должна различать старый backup/reimport, дополнительный V1 transfer/TMA consumer и допустимое обратное Web подмножество.
- **Old PWA rollback имеет явное функциональное ограничение.** Старый client не покажет проекты нового namespace, даже когда данные существуют; старый build нельзя заставить предупредить о них задним числом. До rollback необходим source-owned UX/release путь, честно указывающий невидимость и проверенный экспорт/отдельное восстановление из файла без объявления удаления или синхронизации. Проверить, что старые проекты и их exports при этом не меняются, а возврат на новый build снова показывает корректные scoped cards.
- **Общая квота и аккаунт не разделяются именем DB.** Storage pressure или origin eviction могут затронуть обе DB; новый import при quota failure не вправе освобождать legacy Projects/resources и не должен маркировать другую базу пустой. Browser-local namespace не создаёт отдельного пользователя, приватности или авторизации; нельзя переносить Telegram identity assumptions в browser adapter. Проверить storage estimate/persist UX и последствия очистки на обе области.
- **SPEC/UX/readiness должны отдельно принять новые границы, а не следовать из ADOPTED.** SPEC §1.4 исторически описывает browser ingress и предыдущую storage applicability; требуются согласованные CAP/FR, directory UX, старый client и crash/recovery policy, а также собственный gate AD-31. `ADOPTED` означает принятую архитектурную направленность, не правку SPEC kernel, не интеграционные результаты и не release. Пока эти source/evidence условия открыты, отсутствие новой DB или отдельные успехи Telegram не позволяют включить scoped browser ingress.
