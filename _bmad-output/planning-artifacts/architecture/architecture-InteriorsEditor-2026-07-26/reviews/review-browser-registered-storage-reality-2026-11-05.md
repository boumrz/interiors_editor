# Independent reality review — isolated browser registered storage

Date: 2026-11-05. Scope: AD-31 and `browser-registered-storage-disposition-2026-11-05.md`, checked against the current browser controller/repository/resource ports, Telegram-specific substrate, registered and legacy backup paths, and current SPEC companions. This is read-only source inspection; no application or canonical document was changed, and no two-database, recovery or device test was run.

**Verdict: PASS WITH SOURCE RECONCILIATION, IMPLEMENTATION AND EVIDENCE PENDING; NOT READY to enable the new storage.** The architecture accurately identifies that merging card lists is insufficient, preserves the existing legacy backup restriction and does not fabricate Telegram identity. The new isolated repository, owner-aware routing, bootstrap/eviction proof and cross-namespace raw-ID disposition are not implemented or demonstrated by the inspected code.

- The current browser composition constructs one legacy `IndexedDbVersionedProjectStore`, one `IndexedDbCustomAssetResourceStore`, one fenced repository and one pin journal (`apps/web/src/app/production-app.ts:43–88`). `createSharedProjectController` accepts one repository, resource store, library, pin-staging port and feasibility policy (`shared-project-controller.ts:78–150`). No `interiors-editor-browser-registered` implementation was found in the application tree. AD-31 correctly describes an architectural direction rather than an existing browser capability.

- A distinct new database name can prevent the inspected old browser build's ordinary Project, Revision, staging and recovery code from operating on that database, provided the supported old-build inventory confirms its fixed names. It does not make the old PWA display new-scope Projects, isolate code running on the same origin, prevent shared origin eviction/clear or provide extra storage quota. Test actual versions and distinguish browser tab from iOS Home Screen storage; the disposition states these boundaries rather than promising transparent rollback.

- `ProjectSummary`, `ProjectDirectoryPort.loadProject` and `ProjectDeletionPort` currently identify a card by raw `projectId` alone (`application/ports.ts:449–503`); `AppShell.tsx` also keys and opens cards by that string. Equal IDs across two stores can collide in presentation or select the wrong Project. The proposed trusted `(namespace, raw ProjectId)` handle must survive all card, load, export, delete and async paths without rewriting the Project ID stored in a Revision or backup. A first-match lookup, inferred prefix or duplicate React key is not sufficient.

- A composite handle prevents confused routing but does not alone establish FR-45's new Project ID requirement across local stores. The disposition correctly leaves globally unique raw ID versus explicitly approved scoped-identity semantics to source owners, including concurrent legacy producers. A random UUID or reading two databases one after the other does not prove an atomic cross-store absence invariant; forced same-ID tests and an explicit decision remain gates.

- Routing must also bind `create`/registered import destination, active Project commands, `publishNextRevision`, writer lease inspection/takeover, history, pending/retry and recovery to the source owner. The current `SessionRetentionProjectRepository` decides whether roots belong to a candidate using only `candidate.project.projectId` (`session-retention-project-repository.ts:110–125`); equal IDs across stores can wrongly join histories unless owner is part of the binding. Capture owner and generation across awaits rather than dereferencing a mutable global current store.

- The current renderer requests GLB bytes through `readCustomGlbResource(resourceHash)` with no Project/namespace (`project-controller.ts:947–953`; `AppShell.tsx:2247–2253`). The same unscoped resource dependency serves integrity, exact repair and recovery. Routing only directory operations would let a late render/repair read or write the wrong DB, potentially reporting false missing data or modifying another scope. Tests must switch Projects while reads, repair, cleanup and writer takeover are delayed, including equal hashes in both stores.

- Current `BrowserRegisteredProjectExporter` is wired to `customAssetResources.readPinnedSnapshot` in browser production, and the controller reloads a selected Project through a single `projectDirectory` before export (`production-app.ts:81–110`; `project-controller.ts:2019–2057`). Selecting a new-scope Project while retaining that legacy resource callback would combine a correct Project row with the wrong resource store. Both existing legacy backup and additional V1 transfer/recovery exports need the selected owner's exact durable snapshot, checksum, resource roots and lifetime, not lookup by raw hash alone.

- Registered ingress already requires the old browser backup representability check in SPEC §1.4 and `BrowserRegisteredTransferDecoder`; isolation is not permission to accept arbitrary uppercase hashes, `-0` or own-undefined. The disposition appropriately requires each new-scope non-corrupt Durable Project, including subsequent commands and undo/redo, to remain fully exportable offline by the existing browser codec with exact resources. Prove the actual legacy exporter/decoder, applicable parser/limits and scoped resource reads end to end; a successful V1 writer or an import-only check does not establish that invariant for later mutations.

- A cross-scope library choice is more than a shared hash. Current UI and controller assume one `CustomAssetLibraryPort` and resource store, including register, remove, hydration and placement (`project-controller.ts:947–970`; `shared-project-controller.ts:122–150`). When a new-scope Project uses a model present only in legacy storage, copy independently verified exact bytes into the destination, establish its own pinned root and feasibility before publication, and leave the original/other histories intact. Define UI ownership and removal behavior without silently moving cards or falling back to a remote browse cache.

- Deletion and recovery cannot use an arbitrary legacy method on a new-scope handle: browser `permanentlyDeleteProject` deletes owned Project rows and associated lease in its particular database, and legacy `recover()` discards staging by Project ID (`indexeddb-versioned-project-store.ts:323–340,349–399`; `durable-project-repository.ts:255–260`). Each scope needs its own fenced delete, receipt/no-publish reconciliation and current/undo/redo resource roots; an error, absent scope or ambiguous result must not authorize cleanup in the other store.

- `production-app.ts` currently wires release/startup reconciliation only to the legacy store and pin coordinator. The additional database requires separately proved initialization, identity/counter, schema-version handling, crash recovery and capability checks. An absent DB/marker alone cannot distinguish first use from origin eviction, clear or rollback with a delayed attempt; fail closed for the affected scope when this distinction cannot be established, preserve legacy access, and never reset or silently recreate user data as a recovery shortcut.

- The Telegram substrate is not a browser identity adapter: `TelegramRuntimeSession` requires `VerifiedTelegramScope`, `TelegramScopeStore` binds that session to `interiors-editor-projects:${scope}`, a `interiors-tma-storage-v1` Web Lock, scoped metadata and `tma-v1:` attempt/lease IDs (`telegram-runtime-session.ts:1–14`; `telegram-scope-store.ts:35–59,132–186`). The disposition correctly forbids casting a made-up scope or weakening AD-26. Any host-neutral algorithm extraction requires a separately owned browser adapter and proof, while preserving Telegram's identity, lifecycle and tests; Telegram test counts are not browser evidence.

- Secure Web Locks and strict IDB durability are availability gates for the currently inspected Telegram-style substrate, whereas the current browser UUID fallback explicitly supports a non-secure local HTTP preview (`browser-ports.ts:21–35`). The proposed browser scope must not silently fall back to unsafe publication when those guarantees are absent, nor block unrelated healthy legacy Projects. Supported browser/device behavior and a precise read-only/unavailable outcome require explicit UX and test evidence.

- The current directory result can expose `recoveryNeeded` alongside healthy cards but has no typed owner-level unavailable state (`application/ports.ts:455–470`). Two-store aggregation needs to preserve accessible cards, identify an unavailable/unknown source, reject ambiguous destructive actions and prevent late responses from replacing current UI state. An inaccessible database is not an empty directory and must not trigger mass creation, deletion or corruption classification.

- Evidence remains necessary for forced equal Project/Revision/hash IDs, simultaneous old/new tabs, stage/fence/lease/pin and counter collisions, crash before/after commit, lost response, quota and eviction, lock denial, owner switches during async operations, single-source failure, exact repair, scoped library copy, confirmed deletion, full legacy backup/reimport and V1→strict TMA handoff. Verify unchanged legacy browser/PWA and actual mobile version/storage matrix; source inspection or Telegram-only tests do not prove implementation, physical FR-57 or release readiness.
