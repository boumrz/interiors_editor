# Независимая rubric/source-проверка browser registered storage

Дата: 2026-11-05. Проверены AD-31 и `browser-registered-storage-disposition-2026-11-05.md` против CAP-1/8/9/10/13, FR-44/45/57/58, NFR-10–13/28, AD-4/25–30 и актуального `project-and-backup-contract.md` §1.4; статически сверены browser composition и directory ports. Канонические источники этим review не изменялись.

## Вердикт: PASS ДЛЯ АРХИТЕКТУРНОГО НАПРАВЛЕНИЯ; SOURCE RECONCILIATION, IMPLEMENTATION И EVIDENCE PENDING

AD-31 задаёт отдельный browser-local owner для нового registered import и не называет это доказанной реализацией или принятым исключением из CAP/FR. Диспозиция правильно отделяет видимость в старой PWA, routing по namespace и Project ID, scoped resource roots и прежний backup contract. После первоначальной сверки уточнено: невидимость новых Projects старой PWA — техническое следствие предлагаемого направления, не доказательство полного product/source acceptance rollback. Применимость SPEC/UX и безопасность реализации ещё нужно отдельно подтвердить; этот review не является readiness verdict или разрешением release.

## Согласование источников и ответственных

- **SPEC owner:** согласовать `project-and-backup-contract.md` §1.4 и `telegram-platform-and-compatibility-contract.md` с новой browser composition, условиями bootstrap/recovery, объединённой directory и version/rollback matrix, сохранив CAP-1/8/9/10/13 и FR-44/45/47/57/58. Текущая §1.4 предписывает прежнюю browser default feasibility, exact legacy-backup representability и proof для ранее выбранного старого cleanup в существующем подходе; нельзя объявлять их автоматически переопределёнными одной записью AD-31. Если нужен пересмотр SPEC kernel, его выполняет только `bmad-spec`.
- **Architecture owner:** поддерживать AD-31 и его связь с AD-4 и AD-25–30, зафиксировать trust и lifecycle нового browser scope, маршрутизацию и полный protocol/conditional cleanup. Сохранение старых DB names/data по AD-25 обязательно; новая DB не доказывает безопасность старого browser history protocol и не является Telegram identity/scope.
- **UX owner:** обновить `EXPERIENCE.md`/другие затронутые UX surfaces для общего списка и действий каждого Project, частичной недоступности одного источника, различимых одинаковых карточек, backup и честной невидимости нового scope при старой PWA/rollback. Нельзя заставить уже установленный старый build задним числом показать новое предупреждение или представить отсутствие карточки как удаление. Source-owned поддерживаемую version matrix ещё предстоит определить.
- **PRD/Product owner:** сохранить FR-44/45/57/58 и принять отдельную disposition только если предлагается изменение product guarantee, raw Project ID semantics или обязательной совместимости rollback; нельзя считать сам выбор новой DB разрешением на вероятностное ослабление или новую policy. FR-58 сохраняет существующие Web/PWA данные и поддерживаемые clients, но не содержит прямой формулы «каждая старая сборка читает каждый будущий Project»; фактическую границу версий нужно согласовать и проверить.
- **Epic/story и readiness owners:** добавить AD-31 к CAP/FR/NFR traceability, зависимостям и приёмочным критериям; отдельно проверить применимый implementation-readiness gate или явно действующий письменный waiver в его точном scope. Исторический Alpha READY, S1, локальные S2/S3 и один архитектурный документ не являются READY для AD-31, подтверждением old-PWA compatibility или physical release.

## Незакрытые условия и evidence

- Один новый IDB bundle с Project/Revision, attempt/receipt, fence, pin/roots, resources и library может изолировать новый import от обычных путей проверенных старых builds, обращающихся только к старым DB names. Это не авторизация, не изоляция от same-origin code, origin-wide clear/eviction или общей квоты; нужны inventory и evidence для каждого поддерживаемого старого клиента.
- Scope выбирает trusted composition, а не данные файла, Project ID prefix или Telegram identity. Новый browser runtime не должен выдавать себя за `VerifiedTelegramScope` или наследовать Telegram READY; общий host-neutral алгоритм нуждается в отдельном browser adapter, проверках и traceability.
- Composite handle `(namespace, raw ProjectId)` необходим для точной адресации существующих records, но не доказывает FR-45 «новый Project ID» относительно остальных локальных Projects. Пока не выбрано доказанное глобальное исключение collisions либо owner-defined допустимая scoped identity semantics, случайный UUID и два последовательных чтения независимых DB не являются atomic proof. Forced collision не должен открывать, изменять или удалять другой Project.
- Объединение списка не завершает routing: handle и generation должны сохраняться в open, редактировании, takeover, undo/redo, pending/retry, repair, hydration, обоих exports, deletion и async callbacks. Текущие `ProjectSummary` и `ProjectDirectoryPort.loadProject` содержат только raw ProjectId (`ports.ts:452–475`); выбираемый owner нельзя определять первым совпадением, именем или raw hash.
- При отказе/блокировке одной DB вторая должна оставаться доступной по своим правилам; directory обязана показать неполноту источника без ложного `empty`, массовой corruption, auto-repair или удаления. Достаточные typed partial outcomes и понятное различение совпадающих карточек ещё требуют UX/source и implementation evidence.
- Exact bytes, hash, length и local pin должны принадлежать правильному owner; library asset из старой области копируется только после проверки, собственного pin и feasibility нового scope. Если stores разделены, нужен доказанный cross-store journal; ни cleanup, repair, quota failure, ни общая library не могут освобождать чужие current/recovery/staging/pin/undo/redo roots.
- CAP-10/FR-44 сохраняют offline complete backup каждого non-corrupt Durable Project текущей policy. Существующее действие для нового Project должно вызывать прежний codec с **его** scoped resource store; новый V1 transfer не заменяет этот backup. Вход §1.4 по-прежнему отклоняет snapshots, чья точная representability старым backup не доказана; смена DB не разрешает незаметно принять uppercase, `-0` или own-undefined вне этой границы.
- Новый scope сам требует доказанного первого запуска, двух новых вкладок, одного fenced writer, takeover, crash/unknown commit, сохранности attempt/receipt и non-reuse. Отсутствующая DB после очистки, eviction или restore не доказывает virgin state, пока другой new-client context может удерживать старые IDs. Самостоятельный counter или новый DB name не является доказанным anti-ABA механизмом; неоднозначность не должна сбрасывать данные или блокировать безопасный legacy scope.
- Старый установленный PWA не сможет сам открыть новое хранилище, если он обращается только к прежним names. Его старые Projects и файлы сохраняются; импорт полного поддерживаемого файла в старом клиенте создаёт отдельную копию, а не синхронизацию. Нужны конкретная версия/rollback UX, фактическое внешнее сохранение и reimport, условия доступности старого контекста и тестирование; этот факт не объявляет новую функцию доступной или полную FR-57 matrix пройденной.
- До реализации/включения требуются подтверждённые source applicability и gate; затем поведенческие evidence по concurrent contexts, stale async owner, forced IDs, partial DB availability, exact pinned GLB, offline reopen/edit/undo/export/repair, old PWA/version rollback, quota/crash и независимым legacy Projects. Физические iOS/Android handoff и NFR-28 остаются отдельными условиями; отсутствие новой registered DB не должно молча считаться пользовательским согласием на создание пустого scope.
