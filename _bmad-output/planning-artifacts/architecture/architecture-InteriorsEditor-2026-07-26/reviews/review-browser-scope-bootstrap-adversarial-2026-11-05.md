# Независимый adversarial review browser scope bootstrap

Проверены AD-31, `browser-registered-storage-disposition-2026-11-05.md`, SPEC `project-and-backup-contract.md` §1.4 и UX directory; сопоставлены текущие browser importer/profile/controller и Telegram storage test harness. Канонические документы не изменялись. Это review планируемого протокола, а не факт реализации нового browser storage или physical acceptance.

Вывод: **принятое scoped FR-45 решение и bounded fresh-v0 описывают достижимое направление без вымышленного доказательства глобальной raw-ID уникальности.** Реализация и readiness остаются открыты; обновлённая disposition уже точно различает unknown commit и valid-present rollback; их ещё необходимо доказать вместе с late-open, durable ownership, соответствием фактическому profile и сохранением настоящих TMA тестовых путей. Никакой риск-waiver не подразумевается.

- **Receipt для неизвестного исхода ещё требует executable proof.** Обновлённая disposition уже правильно различает доказанный abort до commit, подтверждённый Durable commit и неизвестный исход, сохраняющий roots до receipt-based reconciliation. Если pointer commit завершился до потери ответа, Project существует, даже если клиент ещё не знает результат. Проверить это в реальных crash/cancel race и не называть cancellation после commit откатом.
- **Valid-present rollback по-прежнему требует lifecycle proof.** Обновлённая disposition уже различает snapshot без DB, который может выглядеть как fresh-v0, и восстановленную корректную существующую v1 DB, которая может открыться без upgrade event с устаревшим marker/counter. Оба случая не доказывают отсутствие ранее выданных ID; необходима проверка ограниченной lifecycle модели либо внешнего anti-rollback evidence.
- **`not-provisioned` — результат проверенного probe, не отсутствия видимой карточки.** Текущий directory может исключать нечитаемые Project rows и сообщать recovery отдельно; для новой DB отсутствие записи списка, failure, blocked, timeout или отсутствие `indexedDB.databases()` не являются доказанной отсутствующей DB. При open-based probe нужно различать действительно увиденный `oldVersion=0` с завершённым abort от общего AbortError и не оставлять DB, а затем учитывать, что другая вкладка могла её создать. Не подменять актуальную недоступность чистым `empty`.
- **Поздний open должен оставаться под контролем после timeout или отмены.** `IDBOpenDBRequest` не прекращается автоматически при reject promise, `onblocked` или освобождении Web Lock. Abandoned flag и generation проверяются внутри позднего `onupgradeneeded`, transaction abort-ится при утрате допуска, поздний `onsuccess` закрывается; обработчики остаются действующими до фактического завершения request. Текущий browser `openVersionedProjectDatabase` лишь вызывает reject на `blocked` и не доказывает такого поведения; нужна реальная contention-проверка, а не только синтетическое событие.
- **Lock не отменяет активную работу и не заменяет атомарный fence.** Web Locks кооперативны; после grant переданный AbortSignal сам не отменяет callback или IDB transaction, а callback, вернувшийся до `transaction.oncomplete`, рано освобождает lock. `steal` может оставить старый код исполняться без исключительного владения. Disposition это правильно запрещает/ограничивает; проверить cancel до/после grant, завершение всех IDB requests и receipt до release, stale writer после takeover и scope-switch без рекурсивного захвата.
- **`versionchange`, `close` и JS generation имеют разные границы.** Обработчик должен отозвать допуск и явно разрулить уже начатые transactions; `db.close()` ждёт их окончания и не доказывает abort. Forced close/ошибка может прийти без обычного versionchange, а frozen/killed context не обязан доставить приложению событие. Проверить late callbacks и reopen в реальном двухконтекстном browser: получивший старую generation не может автоматически присвоить новую и продолжить writes/cleanup; уже совершённый commit рассматривается по receipt.
- **Counter подтверждается в рамках текущей инкарнации, не всей внешней истории.** Fresh-v0 создаёт начальный marker/counter атомарно только после разрешённого выбранного импорта; existing bad/missing/foreign metadata остаётся закрытой. Для active contexts нужны durable monotonic allocation, обязательная commit до раскрытия ID, проверка identity/generation и обработка overflow. После неразличимого origin clear или old snapshot локальное состояние не может само доказать глобальное non-reuse. SPEC/UX должны сохранять оговорку NFR-13 и не объявлять эту более сильную гарантию выполненной.
- **Проверка raw ID должна точно следовать принятой scoped semantics.** Candidate Project ID сравнивается с исходным Project ID по точным code units, затем с существующими Projects обоих известных browser stores до принятия; unavailable/corrupt lookup не выдаётся за отсутствие. Destination atomically checks/adds свои Project/Revision и no-ABA. Конкурирующий или будущий old-client collision после preaccept не запрещён: две записи остаются, никакой global uniqueness или повторной блокировки старого клиента не требуется. Тест должен проверять обе временные последовательности, а не только независимые UUID.
- **Profile и destination owner нужно провести через текущий importer без fallback.** `BrowserRegisteredTransferDecoder` сейчас владеет приватными `decoded`/`sealed` WeakSets и зависимостью от прежнего resource port; `ImportPortableBackupUseCase` вызывает `prepare`/`seal` до staging и `beforePublish` перед repository. Новый route должен выполнить source-only preflight без создания DB, затем безопасно привязать profile, destination resource service, `(namespace, raw ID)`, immutable candidate и конкретную попытку к одному scope. Clone, switch, потеря capability и generic retry не должны незаметно вернуться в старый repository либо подменить proof.
- **Current `saved`/pending и UI identity не содержат owner.** Текущий `ImportPortableBackupResult` и status несут raw Project ID/candidate; `ProjectController` и `AppShell` местами сравнивают, фильтруют и ключуют карточки одним raw ID. При разрешённом совпадении двух stores успешный импорт, open/delete, история и поздние callbacks должны продолжить с проверенным owner handle, а UI — показывать две различимые записи. Scope остаётся внутренним context, не записывается в domain Project/backup и не угадывается по содержимому файла.
- **Source и UX о явном fresh-v0 должны быть согласованы для shipped версии.** UX уже различает обычный не создающий probe и явно выбранный validated import, который может создать текущий v0; известная потеря существовавшего marker остаётся recovery. Диспозиция оставляет условное предложение уточнить старую wording `не создавать заново`; перед readiness следует проверить точные актуальные UX/SPEC строки и историю внешней потери. Не трактовать user selection как согласие стереть данные или подтверждение, что прошлых Projects не было.
- **Schema commit и последующий отказ — отдельные outcomes.** После успешного native versionchange может остаться валидная служебная DB без Project, если следующая проверка обоих IDs, quota или пользовательская отмена блокируют import. Не удалять её при cancel, не показывать импорт успешным и не объявлять, что в прошлом данных не было; новый import проверяет actual marker/counter. Existing invalid schema, future version, чужой marker и неразличимые ошибки требуют fail-closed без reset/upgrade и без влияния на legacy store.
- **Сохранение TMA tests означает реальные существующие adapters и fixtures.** `playwright.telegram-storage.config.mjs` включает browser storage/project/resources/recovery/library/atomicity checks; harness создаёт реальные `TelegramScopeStore`/`TelegramProjectRepository` поверх IDB и использует явно тестовые fake scope IDs. При host-neutral extraction нельзя заменить adapters in-memory mocks или ослабить эти проверки, но и нельзя объявлять test-only fake scope подписанным Telegram physical acceptance. Нужны существующие runtime/identity/race suites и отдельный browser corpus после каждого соответствующего извлечения.
- **Source changes не превращают тестовые планы в evidence.** AD-31 и §1.4 уже приняли scoped identity; принудительное требование вечной глобальной raw-ID уникальности противоречит принятому решению. Предыдущий `review-browser-registered-storage-adversarial-2026-11-05.md` записан до этого решения и его исторический пункт о незакрытом выборе глобальной уникальности не является текущим prerequisite. До scoped implementation/readiness и фактических old-PWA, device и offline проверок нельзя объявлять новый ingress готовым к выпуску.
