# Независимая rubric/source-проверка browser scope и fresh-v0 bootstrap

Дата: 2026-11-05. Проверены AD-31 и `browser-registered-storage-disposition-2026-11-05.md` против PRD FR-45/57, SPEC CAP-10 и Project/Backup §1.4, UX `EXPERIENCE.md`, AD-4 и S2 `telegram-s2-fencing-disposition-2026-11-04.md`. Канонические документы этим review не изменялись.

## Вердикт: UX SOURCE RECONCILIATION PENDING; IMPLEMENTATION И EVIDENCE PENDING

Architecture согласована с принятым FR-45 по scoped identity и описывает fresh-v0 как создание новой **текущей** области, а не доказательство отсутствия или восстановления прежних данных. После обновления SPEC §1.4 и UX table также различают явный fresh-v0, existing missing/corrupt marker и unknown commit. В старой строке UX об импорте ещё остаются безусловная формулировка об отмене и неверный статус решения FR-45; это source reconciliation, а не отсутствие physical evidence. Review не является readiness verdict или разрешением release.

## Source-сверка и конкретные расхождения

- FR-45 (`prd.md:716–744`), SPEC §1.4 (`project-and-backup-contract.md:265–284`) и AD-31 фиксируют одинаковую последовательность: новый raw Project ID точно отличается от source ID; до принятия проверяется отсутствие существующих Projects с таким ID в обоих доступных browser stores; destination атомарно проверяет и создаёт Project/Revision; проверка двух отдельных IDB не атомарна, а конкурентное или позднее совпадение старого клиента сохраняет отдельные записи по доверенному `(namespace, raw ProjectId)`. Глобальная уникальность и слияние не предполагаются.
- SPEC §1.4:306+ и UX table после обновления отдельно описывают отсутствующую сейчас whole DB, разрешённый только явным validated import fresh-v0 и existing DB с недоступной/повреждённой metadata. Оба источника сохраняют запрет auto-reset и не объявляют данные прошлого отсутствовавшими или восстановленными; считать прежнее замечание об отсутствии этой ветви устранённым.
- `EXPERIENCE.md:364–367,438` всё ещё говорит о необходимости решения FR-45 по областям; source decision уже отражён в PRD и SPEC. Следует сохранить pending реализацию, evidence и readiness, но не представлять принятое scoped-identity решение как отсутствующее.
- `EXPERIENCE.md:438` безусловно заявляет, что отмена не публикует Project. После фактического commit или при неустановленном результате cancel/timeout сам по себе не доказывает no-publication. Нужно различить доказанный abort до commit и committed/unknown с сохранением roots и receipt reconciliation, как это делает disposition после корректировки.
- SPEC §1.4 после source-owner уточнения различает запрет reset counter существующей DB и разрешённый при условиях fresh whole-DB v0. Это условная применимость, а не proof реализации или восстановления данных после внешней очистки.

## Условия реализации и отдельные доказательства

- Обычный listing/probe не создаёт новую DB; если existing-only проверка использует `indexedDB.open`, v0 upgrade прерывается и поздний success закрывается. Наблюдаемая текущая пустота или отсутствие DB не сообщает историю пользователя и не является доказательством, что прежних Projects никогда не было.
- Только явно выбранный registered import после bounded validation, smoke, cancellation и pre-ID legacy representability может начать bootstrap. Под общим проверенным lock native `oldVersion=0` создаёт schema, identity и counter одной versionchange transaction; в existing DB missing/corrupt/foreign marker, counter или schema дают recovery/read-only/отказ без reset и fallback. Вторая вкладка, обнаружив уже созданную DB, проверяет existing path.
- После schema commit повторно проверяются identity, counter и publication predicates; только затем проверяется сгенерированный candidate ID по source и обоим stores и выполняется destination no-overwrite/no-ABA. Если позднее старая область создаст тот же raw ID, обе записи остаются различимыми и все действия направляются по их owner handles.
- Ранее подтверждённая DB, исчезнувшая в живом context, не приравнивается к безопасному fresh bootstrap. Полная потеря всех markers или старый valid snapshot могут быть внешне неотличимы от первого запуска либо безопасной предыдущей версии; нельзя заявлять восстановление прошлого, бесконечное non-reuse или отсутствие eviction. Известная потеря остаётся recovery; неизбежный внешний риск и проверенный backup показываются честно.
- Native `versionchange`, lock/cancellation и late callbacks требуют реального исполнения: `db.close()` не abort-ит уже начатую transaction, timeout не отменяет `IDBOpenDBRequest`, а lock cancellation после grant не отменяет mutation автоматически. Старые capabilities/attempts не должны писать или чистить новый scope; при недоказанном жизненном цикле mutation fail closed.
- Если schema v0 создана, но подтверждённого Project commit нет, валидная служебная область может сохраниться без автоматического удаления; её текущее состояние можно назвать пустым только после успешного чтения и без заявлений о прошлых данных. При неопределённом commit сохраняются journal/pins и применяется reconciliation; ни `imported`, ни отсутствие Project по timeout не утверждаются.
- Composite routing сопровождает directory, selection, open/edit/history, pin/repair/export/delete и A→B→A async callbacks. Частичный отказ одного store не выдается за `empty` или corruption всех Projects; безопасный legacy scope продолжает работать, а source файла остаётся неизменённым.
- Нужны исполняемые проверки fresh-v0, parallel bootstrap, existing missing/corrupt marker и counter, blocked/late upgrade, quota/abort, cancel до и после commit, actual unknown outcome, eviction/restore и живой stale context; отдельно — source-ID equality, forced collisions каждого store, поздняя old-client collision, full roots и старые PWA regressions. Реальные iOS/Android и external file tests относятся к отдельным physical gates, а их отсутствие само по себе не является документным противоречием.

## Метод и границы

Проведены чтение актуальных sources и статическая проверка; тесты, приложения и fault injection в рамках review не запускались. Наличие предложенных gates не означает их выполнения или готовности rollout.
