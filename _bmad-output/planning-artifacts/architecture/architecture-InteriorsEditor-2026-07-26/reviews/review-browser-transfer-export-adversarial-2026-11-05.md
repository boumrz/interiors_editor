# Независимый adversarial review дополнительного Web/PWA export

Объект: AD-30 и раздел «Дополнительный Web/PWA export для переноса — owner direction» в `telegram-portable-v1-disposition-2026-11-04.md`, с сопоставлением существующих browser controller, V1 exporter/codec, UI и SPEC §1.4. Канонические файлы не изменялись. Это проверка выбранного контракта и текущего кода; потенциальные гонки и требуемый corpus не выдаются за воспроизведённые пользовательские дефекты.

Вердикт: **дополнительное действие архитектурно отделено от прежнего экспорта, а ограничения обратного Web ingress и старого empty recovery названы честно. Implementation/readiness остаётся закрытым до UX/SPEC reconciliation и доказательств exact durable source, resource lifetime, old-PWA и конкретных file pairs.** Текущий browser production ещё не подключает этот exporter как отдельное действие. Пункты ниже в основном уточняют доказательства условий, которые новый текст уже требует.

- **Проверить фактическое durable происхождение, а не только in-memory current.** `ProjectController.loadProjectTransferSource()` возвращает `this.current` для открытого Project; между чтением controller и новым export мог измениться pointer, fence или выбранный Project. Требуемая disposition проверка selected Project/Revision должна атомарно либо эквивалентно доказать исходную durable ownership и выбрать понятную семантику: экспортировать захваченную Revision с точным обозначением или отказаться при устаревании. Нужны тесты текущего Project и выбора другой карточки, takeover, смены активного Project и удаления до/после snapshot.
- **Защита одного read transaction не доказывает долговечность исходной row.** Существующий старый `writeStaging` делает `revisions.put` до fence/base; старый клиент может затронуть строку с тем же ID как до снимка, так и позже. Чтение pointer и Revision вместе доказывает согласованное содержимое в этот момент, но без подтверждённого durable происхождения и сохранности оригинальной row не устанавливает, что она не подменена staging. Контракт правильно требует исключить cleanup/delete/takeover races; до допуска нужен проверяемый cross-version способ или fail closed. Не считать случай уже воспроизведённым и не заявлять глобальное исправление старого history protocol.
- **Structured identity нельзя вывести из старого checksum.** `ExportRuntimePortableBackupUseCase` сравнивает `serializeProjectCanonically(candidate.project)` с revision string и checksum; serializer использует JSON и не различает `-0`/`0`, own-undefined/absent, некоторые свойства массивов. Дальнейший `copyProject` сохраняет то, что получил, но не доказывает, что объект равен exact выбранной durable row. Доказать поле-в-поле identity structured snapshot, включая own keys, UTF-16 и массивы, прежде чем подписывать файл как результат выбранной Revision; при непредставимом сохранённом значении отказывать без изменения source.
- **Resource read и корректный hash не подтверждают pin/lifetime.** Все raw keys, включая case aliases, должны быть прочитаны в правильном browser scope и индивидуально проверены на length, SHA bits и exact bytes; два alias требуют независимой проверки и byte equality до dedup. При конкурентном удалении или очистке источник может исчезнуть между выбором Project и отдельными чтениями. Доказать root/pin удержание до получения полного immutable набора, включая старый cleanup; при невозможности отказать и не выдавать частичный архив. Доказать, что library/browse cache и Telegram store не используются вместо Project-owned pinned bytes.
- **Надёжность отдельной composition нужно проверять на полном wiring.** В `createSharedProjectController` общий `portable.feasibility` выбирает policy wrapper для всех публикаций, а `portable.exporter`, `decoder` и `recoveryDecoder` обслуживают другие пути. Добавление только отдельного V1 export не должно внедрить Telegram feasibility в browser, заменить legacy export/decoder или обойти зарегистрированный ingress и retry guard. Нужны integration tests реальной production composition, а не только экземпляра writer с тестовыми портами.
- **25 MiB и closed V1 grammar ограничивают действие сильнее, чем один envelope cap.** Текущий registered writer использует `validateProject` с 25-MiB custom limit и V1 closed grammar, а старый readable Project потенциально шире. Disposition уже разрешает безопасный отказ; UX и тесты должны сохранять этот отказ для >25 MiB, non-index array properties и иных непредставимых состояний, без классификации их как повреждённых и без подмены старого exporter. Возможность зарегистрированного TMA writer не доказывает экспорт всех healthy/readable browser Projects.
- **Утверждение о переносимости должно быть связано с конкретным получателем.** Отдельный V1 wire не принимается старым decoder; новый Web registered ingress имеет дополнительное legacy representability ограничение и может отклонить допустимые для wire `-0`, own-undefined и uppercase aliases. Успешное формирование файла не является доказанной browser recovery-копией или универсальным двусторонним переносом. UX owner должен определить видимое назначение, ограничения и обратную совместимость до внедрения; таблица evidence должна проверять Web→TMA и TMA→Web отдельно.
- **Unsaved и recovery data не должны маскироваться под экспортированную Revision.** При pending/saving либо fence-loss controller может иметь current Durable Project и отдельный draft/recovery candidate. Контракт требует честно различать их, но не выбирает конкретное UI состояние. Нужно проверить оба entry point — карточку и editor — при изменённом draft, ожидании и persist-failed: файл содержит только явно обозначенную Durable Revision; отдельный recovery export остаётся доступным под своим названием и не называется complete backup.
- **Существующий старый путь надо сохранить фактически, а не только название кнопки.** Старый UI выдаёт архив через `exportProjectTransfer` и browser local handoff; новый action не должен менять его encoder, тип/selector файла, local file session, directory entry, состояния ошибок, выбор версии, PWA offline capability или old retained chunks. Проверять до/после на старой и новой оболочке, в том числе одновременный открытый старый PWA. Само отсутствие schema upgrade не доказывает отсутствие нового поведения в shared modules.
- **Реакция на verifier failure и отмену должна отражать реальный результат.** Директива не позволяет объявить exception признаком повреждённого Project и не считает `ready`/picker доказательством сохранения. Обновлённая disposition уже фиксирует, что синхронный `zipSync` проверяет отмену только до/после упаковки и не даёт обещания отзывчивой отмены внутри неё или доказанного peak memory. Эти условия ещё требуют UX/evidence: проверить честное состояние этапа, отсутствие upload, утечек object URLs и изменения source при отказе/прерывании.
- **Проверяемый recovery старого empty файла пока отсутствует.** Старый selector без PPJ-disjoint witness остаётся ambiguous; новая export-кнопка не разрешает его автоматически и не доказывает происхождение. Кандидатная цепочка требует работающего проверенного старого importer для копии конкретного файла, открытия именно того же storage context новым build, успешного V1 export, внешней передачи и strict TMA import. Зафиксировать source archive SHA до/после, состояние старой копии, actual build IDs и field/resource equality с разрешённой заменой IDs/timestamps; при отсутствии любого шага sole-copy и FR-57 остаются pending.
- **Browser и iOS Home Screen не следует считать одним хранилищем.** Даже успешное открытие файла в одном контексте не доказывает, что обновлённый action видит Project из другого. Recovery chain и оба UI entry нуждаются в evidence конкретных origin, storage namespace, worker/release и upgrade без удаления старых assets. При недоступном старом контексте нельзя предлагать новый export как уже работающий путь.
- **Физическая матрица должна включать отрицательные и ограниченные пути.** Отдельно от положительного empty/Room/GLB corpus проверить реальные iOS и Android picker/download/reselect, strict TMA consumer, обратный Web отказ на непредставимом V1, старый клиент с новым selector, missing/corrupt/unpinned resource, cancel/exception и сохранность source. Получение `ready` или click не доказывает внешнее сохранение; не закрывать NFR-28/FR-57 одним synthetic ZIP или единственным устройством.

Опорные файлы текущего кода: `apps/web/src/app/project-controller.ts` (`loadProjectTransferSource`, `exportProjectTransfer`), `apps/web/src/application/export-runtime-portable-backup.ts`, `apps/web/src/adapters/portable-backup/registered-runtime-portable.ts`, `runtime-portable-backup-codec.ts`, `apps/web/src/app/shared-project-controller.ts`, `production-app.ts`, `apps/web/src/ui/AppShell.tsx` и `apps/web/src/adapters/persistence/indexeddb-versioned-project-store.ts`. Существующие source constraints, planned tests и owner direction не считаются прошедшими integration или physical checks.
