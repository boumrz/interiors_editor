# Independent reality review — additional browser transfer export

Date: 2026-11-05. Scope: updated AD-30 and “Дополнительный Web/PWA export для переноса” in the S3 disposition, checked against browser/Telegram composition, runtime V1 writer, Durable Project access, pinned resources, UX and SPEC. No application or canonical files were modified. This is source inspection; no new tests or physical transfers were run.

**Verdict: PASS WITH IMPLEMENTATION AND EVIDENCE PENDING.** A separate trusted browser action is a feasible additive design; the existing runtime exporter is a candidate for reuse, not a wired or demonstrated browser feature. The architecture disposition now reflects that UX and SPEC have added the export direction. Their mutual source reconciliation and applicable readiness/evidence gates remain open; nothing in this review authorizes or proves deployment.

- The current browser `production-app.ts:81–105` creates the registered decoder/smoke for the separate import, while its ordinary exporter remains `ExportPortableBackupUseCase` in `shared-project-controller.ts:254–264`. Telegram explicitly constructs `ExportRuntimePortableBackupUseCase` with its own scoped `repository.resources` after creating that repository (`telegram-runtime.ts:183–212`). A new browser dependency and action must be separate; replacing the shared `portable.exporter` would change the existing browser action.

- The updated S3 disposition now correctly recognizes the dedicated export sections in `telegram-platform-and-compatibility-contract.md` and `EXPERIENCE.md`. Verify their final source-owner reconciliation and the applicable readiness/evidence gates; neither section claims the feature is already available.

- `ExportRuntimePortableBackupUseCase` checks V1 schemas and matching Project IDs, performs read-only domain validation, deep-copies the Project, then requires exact canonical serialization and checksum of the Revision (`export-runtime-portable-backup.ts:27–50`). Its internal checks do not themselves prove that the supplied candidate is the selected persisted Durable Revision. The new route must establish Project/Revision ownership and exact structured persisted identity independently before naming the output a complete transfer.

- The current `loadProjectTransferSource` can return the in-memory `current` before consulting the durable directory (`project-controller.ts:1977–1989`). An in-memory clone or JSON checksum alone cannot prove that the Project object exactly matches its stored structured snapshot: JSON normalizes `-0` and omits own-`undefined`. Establish an immutable exact selected snapshot with source/pointer identity and protect it throughout export; do not export a pending unsaved candidate as Durable or silently mix an older Revision with newer resources.

- Browser `IndexedDbCustomAssetResourceStore.read` retrieves bytes by key (`indexeddb-custom-asset-resource-store.ts:55–62`); it does not by itself attest that the key is pinned or that its root will survive cleanup/delete/takeover. The disposition correctly calls for exact resource/root proof and lifetime protection. Demonstrate protection across the separate Project and resource stores and multiple contexts; do not replace unavailable Project-owned bytes with a browse cache or remote URL.

- The use case reads each original resource key separately, checks length and copies bytes before smoke (`export-runtime-portable-backup.ts:52–73`). Registered smoke checks static GLB/security, 256-bit digest and the configured 25 MiB resource cap; the registered writer repeats domain/resource validation and hashes each alias, deduplicating only when bytes agree (`portable-backup-read-render-smoke.ts:74–108`; `registered-runtime-portable.ts:71–98,129–150`; `runtime-portable-backup-codec.ts:185–205`). Verify missing, altered, unpinned and mixed-case alias rows with real bytes, including resource changes during the operation.

- The technical envelope's 50 MiB per entry is not the effective registered Web/TMA smoke/writer admission: current registered configuration uses 25 MiB (`registered-runtime-portable.ts:23,93–98,129–147`). The disposition correctly requires a separate source decision for a 25–50 MiB route. The use case can read resource bytes before smoke rejects them, so size-before-parse is not by itself proof of bounded peak memory; test real allocation, cancellation and aggregate limits.

- Empty/open Projects are admitted by the domain validator if otherwise valid; the smoke returns true without a 3D projection when there are no Room records. With Rooms it requires a constructible `projectRectangularRoomForWebGl` scene (`runtime-v1-project-validation.ts:35–48`; `portable-backup-read-render-smoke.ts:55–71`). This is neither a real GPU render nor evidence every valid complex room is accepted. Test an actual empty Project, a normal Room, a more complex valid plan and existing geometry failures with the real writer.

- The current writer is closed V1 grammar, not a codec for every readable historical object. It rejects non-index array properties and other out-of-grammar structures (`runtime-v1-wire.ts:233–250`), while the exporter also requires its canonical serialized Project to equal the stored Revision string. Durable repository readability is less strict because it compares JSON-normalized values (`durable-project-repository.ts:267–305,328–342`). Do not classify a safe unsupported legacy snapshot as corrupt, replace the old exporter, or assert FR-44 for all non-corrupt Projects.

- Runtime V1 can preserve `-0`, own-`undefined`, Unicode and original case-sensitive hashes, but the planned browser registered ingress separately requires exact representability by the old browser backup. Thus Web→TMA and TMA→Web differ for some valid V1 snapshots. Old browser decoder cannot consume the new selector, and a file being prepared or a system picker opening does not prove an external save or successful import; UI and compatibility claims must state these boundaries.

- The existing use-case tests cover validation, checksum, source snapshot, resource errors and cancellation but several cases inject mock smoke/writer (`export-runtime-portable-backup.test.ts:38–160,211–335`); they do not establish actual Web browser composition, pinned real GLB, strict TMA import or physical handoff. Run integration and device evidence for actual empty/room/model files, exact fields/hosts/resources, source unchanged, current/other Project selection, old export and PWA regression, and return-route limitations.

- The export use case catches a resource-read exception, but checksum, smoke and writer failures may throw (`export-runtime-portable-backup.ts:44–87`). The new action must distinguish unavailable verifier/unsupported state/cancellation and avoid reporting an implementation error as a corrupt Project or completed file; keep source and existing actions intact. Also test concurrency with writer-lease takeover, deletion, stale directory selection, late cancellation and failed or inaccessible system handoff.

- The proposed ambiguous empty legacy recovery is correctly conditional on a particular actual file, intact original hash, the right browser/iOS Home Screen storage context, verified old import and upgrade, new local export, external save/reselection and strict TMA import. It is not evidence of provenance or a general legacy/PPJ fallback. The physical iOS/Android file/build matrix and FR-57/NFR-28 remain separate evidence gates.
