# Независимая rubric/source/UX-проверка дополнительного browser export

Дата: 2026-11-05. Проверены обновлённые AD-30 и раздел «Дополнительный Web/PWA export для переноса» в `telegram-portable-v1-disposition-2026-11-04.md` против актуальных SPEC CAP-10, `telegram-platform-and-compatibility-contract.md`, `project-and-backup-contract.md` §1.4, UX `EXPERIENCE.md` и PRD FR-44/FR-57; статически сверены существующие browser и Telegram composition. Канонические источники этой проверкой не изменялись.

## Вердикт: PASS ДЛЯ АРХИТЕКТУРНОЙ ДИСПОЗИЦИИ; SOURCE HANDOFF, IMPLEMENTATION И EVIDENCE PENDING

Архитектурное решение отражает конкретное пользовательское направление: отдельный явный экспорт рядом с прежним на двух указанных поверхностях. Оно не заменяет существующий browser exporter и не заявляет полную совместимость или восстановление. Пока review выполнялся, UX и SPEC owners добавили соответствующие условные тексты; disposition уточнена и теперь фиксирует внесённые тексты и открытые взаимную сверку и readiness gate. Этот review не является readiness verdict, разрешением поставки или physical acceptance.

## Сверка sources и применимости

- UX и SPEC параллельно внесли условные тексты для нового действия (`EXPERIENCE.md:389–425`, SPEC CAP-10 и platform companion); архитектурный handoff уточнён после первоначального замечания и правильно сохраняет pending source reconciliation и применимый gate. Draft не является поставленным действием.
- AD-30:860 и disposition:142–158 отделяют новый registered V1 writer от прежнего browser exporter, default feasibility, History и DB. Старый экспорт и его проверка FR-44 для **всех** non-corrupt Durable Projects не замещаются доказательством только зарегистрированного V1-подмножества. `project-and-backup-contract.md:260–264` сохраняет полное множество для replacement gate.
- CAP-10, platform companion и `EXPERIENCE.md` уже содержат отдельные формулировки предполагаемого действия, но их статусы требуют дальнейшего source/readiness согласования. Конкретный пользовательский выбор названия и расположения не нужно превращать в требование повторного разрешения; следует выполнить необходимые workflow/source handoffs и не заявлять, что реализации разрешены одним архитектурным текстом.
- Для source reconciliation остаётся проследить оба entry points — действие выбранного Project в списке и меню открытого editor — вместе с copy, объяснением недоступности, cancellation, проверкой сохранённой версии и UXF-8. Историческое единственное видимое действие не должно молча переключаться на другой codec.
- `AppShell.tsx:6190–6196,7278–7283` сейчас направляет прежние кнопки к `exportProjectTransfer`; в `production-app.ts` registered writer не подключён как новый browser action. `ExportRuntimePortableBackupUseCase` используется Telegram composition; наличие кода writer не доказывает новый browser маршрут, pinned-store wiring или его тесты.
- Дополнительный export применим только к конкретной проверенной Durable Revision, а не к pending candidate: RecoveryDraft имеет отдельный статус и не называется complete backup. При конкурентной редакции/delete/cleanup необходимо доказать exact ownership неизменяемого snapshot и сохранность pinned ресурсов до завершения; ID или JSON checksum не отличают все structured состояния, например `-0` и own-undefined.
- Новый writer должен независимо прочитать каждый исходный case-sensitive resource key, подтвердить pin/root, точные bytes, длину и все 256 бит SHA, сохранить остальные domain, limits, security и applicable GLB checks. `resources.read`, browse cache, возможность сформировать ZIP или selector не доказывают полноценный Portable Backup. Отказ при неподходящем, но читаемом Project не означает доказанной corruption.
- Registered V1-wire и текущий V1 consumer имеют ограниченную grammar: непредставимые historical snapshots и non-index array properties остаются в исходном контексте, а прежние способы не объявляются заменёнными. Сам факт строки «healthy Durable V1» в disposition охватывает уже ограниченную grammar и не является доказательством поддержки всех non-corrupt Durable Projects по FR-44.
- Отдельные направления matrix сформулированы корректно: Web → TMA требует проверенного actual V1 файла и strict import; TMA → Web дополнительно ограничен exact представимостью старым browser backup. V1 `-0`, own-undefined или uppercase alias могут быть допустимы в первом направлении и отвергнуты при обратном ingress. Успех export или Telegram import не доказывает универсального roundtrip.
- Указанный old-Web empty legacy → новый registered export → strict TMA import — кандидат для конкретного файла, а не уже работающий recovery. Требуются доказанный исходный storage context, сохранность source и его hash, конкретная безопасная пара версий, фактическое внешнее сохранение/повторный выбор и сравнение геометрии, metadata, hosts и exact resources. Без этого FR-57 и sole-copy recovery остаются pending; происхождение файла не удостоверяется.
- Пользовательские состояния должны различать подготовку, явную отмену, непредставимый snapshot, отсутствующие ресурсы, недоступную выдачу и неопределённое внешнее сохранение. Появление bytes или вызов picker не доказывает, что файл сохранён за пределами приложения; source, текущая история и данные не меняются, server upload не вводится.
- До compatibility/release claims нужны исполняемые обе UI-точки на телефоне, прежний export/PWA regression, real GLB и exact resources, empty/open/room project, крайние structured states, отказ по integrity/limits, race/cancel и bounded memory, а также реальные внешние файлы и физические client pairs. Эти пункты — требуемое будущее evidence, а не результаты этого review.
