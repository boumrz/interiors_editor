# Граница и исходные данные

AD-30 определяет этот контракт; владелец SPEC зарегистрировал PPJ-A1, V1-wire и V1-legacy. Readiness разрешил локальную реализацию S3/10.4 и независимых file seams 10.5 при указанных зависимостях. Регистрация и локальный READY не доказывают полную реализацию, совместимость файлов, physical acceptance или release. Канонический PPJ-A1 `interiors.project/alpha-1@1` и его закрытые raw/Unicode/AST/schema/domain rules остаются неизменными. Старый exporter использует тот же manifest selector для другого V1 DTO без root selector; старый importer не подключает полный PPJ staged ingress. Одинаковый label не доказывает PPJ compliance или происхождение файла.

Project V1 в текущем IDB хранится двумя формами: structured-clone `candidate.project` и `Revision.serializedProject`/checksum. `canonicalProjectSerializer`, checksum, schema 1, DB names и recovery остаются неизменными. Source revision/Project и исходный файл при export/import никогда не изменяются. Wire строится из **проверенного durable candidate.project**, а не только из строки revision: checksum проверяется по точной сохранённой строке и existing repository semantics. Успешный import создаёт новую V1 Revision обычным serializer после создания нового Project ID; source bytes не перезаписываются.

Под «healthy Durable V1» ниже понимается читаемый current candidate с принадлежащими ему checksum-valid revision, моделью, соответствующей закрытой V1 grammar ниже, и поддерживаемой текущей domain geometry/host semantics, а также точно присутствующими и hash-valid ресурсами в пределах policy. Один `DurableProjectRepository.isReadable` этого не доказывает: его structural guard и JSON-semantic equality принимают дополнительные случаи и не проверяют BackupFeasibility/полную domain/resource integrity. Например, guard для `colorVariantId` использует `String(value)` и может принять вложенные одноэлементные массивы вместо V1 string; ниже явно регистрируется безопасный ограниченный вариант, без coercion при сохранении. Кроме того, storage может содержать non-index properties у массивов, которые JSON serializer/equality игнорирует. Нельзя по одному `isReadable` объявлять такие данные повреждёнными или утверждать, что эта grammar их целиком переносит: источник сохраняется; если sole-copy такого snapshot не имеет проверенного exact recovery path, соответствующая совместимость и её Product/source-owner disposition остаются открытыми. Recovery bytes остаются доступными по существующему контракту.

# Три закрытые строки выбора

| Manifest pair; root Project member | Строка и действие |
|---|---|
| `interiors.project/alpha-1@1`; root `projectSchemaId="interiors.project/alpha-1"`, root `schemaVersion` raw `1` | Только существующий PPJ-A1 staged ingress, без fallback. |
| `interiors.project/alpha-1@1`; root `projectSchemaId` отсутствует, root `schemaVersion` raw `1` | Только зарегистрированная `V1-legacy` grammar ниже, с обязательным PPJ-disjoint witness. Это синтаксическое совпадение, не авторство/подлинность. |
| `interiors.project/runtime-v1-wire@1`; root `projectSchemaId="interiors.project/runtime-v1-wire"`, root `schemaVersion` raw `1` | Только `V1-wire` grammar ниже. |

Null/empty/wrong/duplicate selector, mismatched source ID/pair, другой registered/unregistered selector или версия не переключают decoder; по результату положенной стадии — `BACKUP_SCHEMA_UNREADABLE`. Malformed manifest — `BACKUP_MANIFEST_INVALID`. Новая строка и legacy exception зарегистрированы владельцем SPEC в `portable-backup-ingress-registry.md`; это не доказывает совместимость конкретного файла или завершение реализации.

V1-legacy допускается лишь после полного closed V1 decode и byte equality исходного Project member с историческим `serializeProjectCanonically` для decoded объекта. Дополнительно обязателен хотя бы один зарегистрированный **PPJ-disjoint witness** в валидном V1 record: (1) item с `anchorClass=floor|wall`; (2) definition с `format=glb` и `resourceHash`; (3) Room с обычным `type`; (4) Room без обязательного PPJ `name`; либо (5) Room с `faceFingerprint`, не являющимся lowercase SHA-256 из 64 hex. Каждое такое поле/отсутствие несовместимо с закрытой PPJ record grammar. Условие оценивается по точным raw decoded values после V1 validation, не по предполагаемому производителю. Если witness отсутствует — `BACKUP_SCHEMA_UNREADABLE` и сохранённый исходник, даже если конкретный PPJ checker отверг бы документ позднее. Существующий selector-only classifier не является полной PPJ validation и не используется для доказательства disjointness. PPJ с обязательным root selector по-прежнему идёт только в PPJ decoder; fallback отсутствует. Root absence и checksum не удостоверяют происхождение/автора. Пустой old V1 без witness консервативно ambiguous.

FR-57 разрешает отказ по неоднозначности при сохранении файла и честном сообщении, но существование старого Web/PWA не доказывает recovery. Кандидат evidence-пути: изолированный неизменённый старый build `ccdd13662cdca379` принимает **копию** конкретного файла своим V1 importer; сохранённый Project открывается после проверенного обновления того же local context до совместимого нового browser build; экспортируется V1-wire, затем импортируется на целевой поверхности с полным сравнением geometry, metadata, hosts и exact resource bytes. Должны быть доказаны целостность release/DB migration, source archive SHA до/после и доступный пользователю путь на конкретных версиях/клиентах; никакого upload. Пока такой путь не проверен, он только кандидат. Для sole-copy без него восстановление и приёмка затронутой совместимости pending; если проверка подтвердит отсутствие пути, Product Owner решает вопрос FR-57 об обязательной гарантии/условиях ограничения. Автоматический guess и выдуманное согласие не допускаются.

# V1-wire: общие правила записи

Это отдельный JSON DTO, а не IDB serialization. Root содержит первым `projectSchemaId`, затем следующие поля V1: `schemaVersion`, `projectId`, `name`, `createdAt`, `updatedAt`, `lifecycle`, `level`, `assetInstances`, `assetDefinitionRefs`. Все поля закрыты; duplicate/unknown key, null вместо обязательного значения, любые unregistered record/Command/History/renderer fields отклоняются. Сохраняются array order, optional own-property presence и порядок nested V1 record keys; root и level writer создаёт в фиксированном порядке существующего serializer, независимо от insertion order source object. Это не утверждает raw-object identity порядка root/level; исходный object/revision bytes остаются нетронутыми. Новый selector и переносимые manifest fields не становятся частью IDB Project. Writer использует stable ECMAScript own-property ordering nested records исходного snapshot; reader не сортирует V1 records и сохраняет порядок. UTF-8 archive bytes валидны, BOM запрещён.

**V1String** — непустая JS string 1..256 UTF-16 code units, exact code-unit equality, без trim, Unicode normalization или case fold, если конкретная строка не ограничена ниже. Scalar-only строка записывается JSON string; string с хотя бы одним непарным surrogate записывается только как точный closed object `{"utf16be":"<base64url-no-padding>"}`: big-endian 16-bit code units, canonical base64url без padding, 2..512 исходных bytes, декодированный результат действительно содержит хотя бы один непарный surrogate. Запрещены extra keys, malformed/noncanonical base64 и wrapper для scalar строки. Никакой U+FFFD замены. Такой object допустим **только** на указанных V1String pointers; JSON keys и discriminator values ASCII. На import восстанавливаются точные code units и own-property/array order. V1 legacy допускает canonical JSON.stringify escapes `\\ud800`–`\\udfff` как V1 code units на V1String pointers; отдельный ограниченный V1 raw parser сохраняет их, не меняя PPJ AST-R1 scalar rejection. `project.name` дополнительно обязан быть Unicode scalar и `name.trim()===name`. Other V1String поля сохраняют допустимые whitespace/C0 и lone surrogate.

**OptionalUndefined** — closed object `{"undefined":true}` только на указанных optional pointers, если own property существует со значением `undefined`. Отсутствующий key остаётся отсутствующим; нормальное значение не использует marker. Legacy JSON уже опустил own-undefined и его нельзя восстановить. Любой marker в required поле, array или неизвестном pointer — unreadable.

**Integer** — JSON number raw lexeme `-0` либо `-?(0|[1-9][0-9]*)`, safe integer и в указанном диапазоне; `-0` разрешён только где 0 входит в диапазон и восстанавливается как IEEE-754 negative zero. Никаких fractional/exponent/string/unsafe integers. `schemaVersion` — только raw `1`. **FiniteNumber** — JSON number, finite binary64; raw `-0` сохраняется, все остальные значения имеют точную canonical ECMAScript JSON.stringify round-trip лексему. Это применяется только к optional `yawRadians`; `0.5` допустимо. NaN/Infinity и несоответствующие aliases запрещены.

На export `Object.is(value,-0)` задаёт raw token `-0` на каждом допустимом numeric pointer, включая x/z, offsets, elevation, sill, `yawStep` и `yawRadians`; обычный `JSON.stringify` целого DTO запрещён, поскольку он стирает знак. На import raw `-0` становится `-0` в `candidate.project` и сохраняется structured-clone в IDB; прежний serializer пишет `0` в новой revision string и считает прежний checksum. Проверить `Object.is` после reopen. В legacy file `0` уже не содержит информацию о прежнем -0: импортировать +0, не выдумывая исторический знак. Source IDB object и revision string/checksum остаются нетронутыми. Опираемся на [WHATWG structured serialization](https://html.spec.whatwg.org/multipage/structured-data.html#structuredserializeinternal); поведение целевых WebView всё равно требует evidence.

# Закрытая V1 record grammar

`S` ниже означает V1String, `I[a,b]` включительный Integer; все object keys кроме перечисленных запрещены. Optional поле может отсутствовать, иметь указанное значение или OptionalUndefined. Верхние пределы collections: vertices 600, walls 300, rooms 50, openings 200, items 250, definitions 250.

| Record | Required: key → value | Optional: key → value |
|---|---|---|
| root | `projectSchemaId` exact wire selector; `schemaVersion` raw 1; `projectId:S`; `name:S` + scalar/trim equality; `createdAt`, `updatedAt`: valid JS ISO instant; `lifecycle:"active"`; `level`, `assetInstances`, `assetDefinitionRefs` | — |
| level | `levelId:S`; `vertices`, `wallSegments`, `rooms`, `openings`: arrays соответствующих records | — |
| vertex | `vertexId:S`; `xMm`, `zMm:I[-100000,100000]` | — |
| wall | `wallSegmentId`, `startVertexId`, `endVertexId:S`; `thicknessMm:I[20,1000]` | — |
| room | `roomId`, `faceFingerprint:S`; `heightMm:I[500,10000]` | `name:S`; `type` = bathroom/bedroom/hallway/kitchen/living-room/office/other/storage |
| opening | `openingId`, `wallSegmentId:S`; `offsetMm:I[0,100000]`; `widthMm:I[1,100000]`; `heightMm:I[1,10000]`; `sillMm:I[0,10000]`; `kind=Door|Window` | Door only `swingSide=left|right`; Window имеет право только на отсутствующий либо own-undefined key |
| floor item | `assetInstanceId`, `roomId`, `label:S`; `anchorClass:"floor"`; `xMm`, `zMm:I[-100000,100000]`; `widthMm`, `depthMm`, `heightMm:I[1,100000]`; `color` = `#[0-9a-fA-F]{6}` | `assetDefinitionId:S`; `colorVariantId:VariantValue` по таблице ниже; `elevationMm:I[0,0]`; `locked:true`; `yawRadians:FiniteNumber`; `yawStep:I[0,7]` |
| wall item | `assetInstanceId`, `wallSegmentId`, `label:S`; `anchorClass:"wall"`; `side=left|right`; `offsetMm:I[0,100000]`; `elevationMm:I[0,10000]`; `widthMm`, `depthMm:I[1,100000]`; `heightMm:I[1,10000]`; `color` как выше | `assetDefinitionId:S`; `colorVariantId:VariantValue` по таблице; `locked:true` |
| definition | `assetDefinitionId`, `displayName:S`; `byteLength:I[1,9007199254740991]`; `widthMm`, `depthMm`, `heightMm:I[1,100000]`; `format:"glb"`; `resourceHash` = 64 ASCII hex digits, case preserved | `source`, `catalogAssetId`, `catalogEnvelopeHash`, `catalogVersion` как quartet ниже |

Для legacy root отсутствует `projectSchemaId`; marker wrappers в legacy не допускаются: принимаются только байты старого JSON.stringify, в котором optional undefined уже опущен и -0 уже превращён в 0. В V1-wire root `schemaVersion` и scalar discriminators не принимают wrappers; optional marker не разрешает некорректный обычный value. JS ISO instant означает строку, для которой `new Date(s).toISOString()===s`, включая поддерживаемые extended years; parse error недопустим. Catalog quartet: либо все четыре отсутствуют/own-undefined, либо все имеют обычные значения: `source="CatalogVersion"`, `catalogAssetId` и `catalogVersion` — S и равны собственному trim, `catalogEnvelopeHash` — ровно 64 ASCII hex, case сохранён. Смешанное наличие обычных и undefined значений отвергается.

|---|---|
| `alpha-warm-wood` | `#a76a3b` |
| `alpha-blue` | `#416b91` |
| `alpha-violet` | `#716796` |
| `alpha-walnut` | `#8c6e4c` |
| `alpha-terracotta` | `#835a45` |
| `alpha-forest` | `#536d62` |
| `alpha-berry` | `#8a4f54` |

**VariantValue** — строковый variant ID из таблицы либо одноэлементный JSON array `[VariantValue]`, рекурсивно, пока общая глубина Project JSON не превышает 8. Терминальное значение обязано быть одной строкой из таблицы, без null, holes, дополнительных элементов или object; проверка цвета использует terminal ID, но import/export сохраняет точную вложенную форму, не заменяя её строкой. Это закрытая grammar фактически принимаемого текущим guard `String(value)`, а не новая UI capability. Readable исторические values глубже этого безопасного envelope сохраняются в старом контексте; support/recovery такой sole copy не считается доказанным.

Идентификаторы сравниваются по exact UTF-16 code units; все ID в своей коллекции уникальны; coordinates vertices уникальны математически (+0 и -0 совпадают). Wall endpoints существуют и различны; opening host существует; floor item имеет существующий Room, wall item — существующую Wall; optional definition ID ссылается на definition. При наличии обычного `colorVariantId` `assetDefinitionId` отсутствует или own-undefined, color совпадает case-sensitively. Definition IDs и resourceHash уникальны по точному написанию; hash-файлы дополнительно проверяются по 256 битам. Все domain topology, collision/host и resource conditions проверяются после closed shape, до publication. `yawStep` если есть — V1 authority; если отсутствует, существующая read-only projection может использовать исторический yaw. Сам `yawRadians` и его own presence не переписываются и не превращаются в округлённый step. Новых свободных углов как команды это не вводит.

### Read-only проверка legacy orientation

`FiniteNumber` в wire по-прежнему принимает **любой конечный binary64** `yawRadians`, включая ±`Number.MAX_VALUE`; этот случай не превращается в ошибку closed shape или `BACKUP_SCHEMA_UNREADABLE`. После schema и policy limits, на domain/placement стадии whole-project validator сначала для **каждого** сохранённого floor item вызывает действующую disposable `yawRadiansFor` с его исходными `yawStep` и `yawRadians`, без `continuousYaw`. `yawStep` при наличии имеет приоритет; отсутствие обоих даёт существующую проекцию 0. Если derived yaw не конечен, вернуть существующий domain reason `INVALID_DIMENSION` до collision, staging/pin или publication; это не новый codec reason и не утверждение, что текущий production importer уже выполняет эту проверку. Source Project, все own fields и исходные file/IDB bytes остаются нетронутыми; доступны только действительно проверенные пути сохранения/восстановления, без обещания автоматической repair.

Только после успешной предварительной проверки всех floor projections validator применяет действующий `assessParametricFloorItemPlacement`: его интерфейс принимает `yawStep`, поэтому временный assessment input получает step через существующую `rotationStepForYawRadians` от конечного derived yaw и исключает сам item по `assetInstanceId`. Этот step и derived yaw — только input проверки; исходный `yawRadians`, наличие/отсутствие собственного `yawStep` и durable object не изменяются. Это также не разрешает другим проверкам игнорировать валидные collision warnings или подменять их новым поведением. Для `0.5` и ±`1e100` сохраняется текущая конечная проекция; ±`Number.MAX_VALUE` без `yawStep` при текущем делении переполняется до Infinity и ведёт к нечисловой derived projection. Тот же source с допустимым `yawStep` использует step и не отвергается из-за неиспользуемого legacy yaw. Проверки исходного/derived значения и reason precedence обязательны для обоих signs, отсутствующего/заданного step и одновременной более ранней schema/policy ошибки.

Нового core projection repair для этого отказа не требуется. Если позже потребуется поддержать импорт сейчас невыразимой domain projection, отдельное изменение обязано доказать сохранение **всех ранее конечных** проекций, исходных values и source bytes и пройти свой source/gate; округление в persisted `yawStep`, silent default или изменение finite wire grammar не являются таким доказательством.

# Ограниченный parser и вместимость

PPJ parser/AST-R1 и его 4 MiB scalar boundary не меняются. Новый V1-only scanner строго проверяет raw UTF-8, JSON syntax, duplicate keys, глубину ≤8, ≤65536 value nodes, ≤49152 aggregate members и ≤32 в object, ≤24576 aggregate array elements и ≤1024 в array, ≤128 UTF-8 bytes reconstructed RFC 6901 pointer, ≤64 raw bytes на numeric token, ≤4 KiB decoded charge на string, ≤16 MiB retained metadata и ≤10 MiB Project bytes. Root pointer пустой; хранятся parent/source-span links, а полные pointers реконструируются только по запросу. Для V1 отдельных записей decoded-code-unit charge ≤8 MiB: каждая восстановленная UTF-16 code unit учитывается как 3 bytes, плюс фактические ASCII bytes имён keys/литералов; одновременно удерживаемый base64 payload wrapper также включается в charge, без повторного копирования raw backing. Декодирование одного wrapper добавляет не более 512 transient bytes. Для malformed UTF-8/JSON, duplicate key и capacity faults сохраняется порядок событий AST-R1: malformed/duplicate побеждает capacity на том же событии, более ранняя capacity ошибка не переклассифицируется. Лимит не применяется вместо PPJ AST-R1. Scanner проверяет wrapper canonicality/size до materialization. Raw manifest и checksum ledger имеют bounded parser с теми же duplicate/UTF-8 проверками; `sourceProjectId` в V1-wire — V1String с той же wrapper grammar, а не предположение о scalar ID. В legacy manifest sourceProjectId — историческая JSON string с допускаемыми V1 escaped UTF-16 code units.

Размерный bound для V1 по закрытой grammar, включая ограниченный VariantValue: максимум 4055 свободных строковых значений по 256 UTF-16 units; ≤6 bytes на unit для canonical JSON либо ≤683 bytes для wrapper, то есть ≤6,228,480 bytes. Максимум 1652 record objects включая root/level; бюджет 1024 ASCII bytes на record покрывает все закрытые keys, punctuation, фиксированные enums, finite number lexemes, optional markers и `projectSchemaId`: ≤1,691,648 bytes. Дополнительные одноэлементные VariantValue arrays глубиной до 8 входят в 1024-byte budget соответствующего item record. Сумма ≤7,920,128 <10,485,760. Decoded charge ≤4055×256×3 +1652×1024 +4055×683 =7,575,453 <8,388,608, включая одновременно удерживаемые base64 payloads. Верхний счёт members: root/level ≤15; vertices 600×3; walls 300×4; rooms 50×5; openings 200×8; items 250×16; definitions 250×12: всего ≤11,865 базовых members. Добавить не более 4,055 members для string wrappers и 2,800 для optional-undefined markers: ≤18,720 <49,152. Array elements ≤1,650 основных records + 250×5 singleton variant layers =2,900 <24,576. Value nodes ≤1 root +18,720 member values +2,900 array elements =21,621 <65,536. При AST-R1 formula `48×nodes + 32×members + 8×arrayElements + 16×pointerLinks + decodedCharge + numericLexemeBytes + 8,320` и pointerLinks≤21,621, numericLexemeBytes≤1,691,648, плюс 512 transient bytes получаем ≤11,281,917 <16,777,216. Эти оценки намеренно допускают одновременно несовместимые максимумы. Реализация предоставляет проверяемый worst-case fixture и счётчик; если цифра не подтверждается, rollout блокируется, а не повышает PPJ limits.

Resource budget существующей feasibility: ≤250 V1 definitions, каждый exact resource ≤50 MiB, суммарно по refs ≤180 MiB; ≤190 MiB container и ≤280 MiB unpacked. Даже без compression верхняя оценка 180 MiB + 7,920,128 + 4096 + 250×1024 = 196,923,904 < 199,229,440 bytes. Зарезервированные 1024 bytes на resource включают manifest/ledger entries, два ZIP headers и ASCII path; 4096 покрывают fixed manifest/ledger, source ID до 256 UTF-16 units (до 1538 bytes при scalar control escapes, либо до 697 bytes в JSON wrapper (683 base64url chars и 14 bytes object syntax)), Project headers и ZIP end record. ZIP writer использует single-disk STORE, ASCII имена, заранее известные CRC/lengths, без ZIP64, extra fields, data descriptors и archive/entry comments; другие ZIP writer modes требуют новой оценки. При этих caps ZIP64 не нужен. Фактические точные archive lengths и caps проверяются до выдачи, без молчаливого уменьшения проекта. Proof и тест включают максимальные escaped strings, wrappers, `undefined`, -0 и все caps. Это расчёт проектной границы, не факт уже выполненных тестов/implementation.

# Envelope и ресурсы

Для V1-wire `manifest.json` — закрытый object ровно с `backupFormat="interiors-portable-backup"`, `backupFormatVersion=1`, `canonicalProjectPath="project/project.json"`, `complete=true`, `createdAt` valid JS ISO, `entries`, `projectSchemaId="interiors.project/runtime-v1-wire"`, `projectSchemaVersion=1`, `requiredCapabilities=[]`, `resources`, `sourceProjectId:V1String`. `entries` содержит ровно один Project entry `{byteLength,mediaType:"application/json",path:"project/project.json",sha256}` и по одному entry на каждый **различный 256-bit resource digest**, с `path="custom/<lowercase digest>.glb"`, `mediaType="model/gltf-binary"`, positive length и lowercase sha256. Digests — ровно 64 hex, computed over exact bytes. `resources` содержит ровно одну `{path,resourceHash}` mapping на каждый V1 definition, где `resourceHash` сохраняет исходное hex-написание; `path` соответствует ASCII-lowercase представлению тех же 256 бит. Несколько исходных references, отличающихся только регистром, могут ссылаться на одну entry лишь после независимой проверки точных bytes каждого исходного resource key, равенства byteLength и binary digest. Все исходные keys и их spelling восстанавливаются в локальном store; новые resource hashes не подменяются. Для этой V1 строки сверка валидности — равенство 256 digest bits после ASCII hex decode, а не требование, чтобы исходное V1 имя hash уже было lowercase; adapter/policy обязан сохранять исходное написание и подтверждать точные bytes для каждого key. Это не уменьшает проверку hash и не меняет PPJ grammar. `entries` и `resources` содержат уникальные соответственно paths и исходные resourceHash, связи совпадают с definitions; entries сортируются по ASCII path после Project, resources — по exact ASCII resourceHash. Неполные, dangling или лишние ссылки отвергаются.

`checksums.json` закрыт: `{algorithm:"sha-256",entries:[{path,sha256}]}`; entry paths и hashes точно равны manifest entries. Архив имеет ровно `{manifest.json,checksums.json,project/project.json}` плюс уникальные manifest resource paths; raw filename/path grammar, duplicate, traversal, compression, size и checksum правила действующего registry сохраняются. Новый V1 decoder не выдаёт `catalog/*`, textures или неподдержанные resources за проверенный формат. User-owned bytes не upload-ятся.

## Техническая GLB-проверка и действующая admission policy

Project/backup envelope допускает до **50 MiB на resource и 180 MiB по исходным references**, но это не означает, что любой 50-MiB GLB допустим к admission. Текущий `preflightStaticGlbImport` проверяет hard **25 MiB** до остальных проверок и используется custom import, catalog media и `PortableBackupReadRenderSmokeCheck`; исторический browser smoke сравнивал lowercase SHA string с исходным ключом буквально; семантика текущего рабочего дерева требует сверки с baseline ниже. Контракт `asset-import-contract.md` §3 владеет provisional custom-GLB limits и при пересечении требует меньший предел. Этот документ не меняет эту policy.

Для будущего Telegram-scoped V1-portable route допустимо выделить существующие общие static GLB structure/security preflight checks в ограниченную read-only seam с **явно выбранным portable envelope byte cap ≤50 MiB**; это только техническая проверка существующих referenced bytes, не самостоятельное право на регистрацию/новую custom admission. Default/public `preflightStaticGlbImport`, browser/PWA existing smoke, custom UI/import/placement/library и catalog media оставляют прежний hard 25 MiB, порядок проверок и reason codes. Новый seam выбирается только доверенной Telegram portable composition после распознавания зарегистрированной V1 строки, не автоматически по GLB bytes или заявленному файлом флагу. До любого GLB/JSON parse выбираются и проверяются **все применимые byte guards**: для недоверенной custom admission сначала действует 25-MiB hard, для envelope — максимум 50 MiB; если применимость не установлена, использовать более строгий предел. Только после успешных guards вызывается portable seam; все остальные действующие checks сохраняются: GLB v2 и chunk bounds, reject external/data URI, animation/skins/cameras и unsupported extensions, а также прежние geometry/node/material/texture и decoded-pixel budgets. Перенос большого byte cap не повышает другие limits, не разрешает новые форматы и не удаляет отдельные downstream security/decoded-resource/no-network проверки.

`PortableBackupReadRenderSmokeCheck` сегодня делает structural preflight, точный размер/SHA и `projectRectangularRoomForWebGl` для Project с Rooms; это не доказательство фактического GLB decode, GPU rendering или device security. Новый **явно выбранный Telegram V1-portable smoke** сохраняет ту же clean disposable Project geometry semantics и все проверки при соответствующем 50-MiB envelope cap, не заменяя последующие обязательные decoded/no-network/render проверки. Успех envelope/smoke сам по себе не обходит более строгую применимую admission policy. Для нового custom AssetDefinition/новой reference, включая создание Project из недоверенного backup, до решения владельца действуют применимые 25-MiB custom правила; сам label в файле или hash не доказывают прежде разрешённую admission. Exact repair уже существующего ожидаемого hash без изменения Project reference — отдельный recovery route и не является новым размещением, но не доказывает допустимость parse/decode/render GLB 25–50 MiB и не освобождается от применимой security policy. Если требуется подтвердить 25–50 MiB custom resource при восстановлении/переносе, SPEC/asset-policy owner должен определить применимость 25-MiB hard к parse/decode и admission в этом конкретном маршруте; до такого решения не делать 50-MiB smoke достаточным основанием для Durable publication. Это source-owner handoff, не изменение licensing, Product Limits или Alpha+ scope.

Для V1-portable alias route проверка каждого исходного `resourceHash` начинается со строгой формы ровно 64 ASCII hex, затем сравнивает ровно 256 bits с SHA-256 **каждого** resource, прочитанного по исходному case-sensitive ключу; отдельно проверяются указанная длина и сами точные bytes. Несколько case aliases допускают одну archive entry только после независимой проверки каждого ключа, сравнения bytes и длины между alias copies. Все исходные raw keys восстанавливаются, не нормализуются и не заменяются fuzzy lookup; PPJ lowercase grammar не меняется. До publication и повторного export обеспечить ту же проверку по всей цепочке decoder → smoke → staging/pin → Durable/reopen → Project-owned hydration/3D → export → exact repair/recovery и scoped feasibility: одной замены smoke недостаточно: исторические `backup-feasibility-policy`, `project-controller` integrity/repair, `project-recovery`, import/export и `AppShell` hydration использовали raw string SHA comparison, а hydration вызывает default 25-MiB preflight. Отличающуюся V1 alias semantics выбирать только в trusted Telegram scope и не расширять старые browser пути; соответствие текущего дерева baseline подлежит отдельной проверке ниже. Совместимость подтверждается для каждого уже referenced Project resource, а не включается по непроверенному флагу или утверждению исходного файла; если reopen/hydration/repair не доказаны, publication не объявляется безопасной. Aggregate 180 MiB считать по исходным references **до** archive dedup. Missing alias, неверная длина/hash, несоответствие bytes либо conflict в destination store дают отказ без partial Project или перезаписи существующих bytes.

Операция учитывает peak memory archive, распакованных bytes, копий ресурсов и decoder/GPU buffers; bounded staging и cancellation не должны незаметно дублировать весь payload. Если бюджет текущего устройства не позволяет безопасно продолжить, операция явно завершается без partial publication/удаления источника; это не изменение Project Limits и не доказательство повреждения Project.

Evidence для будущей реализации: 25 MiB и 25 MiB+1 на прежних custom/catalog call sites; portable technical seam на 25 MiB+1, 50 MiB и 50 MiB+1, с отдельной проверкой действующей admission policy; aggregate >180 MiB до materialization/publication; lowercase/uppercase/mixed-case aliases, invalid hex, отсутствующий alias, несовпадение байтов/длины и conflict destination; malformed GLB, URI, animation/skin/camera, extensions, geometry и texture budgets; clean projection, cancellation/crash и exact reopen/export/repair. Ни одна строка здесь не является фактическим запуском тестов, подтверждением 50-MiB GLB admission или физическим device evidence.

## Format-specific BackupFeasibility перед publication

Текущая `SessionRetentionProjectRepository` вызывает `assessBackupFeasibility` для `publish`, `publishNextRevision` и history transition; существующая проверка применяет PPJ AST-R1 к **internal** `Revision.serializedProject`. Это не совпадает с зарегистрированной V1-wire grammar и может ошибочно отказать допустимому V1 из-за PPJ scalar rules. Для trusted Telegram composition допустим application-owned `BackupFeasibilityPolicyPort`: shared controller factory передаёт один выбранный V1 adapter в session-retention wrapper; соответствующие активные use cases с собственным предварительным вызовом той же feasibility policy (в текущем дереве `CreateCustomGlbFloorItemUseCase` после pin) получают этот **же** adapter. Если direct caller не переведён на согласованную policy, его V1 path остаётся явно ограниченным, не bypass-ится. Это не повышает Alpha+ scope и не меняет 25-MiB custom admission/preflight. Domain/application зависят от порта, не от concrete portable codec.

Только доверенная platform composition выбирает зарегистрированный V1 writer и соответствующий feasibility adapter, не пользовательский selector/flag и не содержимое импортированного файла. После выбора immutable scope и создания Telegram repository composition связывает **один и тот же** `repository.resources` этого scope с writer/exporter и policy, а затем передаёт их в shared controller; нельзя конструировать writer заранее с чужим store или подставлять browser store. Resource port и checksum для Telegram обязательны: существующий optional resource-port shortcut без проверки bytes в этом пути запрещён. Отсутствующая policy/encoder/store, неподтверждённый scope, исключение или несовместимость → fail closed, без молчаливого выбора прежнего PPJ checker либо permissive fallback. Browser/PWA composition, default feasibility и прежние exporter/decoder сохраняются; отдельная проверка представимости применяется только к новому явно выбранному browser ingress ниже.

V1 adapter проверяет **тот же защищённый immutable candidate.project snapshot**, который передаётся для publication: выполняет registered `encodeRuntimeV1Project` и его bounded V1 grammar, затем действующую whole-Project/domain policy (включая более строгий лимит **100 definitions**, несмотря на structural grammar до 250). Внутренний `Revision.serializedProject`, его checksum, PPJ grammar и PPJ AST-R1 не меняются; PPJ AST не применяется к V1 внутренней строке как подмена проверки wire. Единого checksum internal JSON недостаточно, чтобы установить равенство V1 snapshot: он не различает `-0`/`0` и own-undefined/отсутствие. Snapshot получает exclusive ownership до первого async шага и используется для обеих проверок и fenced publication; иначе надо повторно доказать exact V1 wire-state equality в commit boundary и отказать при расхождении.

Общие численные hard caps и проверка ресурсов не ослабляются: измеряются фактические bytes V1 Project member и его зарегистрированного STORE envelope, manifest и ledger либо используется доказанная V1 верхняя оценка **4096 fixed bytes + 1024 на исходный resource reference**, с теми же лимитами 10 MiB Project, 50 MiB/resource, 180 MiB по исходным case-sensitive keys до dedup, 190 MiB container, 280 MiB unpacked и действующими limits/counts. Прежняя browser estimate с fixed 2048 bytes не доказывает V1 envelope; её нельзя молча применить к новому формату. Для каждого original key этого repository независимо читать pinned exact bytes, проверять declared size и все 256 bits SHA; одинаковые digest aliases требуют byte-for-byte equality и остаются отдельными keys. Нет чтения из browse cache, отсутствующий/corrupt ресурс не превращается в success.

Feasibility не является ни pin, ни атомарной публикацией и не заменяет `SessionRetentionPolicy` для current/undo/redo roots: после неё сохраняются те же history admission и fenced AD-26 transaction с повторной проверкой scope/generation, expected base, writer fence, exact resource roots и candidate identity; race/cancel/failure не меняет Durable Revision и не ломает redo. Выбор новой scoped policy не должен незаметно лишать уже допустимые session History entries путей Undo/Redo; при history-only corruption применяются лишь exact repair либо явный `DiscardSessionHistory` при healthy current Project по AD-4, не автоматическая очистка. Domain `INVALID_DIMENSION` и прочие ранее определённые domain outcomes не превращаются в codec/schema errors; ошибки feasibility отображаются через стабильные policy/persistence outcomes, без ложного success. Обязательные будущие проверки: V1 lone-surrogate/own-undefined/-0 проходят именно V1 policy при сохранении внутреннего checksum; непредставимый или за пределами policy candidate не публикуется; browser default и прежние browser semantics сохраняются; 100/101 definitions, exact wire/metadata/container boundary, отсутствие/подмена scope store, каждый mixed-case alias и mismatch, прежние custom 25 MiB, history redo roots и delayed feasibility против takeover/cleanup. Это архитектурный seam, не evidence завершённой реализации, physical acceptance или release.

### Browser registered-transfer admission при существующем exporter

Только явно выбранный пользователем новый registered-transfer Web ingress получает read-only destination preflight; обычные browser import/export, команды, history, default `assessBackupFeasibility`, PPJ parser и Web/PWA DB version/names/stores не получают новый global guard. Trusted composition выбирает этот вход и его preflight, не файл или пользовательский flag; Telegram V1 policy сохраняет 256-bit comparison и все исходные case-sensitive keys. Дополнительный registered browser exporter потребовал бы отдельной UX/source disposition.

Owner direction AD-31: новые Projects этого ingress предполагается публиковать в дополнительной изолированной browser IDB, с общей directory и полным owner-aware lifecycle. Сохранение прежних DB names/versions/stores означает, что **старые** DB не изменяются, а не запрет на новую; PRD/SPEC уже приняли scoped identity и FR-45 checks. [Storage disposition](browser-registered-storage-disposition-2026-11-05.md) фиксирует route, bounded fresh-v0 bootstrap и оставшиеся implementation/readiness/evidence gates. Исследование однотранзакционного ingress **в прежней DB**, UUID и его прошлых cleanup ниже является историческим альтернативным вариантом; его old-DB-specific proof не выдаётся за обязательный алгоритм AD-31. AD-4 и FR-44/45/57 при этом не ослаблены.

Порядок выбранного route: actual bounded registered decode и прежние source-owned archive/schema/domain/resource checks → actual render smoke на точных проверенных bytes → проверка отмены → read-only полная legacy representability → штатный ImportUseCase с сохранением browser default FPC и действующих pin/fence/publication guards. Для valid wire, непредставимого по состоянию source, return `PROJECT_BACKUP_ENVELOPE_EXCEEDED` с объяснением несовместимости текущего browser backup **до** выделения Project/Revision IDs, pin и staging; отсутствие проверки или её failure также fail closed, но недоступность проверки не объявляется порчей файла. Нужна явно поддержанная typed ветка import result и пользовательское объяснение: нынешний union не принимает этот reason как ранний `rejected`. Source bytes, raw keys и Project не меняются; отсутствие validation/доказательства — не success. Порядок malformed GLB, cancellation и других предшествующих ошибок проверяется отдельно; legacy route и его precedence не меняются.

Representability охватывает actual прежний serializer, browser exporter **и его потребителя**, а не только lowercase: каждый raw key уникален и имеет точную форму `^[a-f0-9]{64}$`, точные bytes/length/SHA и действующие limits/manifest/container checks; все поля Project, optional own presence, массивы, значения `-0`, UTF-16 code units, hosts и ресурсы сохраняются при предусмотренном восстановлении. Проверить actual применимые legacy decoder/parser/AST и exact structured equality, не JSON equality. Обычные допустимые legacy fields и finite yaw, в том числе `0.5`, не запрещаются самим фактом их наличия. Допустимые преобразования import ограничены новым Project ID и `updatedAt`; `createdAt` и прочее не теряются. Доказательство может использовать actual codec либо проверенный эквивалент с доказанными bounded результатами. Одно соответствие хешей или JSON roundtrip не доказывает полный backup.

Полный snapshot source/resources получает exclusive ownership до async; после штатного создания ID и времени повторно проверяется фактический immutable candidate, включая точную длину member, manifest и envelope, до staging и publication. Для обещания отказа до IDs preflight использует доказанные верхние границы всех допустимых ID/time и container overhead; при отсутствии такого доказательства соответствующий случай закрыт до выделения IDs, а не принимается по непроверенной оценке. Если post-ID candidate не соответствует доказанным bounds/представимости, публикация и staging запрещены. Resource bytes и candidate защищены от подмены до commit.

`persist-failed` существующего ImportUseCase может сохранить pending candidate, а controller retry обходит сам importer. Поэтому до каждого initial commit и retry этого ingress trusted route обязан повторно доказать точную привязку к прошедшему preflight candidate и pinned resources, либо закрыть retry данного route без изменения других retry. Обычный user/file flag, mutable поле Project или один checksum не являются доверенным proof; никакой общий history bypass и ослабление FPC недопустимы. Ошибка/cancel сохраняют source и чужие roots; если staging уже имел место, cleanup допускается только по безопасным условным predicates, без изменения чужих bytes. Неопределённый publication outcome не объявляется no-publication.

Сохранение **прежней** browser-семантики требует проверки не только нового ingress. Исторический reality review зафиксировал literal SHA string comparison в прежних browser smoke/feasibility/hydration, тогда как в текущем дереве общий helper сравнивает 256 bits, а custom library/placement сохраняют исходный key. Потенциальные обходы через hydrated uppercase library entry или local Project JSON требуют воспроизведения и сравнения с pre-S3 build: это пока анализ кода, не доказанный пользовательский сценарий. S3 не должен расширять старые browser пути так, чтобы они создавали новые неэкспортируемые Projects; при выявленном отличии сохранить прежнее browser поведение и изолировать V1 alias semantics доверенной Telegram composition. Если additive сохранение и безопасность не доказаны, соответствующий rollout остаётся закрытым; без отдельного owner decision не вводить global guard или browser protocol upgrade. Отдельно проверить, что обычные browser команды и старый установленный PWA не создают новую несовместимость из допущенного подмножества; не объявлять проверенным весь исторический FR-44 baseline.

Текущий browser history protocol остаётся отдельным открытым source risk AD-4: `writeStaging` делает `revisions.put` до проверки fence/base, а `discardStaging` может удалить Revision при несовпадении pointer. Ранее исследованный existing-row/receipt protocol и его reviews — возможная будущая remediation, не выбранное в этом additive scope изменение и не доказательство исправления. `intent=history` или membership в in-memory roots не доказывают защиту. До отдельного решения не менять browser history semantics/DB protocol, не удалять и не нормализовать Projects, resources или roots; старые установленные PWA не считать автоматически скоординированными. Нормативные AD-4 и FR-44/FR-57 этим не отменяются и не считаются выполненными по одному только admission.

Та же текущая browser publication создаёт staging через безусловные `revisions.put` и `staging.put`; `publish(candidate)` без expected base сам по себе не доказывает no-overwrite при коллизии нового Project/Revision ID. До допуска нового ingress доказать source-owned гарантию безопасной уникальности/отсутствия перезаписи и согласование с параллельными старыми клиентами; простого случайного ID или предварительной проверки до асинхронной записи для этого доказательства недостаточно. При отсутствии доказательства открывается отдельный owner decision о безопасном способе, а затронутый rollout закрыт; глобальный DB protocol upgrade не внедряется побочно. Это выявленный риск текущего кода, не воспроизведённая пользовательская коллизия и не доказательство, что исходные Projects уже повреждены.

#### Историческая альтернатива: scoped no-overwrite в старой browser DB

Предложение использовать private `WeakSet` только для sealed candidate и два opt-in IDB этапа с `add` улучшает защиту от перезаписи **на каждом из этих этапов**, но в предложенном виде недостаточно. Есть гонка без какой-либо коллизии: (1) новый ingress записывает видимый `staging[Q]`; (2) старый client `recover()` считывает список и запоминает Q; (3) новый ingress публикует Q и удаляет свой staging; (4) обычная следующая команда Q создаёт staging другой Revision; (5) отложенный старый `discardStaging(Q)` удаляет эту новую staging/Revision. Проверка fence и exact нового candidate во второй transaction не отзывает уже запланированный старый cleanup. Это вывод из текущего кода, требующий исполняемого воспроизведения, а не заявленный пользовательский инцидент. Два `add` без нейтрализации этого сценария не утверждаются как безопасный способ внедрения.

Предпочтительное узкое направление для проверки — **одна** readwrite transaction нового ingress без видимой старому Project recovery промежуточной staging-записи: проверить незанятые Project/Revision identifiers и все применимые ownership/reference predicates, конкретный current writer lease/fence для того же Project, затем `revisions.add` и `projects.add` как единый commit. Контроллер и публичный ImportUseCase могут сохранять свою общую форму, но внутренний вызов publisher/store должен обеспечить именно такую границу; имитация промежуточного `writeStaging` в памяти допустима только при доказанном неизменяемом attempt и отсутствии durable side effects. Если нельзя сохранить требуемые pin/recovery гарантии без Project staging, альтернативный протокол должен явно устранить отложенный старый cleanup; новый global history protocol или DB upgrade этим решением не предписаны.

Это направление не отменяет staged validation по CAP-10/FR-45 и recoverable resource pin/journal по AD-4: владелец SPEC в §1.4 условно допускает protected bounded validation в памяти и отдельный recoverable pin staging без видимой Project staging записи при сохранении всех checks и crash/recovery guarantees. Это source applicability, не доказательство реализации; применимый readiness gate, CAP/FR и требования к roots/fence сохраняются.

Проверка только `projects.get(Q)`, `revisions.get(R)` и `staging.get(Q)` не полна: `revisions` адресован глобальным R, а старый `staging` — по Project ID; чужой dangling `staging[P]` может ссылаться на R, и его старый `discardStaging(P)` позднее удалит эту Revision. Также отсутствующий `projects[Q]` не исключает orphan Revision, recovery или другие roots, принадлежащие Q, либо pointer, ссылающийся на R. Нужна bounded authoritative проверка всех пересечений существующих Project pointers, Revision ownership/IDs, staging references и применимых lease/journal roots в транзакционно защищаемой области либо доказанный эквивалент; нельзя считать `get(Q)` достаточной inventory. Если невозможно безопасно оценить конфликты или отложенные действия, fail closed без перезаписи/удаления; заранее существующий или уже выбранный старым recovery cleanup учитывается отдельно. Все конфликтные `add` должны abort всю transaction, не подавлять `ConstraintError` и не вызывать старый безусловный `discardStaging(projectId)` для чужих записей. Долгий hashing/IO не выполняется внутри IDB transaction; заранее защищённый snapshot повторно связывается с commit.

Даже single-transaction commit не устраняет уже отложенный old recovery, ранее выбравший Q из **другой** старой staging-записи: эта запись могла исчезнуть до commit, а позже `discardStaging(Q)` удалит staging следующей обычной команды Q. Текущая пустота `staging[Q]` не доказывает отсутствие такого незавершённого действия. Необходим конкретный proof отсутствия ранее выбранного cleanup для Q, например доказанный никогда ранее не использовавшийся Project namespace, совместимый с поддерживаемыми старыми клиентами, либо другая подтверждённая координация; если proof недоступен, scope запуска остаётся закрытым. Простого нового UUID, отсутствия row в одной transaction или нового локального lock недостаточно. Это отдельно от ограничения на будущую произвольную коллизию старого клиента.

Private `WeakSet` — допустимый элемент реализации, не полное доказательство: конкретная trusted registered route capability должна быть привязана к immutable exact candidate, Project/Revision IDs, проверенным raw resource roots и конкретной попытке до первого async и пройти все wrappers без fallback в обычный publisher при clone, потере маркера, retry или недоступной проверке. Текущий browser default wrapper сохраняет object identity, но при injected policy может сделать copy; structured clone/restart не сохраняет WeakSet. Смена reference или потеря capability требует отказа либо явно повторно проверенного безопасного восстановления, а не перехода на старый `put`. Существующий sealed profile и `beforePublish` остаются обязательными; marker не заменяет exact legacy representability, FPC, защищённые pin bytes или проверку fence. Сохранённый pending candidate не должен блокировать пользователя без описанного безопасного исхода; повторный выбор файла и unknown commit не дают права очищать или повторять чужую попытку по одному ID.

Resource pin и Project metadata находятся в разных IDB. До Project commit необходимо доказать, что новый pin/journal attempt не перезаписывает чужой root, а actual bytes/length/hash остаются защищены; существующий journal `create` использует `put`, а `isPublicationPublished` сравнивает только Project/Revision IDs. При forced reuse эти признаки сами не доказывают, что опубликована **эта** попытка. Нужны collision-safe lease ownership и exact привязка результата к собственной попытке либо консервативное удержание journal/bytes до такого доказательства; потеря fence, timeout, cancel после фактического commit и отсутствие pointer не означают no-publication. Конфликт/pending/неизвестный outcome не освобождают и не удаляют чужие roots или shared bytes. Текущий `FencedProjectRepository.publish` получает writer lease до delegate и может менять `writer-leases[Q]` до нового no-overwrite guard. Необходимо acquisition без изменения чужого lease/takeover state при коллизии Q: conditional проверка в общей атомарной границе либо доказанный эквивалент; нельзя считать одну позднюю сверку fence достаточной. Данное условие не предполагает автоматическое добавление глобального receipt/DB upgrade: выбор узкого механизма и его доказательства остаются за implementation owner, а не заменяются случайным UUID.

Граница утверждения принципиальна: даже доказанный атомарный `add` защищает существующие записи от **этой новой операции** в её транзакции и сериализует конкурирующие на тех же IDB stores транзакции. Он не может запретить уже открытому старому клиенту или отложенному старому cleanup позже использовать идентичные IDs и выполнить прежний безусловный `put`/delete. Не заявлять, что новые проверки делают все будущие старые clients fenced. Риск старого browser protocol и AD-4 остаются отдельными; если применимый release действительно требует безусловной защиты от произвольной будущей old-client записи/ID reuse, нужен отдельный owner decision о barrier/протоколе либо ограничении выпуска, а не незаметный scope upgrade. Отсутствие конфликтов в проверенной области и безопасность обычных независимых старых операций нужно доказать, не выдавая универсальную гарантию.

##### Граница UUID, старого cleanup и возможного allocator

Один atomic `add` с проверкой actual актуальных rows/roots может подтвердить **ограниченный факт**: в момент собственной транзакции новый ingress не перезаписал проверенные существующие записи, если конфликтная transaction abort целиком и подтверждены fence, capability и pin/journal predicates. Эта проверка не видит Q, который старый `recover()` уже прочитал и затем staging Q исчез из IDB. Если новый ingress выдаёт тот же Q, старый `discardStaging(Q)` способен позднее удалить staging следующей команды и её неопубликованную Revision; при history transition он может удалить row существующей undo/redo Revision. Это не утверждение, что такой сценарий уже произошёл, и не автоматическое доказательство удаления Durable Project.

**Историческая диспозиция для старой DB:** узкий transaction proof сам по себе не доказывал отсутствие ранее выбранного cleanup для Q. Эти требования относятся к оценённой альтернативе записи в прежнюю DB и не навязываются для изолированного AD-31; текущий SPEC §1.4 выбирает независимый namespace и scoped identity. Нормативные CAP-10, FR-45, FR-57, AD-4 и сохранение History roots не ослаблены. Вероятностное исключение safety-гарантии никогда не утверждалось; независимый registered Web export и Telegram работа этим историческим blocker автоматически не охватываются.

`browserRandomUuid` в текущем исходнике и одном проверенном frozen build использует UUIDv4: при исправном независимом CSPRNG 122 bits случайны. Для одной независимой выдачи и заданного множества из `k` различных ранее запомненных v4 IDs вероятность попадания не более `k/2^122`; для `n` таких выдач — не более `n·k/2^122` по union bound. Для меняющегося набора нужны условные `k_i` и сумма соответствующих bounds; отдельно учитываются Revision/lease IDs и другие races. Это условная оценка, не ноль и не proof при неизвестных `k/n`, зависимости, сбое RNG, принудительном ID или неподтверждённых старых builds. Browser IDB validators принимают непустые строки, не только UUID; один найденный generator не характеризует все legacy состояния и активные процессы. Отсутствие строки в IDB не доказывает отсутствие Q в чужой памяти. Сброс IDB сам по себе не доказывает сброс WebCrypto RNG; в отличие от этого, `prefix+counter` после потери counter может детерминированно переиспользовать ID.

Минимальный **кандидат**, не одобренный как готовый protocol и не требующий нового DB store/version: выделить недвусмысленный namespace новых Project **и** Revision IDs, с отдельной зарезервированной metadata-записью allocator в существующем `writer-leases`, если её безопасная семантика будет доказана. До bootstrap необходимо подтвердить для всех поддерживаемых старых builds/producers и восстановленных contexts, что ни существующие, ни уже удалённые/запомненные old IDs не принадлежат выбранному namespace, включая непривилегированные пути, которые принимают произвольную непустую строку. Выбрать metadata key, не являющийся допустимым Project ID или именем, к которому старый клиент может обратиться; текущий store индексируется по `projectId`, а старые acquire/takeover/delete используют `get/put/delete` этого ключа как обычный lease. Одного необычного имени или текущего отсутствия строки недостаточно. Нужны проверка всех затрагиваемых stores и реальный regression corpus старых сборок.

Для инженерной оценки конкретной схемы допустимо рассмотреть `projectId` metadata key длиной более 256 UTF-16 code units и typed marker с отдельными Project/Revision counters: текущий Project validator ограничивает непустой ID 256 units, а прочитанный текущий и один frozen old build обращаются к `writer-leases` по конкретному Project ID. Это лишь **кандидат разделения**, потому что direct/recovery API и другие старые builds не доказаны, и несовместимый или повреждённый store может содержать такой key. Сам Project/Revision ID может использовать отдельный новый prefix либо совместимое 36-character пространство вне подтверждённого UUIDv4 подмножества; в обоих случаях необходимо доказать virgin namespace и обновить ограничение текущей admission, которая явно требует v4. Не создавать marker и не выбирать такой ID только на основании этой заметки.

Если и только если доказан first bootstrap в context, где ранее не выдавался этот namespace и нет несовместимых старых незавершённых действий, создать marker через атомарный no-overwrite `add`, затем выделять ID атомарным durable монотонным counter до его первого раскрытия вне защищённой попытки; marker не принадлежит удаляемому Project, не очищается при Project deletion и валидируется вместе с форматом, scope и счётчиком. Abort/crash, конкурентные allocators и повторная попытка не должны повторно выдавать уже раскрытый ID; invalid marker, overflow, потеря или rollback counter → fail closed, без reset. Текущая admission требует UUIDv4 для обоих новых IDs и оценивает их как 36 ASCII bytes, поэтому другой формат требует отдельной корректировки bounds, совместимости legacy codecs и тестов; подменять эти условия нельзя.

Отсутствующий marker сам по себе не отличает первый legacy bootstrap от очистки/eviction или отката DB после предыдущей работы allocator, пока другая вкладка могла сохранить старый Q в памяти. Даже присутствующий и корректно сформированный marker из старой валидной копии DB с меньшим counter локально неотличим от настоящего более раннего состояния: проверка формата сама по себе rollback не обнаружит. Требование fail closed при rollback выполнимо только при доказанном внешнем monotonic authority либо lifecycle/barrier, который исключает такой restore вместе с живыми ранее выданными ID; иначе allocator не доказан и закрыт. Для такого неоднозначного состояния автоматический первый запуск/reset запрещён без внешне доказанного lifecycle/authority либо совместимого barrier, исключающего старые действия; случайная новая epoch лишь меняет вероятность и не доказывает невозможность повторения. Проверять restore из старой копии, blocked upgrade и отдельные browser/Home Screen contexts; не выполнять очистку базы. Это условный проектный вариант и список обязательных доказательств, не утверждение, что существующий `writer-leases` marker уже безопасен или что source разрешил изменение storage protocol.

Даже доказанный свежий namespace закрывает лишь доказанную область прошлых ID. Старый установленный PWA может штатно открыть **уже созданный новый Q**, выполнить обычную команду и запомнить его staging: последующий stale cleanup может воздействовать на тот же Q без новой UUID-коллизии. Аналогично старый recovery может увидеть staging новой обычной команды. Это независимый pre-existing history/fence risk, не устраняемый prefix/counter и не объявляемый решённым новым ingress; для безусловной защиты такой работы нужен отдельный совместимый протокол/ограничение старых writers или иное source-owned решение. Не требуется побочно внедрять общий DB upgrade/history change ради проверки узкой операции.

Будущие проверки: искусственные Project/Revision/lease collisions, чужой dangling staging `P→R`, orphan/pointer/root, старый recovery scan до нового commit с последующей обычной командой, в том числе ранее выбранная **другая** staging Q уже удалена к моменту нового commit; старая transaction до/между/после commit, lost fence/takeover до записи, mutation/clone/потеря capability, initial/retry/pending, quota/abort/crash до/после commit, оба outcome и pin-journal races с exact bytes. Отдельно проверить сохранность прежних Web commands/history/DB и независимого проекта, отсутствие ложных `durable` и чужого cleanup. Эти проверки пока не выполнены; предложение не является готовой реализацией.

Изолированный probe с реальным GLB показал uppercase registered Web import как Durable, после которого прежний exporter вернул `PORTABLE_BACKUP_RESOURCES_UNAVAILABLE`; исправление и его tests probe не доказывает. Будущая проверка включает uppercase/mixed-case/alias pairs и valid lowercase real GLB; полный legacy export/reimport со сравнением geometry, metadata, hosts и bytes; `-0`, own-undefined, Unicode и реальные допустимые optional fields; bounds и generated IDs/time, forced ID collisions и параллельных old clients; ошибки/cancel/cleanup; initial/retry race; unchanged old browser behavior и старые PWA; отсутствие расширения старых shared SHA paths; Telegram V1 aliases. Каждая actual cross-host client/route pair требует своего file corpus и physical evidence; ограниченное representable подмножество не является доказанной полной FR-57 матрицей.

## Дополнительный Web/PWA export для переноса — owner direction

Владелец просит второе явное действие `Экспорт файла для переноса` рядом с прежним export в действиях Project на Projects и в меню editor. Это направление UX для двух существующих точек входа, не автоматический выбор формата и не изменение прежней кнопки. Architecture допускает отдельный trusted Web exporter на зарегистрированном `interiors.project/runtime-v1-wire@1`; UX и SPEC owners уже внесли направление и условия в свои источники, взаимная сверка source decisions и применимый readiness gate остаются до implementation/поставки. User direction достаточно конкретно задаёт желаемое действие; не подменять source-owner reconciliation выдуманным повторным согласием пользователя.

Новый action выбирает только конкретный **Durable** Project, включая пустой Plan, и выдаёт локальный файл без mutation, нового Project/Revision ID, миграции, изменения raw keys или сетевой отправки. Pending/unsaved candidate остаётся отдельным recovery export, не называется complete backup; если editor содержит несохранённую работу, интерфейс не выдаёт её за экспортированную Durable Revision. Требуются честные состояния подготовки, отмены, неподдерживаемого/непредставимого snapshot, недоступных ресурсов и ошибки verifier; готовые bytes или вызов системного picker не доказывают внешнее сохранение. Host UXF-8 использует местную выдачу без upload; отсутствующий способ явно сообщает отказ. Показ результата не обещает обратный импорт во все версии.

Это отдельная browser composition dependency и action, не замена общего `portable.exporter`, legacy decoder/exporter, browser default `BackupFeasibilityPolicy`, history, recovery path или DB version/stores. `ExportRuntimePortableBackupUseCase`, registered V1 writer и smoke существуют; в текущем исходном дереве browser composition подключает отдельный `BrowserRegisteredProjectExporter` и действия в Projects/editor, пока для legacy browser resource store. Это code wiring, не доказательство интеграции AD-31, end-to-end передачи, release или physical compatibility. Browser writer связывается с actual repository и pinned resource store/checksum **выбранного owner**, не Telegram store, browse cache, чужой DB или remote URL; V1-format smoke/writer не меняют обычные browser resource/hash policies.

Выбранная durable Project/Revision identity и snapshot должны быть получены и проверены как фактически принадлежащие выбранному browser Project; при конкурентном изменении допускается экспорт конкретной уже Durable Revision только с честным обозначением версии, без смешивания снимков. Текущий controller может вернуть in-memory `current`, а internal JSON/checksum не различает `-0`/`0` и own-undefined/absence; одних них недостаточно, чтобы доказать exact structured Durable snapshot. До первой async операции над данным snapshot обеспечить exclusive immutable ownership либо доказать exact сохранённую structured identity на границе; чтение Revision и pointer, связанные ресурсы и их lifetime должны исключать гонки с cleanup/delete/takeover. Прочитать **каждый** exact raw key и подтвердить pin/root, длину, все 256 SHA bits и bytes, включая каждый alias; `resources.read` сам по себе не доказывает pin. Сохранить source и при отказе/cancel, проверяя bounded memory, resource/domain/geometry и форматные limits. Exception verifier не объявляется повреждением файла или Project.

Export разрешён только если current registered writer действительно может полно и точно представить snapshot и resources. Его текущая V1 closed grammar, read-only domain validation и registered GLB smoke/writer не являются поддержкой каждого readable/healthy исторического Project: non-index array properties, несоответствие internal revision string и прочие невыразимые состояния получают безопасный отказ с сохранением источника и прежних действий. Текущий registered resource preflight использует 25 MiB; 50-MiB envelope сам по себе не разрешает 25–50 MiB GLB. Другая применимость export/repair требует отдельного source decision. Roomless Project имеет честный empty/2D path без 3D сцены; существующий smoke не доказывает GPU decode/render или physical transfer. Текущий codec использует синхронный `zipSync`: проверки отмены до/после него не доказывают немедленное прерывание этого этапа или приемлемый peak memory на телефоне. До доказательства устройство/интерфейс не обещает своевременную отмену внутри синхронной стадии; сохранность source и отсутствие ложного ready при отмене обязательны.

Новый action не заменяет прежний export и не закрывает FR-44 gate для **всех** non-corrupt Durable Projects. Новый V1 файл не читается старым browser decoder. Его точные `-0`, own-undefined или uppercase aliases могут быть допустимы в V1 и TMA, но отвергнуты обратным новым browser registered ingress, пока тот требует exact legacy representability по §1.4. Поэтому `Web → TMA` и `TMA → Web` подтверждаются отдельно по actual representable файлам и client/version pair; не обещать universal roundtrip, backup-recovery или поддерживаемую совместимость по одному успешному export.

Для конкретного наблюдённого ambiguous empty legacy файла возможен **кандидат** восстановления: пользователь сохраняет оригинал, прежний Web import принимает его в доступном исходном browser context как новый Project, обновлённый совместимый Web action экспортирует его в V1-wire, затем strict TMA импортирует фактически переданный файл. Нужны доказательства именно этой цепочки и версий: source archive hash до/после, привязка правильного browser/iOS Home Screen storage context, безопасный доступ/upgrade существующего context, фактическое внешнее сохранение и повторный выбор файла, exact сравнение Project/geometry/metadata/hosts/resources с учётом только обычной смены ID/timestamps при import. Браузерный import оригинала и новый export не доказывают происхождение/подлинность файла и не дают automatic promotion другому legacy/PPJ файлу. До доказанного конкретного пути sole-copy и FR-57 остаются pending.

Будущее evidence: отдельные оба UI entry на phone, прежний export и old PWA regressions; actual pinned browser resources/checksums, empty/open plan, Room и real GLB; exact V1 wire → strict TMA import с сравнением fields/hosts/bytes, включая case aliases и поведение отказов; обратный Web ingress только в его допустимом подмножестве; missing/corrupt/unpinned resource, V1-unrepresentable Project, >25 MiB, checksum mismatch, concurrent edit/delete/cleanup, cancel/exception, bounded memory и source unchanged. Отдельно тестируется конкретный old empty file recovery chain, source hash и отсутствие fallback. Реальные iOS/Android внешняя выдача, выбор файла и повторный import требуются до NFR-28/FR-57 claims. Это предписанные проверки, не результаты тестов.

# Порядок, reasons и atomic publication

Для всех строк: safe archive paths/container guards → bounded manifest syntax (не проверять раннюю регистрацию валидного selector) и ledger/path bindings → Project declared/streamed >10 MiB `BACKUP_PROJECT_LIMIT` → Project checksum `BACKUP_CHECKSUM_MISMATCH` → bounded raw syntax/AST → exact selector/root/source и single dispatch → closed grammar/raw lexemes → remaining policy limits → domain/host integrity → exact resource/hash validation → copy-on-write publication. Невалидный path/duplicate → `BACKUP_PATH_UNSAFE`, malformed manifest → `BACKUP_MANIFEST_INVALID`, invalid encoding/duplicate/schema/mismatch/unregistered/ambiguous/unmappable → `BACKUP_SCHEMA_UNREADABLE`; AST capacity и остальные превышения → `BACKUP_PROJECT_LIMIT` на соответствующей стадии. Прежние container/resource/quota/cancel codes не переименовываются; invalid PlanGraph сохраняет domain reason. У неизвестного, но синтаксически корректного selector oversize или checksum failure побеждают неизвестность selector. PPJ ordering/reasons и scalar rejection не меняются.

Чтобы сохранить этот порядок при общем старом manifest selector, bounded non-accepting scan запоминает raw UTF-8/JSON, position и ошибки, извлекает только наличие/значение root selector без публикации или принятия данных; он не может заставить PPJ пройти V1 grammar. PPJ либо неопределённый маршрут применяет PPJ AST-R1 и воспроизводит его ошибки в прежнем порядке; legacy с строго отсутствующим selector применяет отдельный V1 parser и затем witness-check. Duplicate selector, malformed JSON или ранний AST limit не обходятся lookahead. Нынешний production decoder делает source-ID `JSON.parse` до checksum; это факт несовпадения, а не новая норма. В будущем общий contract обязателен для обычного import и exact-repair from backup; repair принимает только exact проверенные bytes по ожидаемым hashes, не подменяет RecoveryChangeSet и не создаёт новый Project. Recovery export непубликованного candidate остаётся отдельным типом, не complete backup.

После validation import сохраняет source `createdAt`, создаёт новый Project ID, ставит `updatedAt=clock.now()`, создаёт новую V1 Revision с новым ID и `createdAt` того же момента и публикует атомарно с прежним internal serializer/checksum. Source Project/file, все прежние revisions и ресурсы не перезаписываются; session History не переносится. Cancel/crash/quota не создают partial Project и не освобождают чужие roots. Export из healthy Durable V1 использует этот отдельный wire codec и полный hash-verified resource set; отказывать такому Project из-за wire representation нельзя. До proof и соответствующего gate прежний browser export остаётся доступным и не заменяется.
