# Наблюдение

В текущем browser baseline `DurableProjectRepository.recover()` перечисляет staging всех Projects и удаляет записи без owner/fence predicate; `writeStaging` пишет по Project ID без проверки lease; stale-base cleanup удаляет staging по Project ID. `PinStagingPublication` содержит лишь Project ID/Revision ID, а startup reconcile сравнивает current revision, не доказывая полный AD-4 journal predicate. `FencedProjectRepository` имеет latest lease и не предоставляет conditional release. Эти наблюдения не утверждают полное нормативное выполнение AD-4. Runtime-local generation queue не синхронизирует разные contexts. При этом существующий S1 browser-only поток, имена/данные/схема и его проверенный результат не переписываются этой архитектурной поправкой.

Общий scope-wide GC/root inventory сейчас отсутствует: `sessionRetentionRoots()` относится к одному in-memory controller, не ко всем contexts; удаления Project и tombstone библиотеки не являются доказанным глобальным GC. В S2 общий GC не создаётся и owned bytes сохраняются. Существующий exclusive pin cancellation cleanup и reconcile — отдельные изменяющие операции, требующие защиты ниже. Нет разрешения молча удалить staging, Project, history или resource в другом scope/context.

# Выбранная граница перед первой writable S2

Для **Telegram scoped runtime** выбран один IndexedDB database на scope: существующий `interiors-editor-projects:<scope>` с `scope-metadata`, Project pointers/revisions/staging, writer/fence, journal, resources и library как object stores одной DB. Version 1 уже содержит identity и uint64 counter; version 2 добавляет stores в одной versionchange transaction, без удаления/пересоздания DB и без изменения identity, identity.protocolVersion=1 или counter. Внутри versionchange transaction **до commit** прочитать и проверить exact identity/counter и весь v1 store inventory; неизвестные stores/records, отсутствие или повреждение metadata → abort без добавления stores. Fresh `oldVersion=0` создаёт v2 со всеми stores, identity и counter атомарно; нельзя локально отличить впервые увиденный scope от полностью очищенного извне origin storage, а значит заявлять восстановление удалённого counter/data. При любом сомнении для уже существующей DB запрещён reset. Перед upgrade scope Web Lock обязателен; blocked/abort/quota/failure оставляет прежнюю v1 DB и данные нетронутыми, запись закрыта до retry. Existing v1 runtime на `versionchange` отзывает session и закрывает соединение; отвергнутый `blocked`/timeout open должен на позднем `onupgradeneeded` abort transaction и на позднем `onsuccess` close DB, чтобы upgrade не состоялся вне удерживаемого lock; старый client, который не умеет открыть v2, не получает writable fallback. После upgrade прежде чем писать повторно проверить точное значение counter, identity, state и schema; обычные write transactions counter/fence/receipt/no-publish требуют `durability:"strict"` с проверкой, без silent downgrade. IDB versionchange transaction создаётся браузером: её durability не подменяется вымышленным параметром, атомарность и фактическое поведение проверяются на клиентах; повреждённое значение не переинициализируется. Browser/PWA обе существующие DB names/schema/adapters не меняются. Если найдены неизвестные данные или устаревшие незавершённые записи вне metadata-only v1, остановить migration и сохранить данные; не объявлять копирование выполненным. Это storage adapter decision, не изменение Project schema, доменной сериализации или Resource identity.

В одном scoped DB admission обеспечивает условные атомарные записи; текущие browser handlers не используются как доказательство, не получают отключения safety/regression. Пока хотя бы один пункт отсутствует или не доказан, Project/runtime остаётся read-only/не начинает mutating действия, включая создание, import, repair и удаление. Signed-launch validation сама по себе не открывает writable runtime. Это часть AD-4/AD-26, не новый readiness verdict.

1. **Межконтекстный lock.** Все contexts одного Telegram storage scope до изменения writer lease/takeover, staging, journal/root, pin/protect, pointer или cleanup получают один exclusive [Web Lock](https://www.w3.org/TR/web-locks/) с именем `interiors-tma-storage-v1:<scope>`, удерживая его до завершения всех задействованных transactions этой DB; все shipped версии, открывающие этот scope, обязаны соблюдать тот же протокол. `steal` запрещён, nested повторный запрос того же lock запрещён; долгие сетевые операции и пользовательский ввод выполняются снаружи, а затем все predicates и bytes проверяются заново под lock. Возможность secure-context `navigator.locks` проверяется до writable runtime: при отсутствии или невозможности получить lock — read-only/ожидание/отказ, не unfenced fallback. Разные origins/storage partitions не объявляются общим lock domain. Lock освобождается после завершения callback или прекращения context; crash разрешается только журналом ниже. Web Lock — взаимное исключение участников, не замена durable fencing/receipt и не security boundary против скрипта origin. Поддержка и поведение на целевых WebView требуют evidence.
2. **Cross-context writer и stage.** Одна IDB transaction охватывает scope-specific Project pointer, staging, revision, writer/fence, journal state и нужные resource/library object stores. До любого stage-write, перезаписи или удаления stage эта же transaction проверяет scope, Project ID, действующего owner и fencing token, ожидаемый base/current pointer и уникальный attempt ID. Новый Project требует проверенного отсутствия pointer/ID collision и своего writer fence; существующий требует точного base. Revision ID, attempt ID и lease ID проверяются на отсутствие collision во всём scope в atomic transaction соответствующего store; Revision создаётся no-overwrite (`add`), кроме доказанного идемпотентного повтора того же attempt с идентичными checksum и owner metadata. Коллизия никогда не перезаписывает существующую Revision другого или того же Project. Undo/Redo — не создание Revision: history pointer transition вправе адресовать уже существующую owned Revision после точной сверки Project ID, revision ID, checksum, serialized bytes и resource manifest; саму Revision не перезаписывать. Для перехода выделяются новый attempt и receipt и атомарно проверяются exact source base и current fence. Новая semantic Revision ради Undo/Redo не создаётся, session History в backup не переносится. Старый writer не может перезаписать чужой stage до проверки pointer. Если хранение не может выполнить общий predicate атомарно — write запрещён. Нельзя использовать unfenced fallback `delegate.publish`.
3. **Publication receipt.** Journal записи получает до записи новых bytes неизменные scope, Project ID, attempt ID, ожидаемый base (либо explicit create), writer owner и fencing token, checksum candidate revision и полный target resource-hash manifest. Fenced transaction, делающая pointer swap, проверяет их вместе и атомарно пишет **durable published receipt**, идентифицирующий revision/checksum и manifest. Проверка только «текущая Revision совпадает» не является receipt: поздний pointer мог измениться. Attempt ID и pin lease ID выделяются из сохранённого scope-local монотонного счётчика: под scope Web Lock отдельная atomic transaction сначала необратимо увеличивает uint64 counter, затем формирует ID как `tma-v1:<scope>:<kind>:<counter>` (`kind` различает attempt и lease). Зарезервированные значения нельзя повторять даже после abort/удаления Project или журнала; counter и scope identity не удаляются и не сбрасываются. Counter сохраняется и сравнивается без потери точности (`BigInt`, фиксированные 8 bytes либо каноническая decimal string; не JavaScript Number). При первом создании нового scope initializer и marker создаются атомарно; отсутствующий или повреждённый counter у уже существующего scope нельзя переинициализировать нулём: запись закрыта до точного восстановления. На исчерпании диапазона запись закрывается без wrap. Рandom UUID или проверка только текущих записей сами по себе не доказывают запрет ABA; durable состояния `prepared`, `published` и `no-publish` и связанные receipt сохраняются до завершения этого exact attempt. Отсутствие receipt допустимо как доказательство no-publish только для полных записей этого протокола при неизменной гарантии атомарной записи receipt вместе с pointer. Повторные операции идемпотентны и не меняют более новую generation или revision.
4. **Безопасный no-publish/cancel.** До destructive cleanup current owner/fence в той же Project-store transaction закрывает конкретный attempt как `no-publish`, доказывая, что receipt/pointer transition не состоялся, и делает его дальнейшую publication невозможной. Конкурирующая publication либо выигрывает эту transaction и оставляет published receipt, либо получает отказ; read-then-delete не годится. Удаление stage сравнивает точные scope/Project/attempt/fence/base, а не только Project ID. При истёкшем/утраченном fence, неясном результате, недоступной базе или старой неполной journal записи сохранять staging, journal и bytes, показывая recoverable/read-only состояние; не превращать неопределённость в успешный cleanup.
5. **Единая физическая DB.** Общая transaction включает pin/protect resource, pointer swap и publication receipt либо conditional no-publish/cleanup вместе с writer/fence и journal; под scope lock bytes сначала читаются в immutable snapshot, асинхронный hash/size вычисляется вне активной IDB transaction, затем новая transaction перечитывает resource и сравнивает immutable identity/version/size вместе с fence/base/journal перед pin/protect и commit; `crypto.subtle.digest` нельзя await внутри незавершённой transaction. При смене identity/revocation отказ или полный retry. Если большой resource нельзя безопасно обработать в одной transaction, использовать предварительный подготовленный immutable staging root в той же DB: перед publication повторно проверить точный hash/size, fence/base/root и сделать atomic переход; не делить итоговую публикацию на две несогласованные DB. До записи bytes создан journal root. Существующая atomic `deletePinnedIfOwned(hash, leaseId)` допустима только после доказанного `no-publish`, проверки scope и сохранения ownership у exact resource record; fallback на неусловный `delete(hash)` запрещён. Каждый второй потребитель до publication **обязан** атомарно защитить существующую resource-запись или атомарно закрепить вновь записанные bytes в той же IDB transaction на resource object store, которая конкурирует с `deletePinnedIfOwned`, и проверить hash/size именно защищённых bytes. Повторное чтение или re-fetch/hash без успешного atomic protect/pin недостаточны. Если cancellation уже выиграл, вторая операция заново получает, проверяет и атомарно pin/protect-ит bytes до publication; при отсутствии безопасной операции публикация запрещена. Published receipt позволяет безопасно завершить только соответствующий root; inconclusive record остаётся корнем. Journal removal и release идемпотентны, не освобождают чужую lease/history или новый root. Этот протокол не требует общего blob GC, но не заменяет AD-4 integrity/BackupFeasibilityPolicy.
6. **Takeover и teardown.** Persisted fence generation монотонно увеличивается для `(scope, ProjectId)` при acquisition/takeover и никогда не сбрасывается или переиспользуется, в том числе при release/delete/recreate; старый token не становится валидным снова. Project IDs не переиспользуются, counter/tombstone сохраняется. При takeover прежний writer теряет право на новые stage/commit/cleanup. AD-26 local barrier закрывает новые допуски и ждёт in-flight операции до уничтожения runtime. Если у substrate нет atomic conditional release с сохранением счётчика и проверкой scope/owner/token, teardown прекращает renewal и оставляет lease истечь; он не удаляет lease и не утверждает немедленное освобождение. Следующий context следует существующему explicit takeover правилу.
7. **Startup и crash.** Startup не вызывает безусловный `recover()` старого адаптера для Telegram и не удаляет все staging. Совместимая scoped reconciliation использует published receipt либо доказанный no-publish выше; остальные записи сохраняются и блокируют только затронутую запись до безопасного resolution. После явного takeover новый owner может под тем же scope lock выполнить adoption отдельной recovery transaction: проверить свой новый current fence, exact immutable identity полного старого attempt, состояние/receipt и отсутствие возможной старой publication; если receipt обновлённого fenced-protocol есть — закончить только его root без подмены newer pointer; если полного receipt нет и гарантированно не могло быть publication по правилам пункта 3 — атомарно закрыть старый attempt `no-publish` и затем выполнять conditional cleanup. При неполной legacy записи, неясной publication или отсутствии этих предикатов сохранить данные и read-only, не угадывать. Временные scope generation, прежние Project data и pin roots не переносятся между аккаунтами и не очищаются при A→B→A.

# Проверки и handoff

До первой writable операции нужны deterministic races с двумя независимыми runtime на одном scope: stage A против takeover B; A stale-base cleanup против новой stage B; две попытки одного hash против cancel и protect, включая delete между read и protect и между protect и publication; попытку ABA с повторным lease ID, crash после резервирования counter, значения выше 2^53, отсутствующий/повреждённый counter существующего scope, переполнение и попытку сброса counter, а также коллизии revision/attempt/lease IDs с проверкой исходной Revision; takeover между no-publish и resource cleanup; crash/expiry с adoption полных и неполных журналов; crash на каждой границе journal/pin/receipt/pointer, upgrade v1→v2 blocked/late-onupgradeneeded/abort/quota/versionchange и точное сохранение identity/counter; revoke во время reserve/upgrade (поздно полученный ID расходуется и не разрешает следующую mutation); Undo/Redo на уже существующую Revision с новым attempt/receipt и без overwrite; receipt после смены current pointer; неизвестная старая journal запись; двойной startup; failure/retry; Project delete и повторное использование ID; release/expiry и отсутствие token reset; A→B→A с поздними callbacks и приостановленным commit/reconcile/cleanup. Каждая проверка подтверждает отсутствие чужой публикации/удаления и сохранение точных bytes/history roots. Отдельно regression подтверждает, что Web/PWA baseline не ухудшен; сами эти проверки здесь не запускались.

SPEC-owner сверяет AD-4/AD-26 с `project-and-backup-contract.md` и `telegram-platform-and-compatibility-contract.md`, включая session retention и допустимую conservative retention; epic/story owner уточняет порядок защиты до первой writable 10.2 и соответствующие AC. Readiness owner оценивает изменение и применимость gate; эта запись не меняет прежний verdict и не является waiver. Никакой general GC, удаление пользовательских данных или новый backend здесь не принимаются.
