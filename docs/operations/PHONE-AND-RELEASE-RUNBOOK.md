# Запуск на телефоне и выпуск InteriorsEditor

Обновлено 24 октября 2026. Этот порядок предназначен для локального владельца
проекта и оператора внутренней Alpha. Проекты находятся в браузере телефона;
резервная копия базы каталога не является резервной копией проектов.

Текущий личный запуск доступен по временному
[HTTPS адресу](https://dry-jeff-mere-settle.trycloudflare.com). В сессии 24 октября
он уже использует живой Kotlin/PostgreSQL catalog через same-origin proxy.
Адрес работает, пока Mac, сервер и tunnel остаются запущенными; он не закреплен
как постоянный hostname. Ниже описаны оба воспроизводимых режима запуска.

## Личный тест на телефоне

Из корня репозитория установить зависимости и собрать приложение:

```sh
npx --yes --package=node@24.19.0 --package=pnpm@11.20.0 pnpm install --frozen-lockfile
npx --yes --package=node@24.19.0 --package=pnpm@11.20.0 pnpm run build
```

Запустить в отдельном терминале из `apps/web`:

```sh
npx --yes --package=node@24.19.0 node scripts/serve-pwa-e2e.mjs
```

Сервер слушает `127.0.0.1:4175`. По умолчанию он использует неизменяемую
catalog fixture с реальными локальными ресурсами. Это воспроизводимый
режим личной проверки; live Kotlin/PostgreSQL проверяется отдельно.
Не применять ручное копирование файлов из старого отчета после исправления
упаковки: чистый build обязан сам подготовить полный набор ресурсов.

Запустить в другом терминале:

```sh
cloudflared tunnel --url http://127.0.0.1:4175 --no-autoupdate --protocol http2
```

Открыть выданный HTTPS адрес на телефоне. Общая Wi-Fi сеть не нужна, но Mac
должен оставаться включенным, бодрствующим и подключенным к интернету.
Остановка — Ctrl+C в терминале туннеля, затем сервера. Перед повторным запуском
проверить, что порт 4175 свободен; не останавливать неизвестные процессы.

На iPhone открыть адрес в Safari → «Поделиться» → «На экран Домой» →
«Добавить»; включить «Открывать как веб-приложение», если переключатель есть.
На Android открыть в Chrome → меню → установка приложения/создание ярлыка.
Названия зависят от версии браузера. Официальные инструкции:
[Apple](https://support.apple.com/en-gb/guide/iphone/iphea86e5236/ios),
[Google](https://support.google.com/chrome/answer/9658361?co=GENIE.Platform%3DAndroid&hl=ru).

Первый запуск и подготовку предметов выполнить онлайн. Затем закрыть PWA,
включить авиарежим и открыть ее с иконки: сохраненный проект должен открываться,
редактироваться, сохраняться и экспортироваться с уже подготовленными ресурсами.
Новый не загруженный предмет может потребовать сеть. Проверить 2D и 3D,
закрыть/открыть еще раз и импортировать сохраненную `.interiors` как новый проект.

### Адрес и сохраненные проекты

Quick Tunnel дает временный адрес, обычно новый после перезапуска. Новый origin
получает отдельное браузерное хранилище. Поэтому до остановки экспортировать
важные проекты в `.interiors`, а на новом адресе импортировать их обратно.
Safari, Home Screen PWA, Chrome и другие браузеры также могут иметь отдельные
хранилища; перенос выполняется резервной копией. Очистка данных сайта удаляет
его локальные проекты. Не очищать их для «обновления приложения».

Development сервер отключает worker/cache и не доказывает offline PWA.
`localhost` на телефоне означает телефон; обычный HTTP адрес Mac не заменяет
HTTPS для worker. См. [Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API).

## Восстановление без перезаписи исходного проекта

При ошибке сохранения различаются две кнопки: «Скачать сохранённую версию»
создает обычную `.interiors`, а «Скачать несохранённую правку» — отдельный
`.interiors-recovery.json` с явно неопубликованным candidate и доступными exact
моделями. Такой файл не объявляется сохраненной ревизией или Portable Backup.
Если точных ресурсов не хватает, файл содержит явный incomplete marker.
Текущий автоматический импорт принимает только полную recovery-копию; он не
дополняет неполный файл моделями из локального хранилища. Для восстановления
нужны точные исходные модели и повторный полный экспорт исходной правки.

На экране Projects команда «Восстановить несохранённую правку» проверяет этот
файл и создает новый Project ID через обычный проверенный импорт. Исходная
карточка не перезаписывается. Пока публикация не началась, импорт можно отменить;
отмена не должна оставлять новый проект. Формат текущей recovery-копии — V1;
неподдерживаемая V2 копия явно отклоняется.

Если повреждены referenced модели, редактор показывает проверенную геометрию
только для просмотра и временно скрывает недоступные модели. Изменение Project
при этом не сохраняется. «Восстановить исходные GLB» требует полный точный набор,
а «Восстановить модели из резервной копии» берет exact bytes из проверенной
`.interiors`, не импортируя и не подменяя ее проект. Успешный exact repair
сохраняет прежний revision ID. Когда повреждена только история, те же действия
ремонтируют ее ресурсы без автоматической очистки Undo/Redo.

Пока файл читается/проверяется, навигация и повторный repair блокируются.
Если оригинальные байты недоступны, удаление всех unresolved references требует
отдельного подтверждения и публикует одну новую ревизию. История очищается
только отдельным явно подтвержденным действием при здоровом текущем проекте.

Cross-context pin staging сохраняет ресурсы живой/неподтвержденной публикации.
Неопределенные orphan journal roots удерживаются консервативно: полноценный
глобальный GC требует доказать отсутствие ссылок всех проектов, истории,
библиотеки и активных операций. Текущий startup не удаляет такие байты наугад.

## Проверки перед передачей сборки

Выполнить из корня:

```sh
npx --yes --package=node@24.19.0 --package=pnpm@11.20.0 pnpm run verify:web
```

Дополнительно проверить backend с JDK 17 и работающим Docker:

```sh
cd apps/catalog-control-plane
./gradlew --no-daemon test pitest
```

Полный корневой `verify` объединяет `verify:web`, `test:backend` и полную web
mutation matrix; backend PIT остается отдельной командой. Полная mutation
matrix может занимать существенно больше времени, чем regression run, и
переписывает выбранные исходники in place: выполнять ее без параллельных правок.

Не отключать Gradle dependency verification для обхода ошибки checksum.
Отсутствующую запись добавлять после проверки происхождения и совпадения
артефакта; неизвестное несовпадение checksum останавливает сборку.
Testcontainers поднимает `postgres:18.4`; установленный локально PostgreSQL
другой версии не заменяет этот integration test.

Зафиксировать app build из `release-manifest.json`, дату, версии инструментов,
catalog version, counts passed/failed/skipped, ссылки на reports и проверенный
origin. Успешный повтор отдельного flaky сценария записывать как повтор, а не
как один зеленый полный запуск. Критический live-catalog skip не считать PASS.

`.github/workflows/verify.yml` выполняет web regression, границы слоев,
delivery и backend в независимых jobs с ограниченным token и закрепленными
actions. Полные web mutation и Kotlin PIT включены только для ручного
workflow dispatch, чтобы не запускать многотысячную mutation matrix на каждом
push/PR. Полная локальная команда остается доступной. Workflow не
делает commit, release или deployment. Первый удаленный запуск возможен только
после отдельно разрешенной загрузки Git репозитория на GitHub. `check:architecture`
использует compiler API закрепленного TypeScript 7: domain импортирует только
domain, application — domain/application/ports; запрещены прямые browser,
storage и network globals, а runtime-cycle с участием renderer дает ошибку.
Type-only edges не объявляются runtime-cycle. UI/composition и нейтральные
byte conversion APIs сохраняют свои текущие зависимости. Это проверка
архитектуры, а не среда изоляции произвольно обфусцированного кода.

## Подключение живого каталога

Выдача каталога не должна принимать Project/Revision/History/Backup, аккаунты
или пользовательские GLB. Для полного локального пути нужны:

1. PostgreSQL 18.4 и роли из `contracts/catalog-control-plane/catalog-operator-bootstrap-v1.sql`.
2. Раздельные migration, publisher и SELECT-only runtime credentials.
3. Flyway migration/validate, публикация versioned envelope и exact resources.
4. Catalog runtime на loopback `127.0.0.1:4174`.
5. Тот же web origin с proxy `/catalog-api/`.

`catalogMigrate`/`catalogValidate` читают `CATALOG_MIGRATION_DATABASE_*`,
`catalogPublish` — `CATALOG_PUBLISH_DATABASE_*` и `CATALOG_ASSET_ROOT`;
`catalogRun` использует `CATALOG_DATABASE_*`. Звездочка здесь означает поля
`URL`, `USER`, `PASSWORD`. Пароли задаются локально или менеджером секретов,
не в репозитории. `catalogRun` сначала валидирует migration отдельной задачей;
сам runtime не получает повышенные credentials.

Для существующего PWA сервера задать `INTERIORS_PWA_CATALOG_ORIGIN=http://127.0.0.1:4174`.
Для development proxy используется `INTERIORS_CATALOG_ORIGIN` с тем же значением.
`INTERIORS_LIVE_CATALOG_E2E=1` включает отдельный live browser scenario.
При недоступном каталоге существующий fully pinned проект обязан продолжить
open/edit/save/undo/export; outage каталога не означает повреждение проекта.

## Постоянный адрес

Текущий Quick Tunnel не закрепляет hostname. При обследовании 24 октября
локальная папка `~/.cloudflared` с named-tunnel credentials не обнаружена;
hosting credentials в именах переменных окружения и файлы конфигурации
Cloudflare/других hosting providers в рабочем репозитории также не обнаружены;
это не доказывает отсутствие Cloudflare аккаунта у владельца. Не следует
создавать новый аккаунт, покупать домен или публиковать данные за него.

Постоянный origin можно подключить после доступного владельцу домена и
авторизации провайдера. Для named Cloudflare Tunnel нужен именованный tunnel,
привязанный HTTPS hostname и credentials вне репозитория; источник должен
обслуживать production bundle и ограниченный same-origin catalog proxy.
Порядок провайдера: [Cloudflare named tunnels](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/get-started/).
Перезапуск такого туннеля сохраняет hostname. Mac остается сервером и все равно
должен работать постоянно; перенос на постоянный хост — отдельная операция.

До внешнего выпуска определить и проверить:

- Конкретный hostname и его owner; TLS и same-origin `/catalog-api/`.
- Web build и release manifest; immutable content-hashed assets,
  revalidation shell/worker, правильные MIME и byte-range responses ресурсов.
- Runtime только с catalog SELECT credentials; DB не выставлена в интернет.
- Восстановление каталога из versioned manifest/resources и проверенная
  резервная копия PostgreSQL; это не обещание серверного восстановления проектов.
- Privacy notice, допустимые diagnostics и канал обратной связи.
- Пользовательский backup перед сменой origin или несовместимым обновлением.
- Рабочая процедура остановки/возврата предыдущей совместимой сборки.

В момент этой записи конкретный домен и provider authorization не предоставлены.
Эти внешние действия не обозначаются как выполненная публикация.

## Обновление и возврат сборки

1. Собрать кандидат в отдельном рабочем каталоге, выполнить проверки и сохранить
   пару bundle/release manifest с проверенными resource hashes.
2. Проверить кандидата на тестовом origin с синтетическим проектом и backup
   roundtrip. Не загружать пользовательские проекты в CI или внешние diagnostics.
3. Обновлять bundle и его release manifest согласованно, сохраняя exact resources
   старых каталоговых ревизий. Не удалять байты, на которые могут ссылаться проекты.
4. В приложении дождаться безопасного предложения обновления после Durable
   Revision; не делать принудительный reload активного жеста или failed save.
5. Проверить browser и установленную PWA: existing project, 2D/3D, сохранение,
   offline reopen, self-contained backup и отсутствие silent schema migration.
6. При сбое остановить распространение и вернуть предыдущую совместимую пару
   bundle/manifest. Если схема уже изменилась, сначала применить ее проверенный
   compatibility/restore план; подмена старым runtime без проверки недопустима.

Product Owner отдельно принимает решение о приглашении участников/публичном
выпуске; готовый runbook не является этой приемкой. Коммиты не разрешены.

## Повтор focused mutation после этой поставки

```sh
npx --yes --package=node@24.19.0 --package=pnpm@11.20.0 pnpm run test:mutation:hardening
```

Команда последовательно выполняет восемь проверенных scopes с порогом 80%. Для текущего TypeScript 7 используется Stryker inPlace: выполнять в отдельной копии исходников либо при остановленных конкурентных изменениях. Recovery scopes разрешаются по уникальным source anchors и останавливаются при их отсутствии или при отсутствующем test filter. Общий domain/application mutation по-прежнему доступен как `test:mutation`. В ручном GitHub workflow можно выбрать `hardening` (по умолчанию) или `full`; обычный push/PR не запускает многочасовую матрицу.
