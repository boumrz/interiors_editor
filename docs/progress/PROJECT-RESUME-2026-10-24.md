## Как попробовать приложение с телефона

Откройте **[InteriorsEditor](https://dry-jeff-mere-settle.trycloudflare.com)** в обычном браузере телефона. Одинаковая Wi-Fi сеть с Mac не требуется: работает и мобильный интернет. Mac должен оставаться включенным, подключенным к интернету и бодрствующим.

Это временный HTTPS адрес текущей сессии. После остановки туннеля он перестанет обслуживать сетевые запросы; новый туннель обычно имеет другой адрес. Скачивайте важные проекты в `.interiors` до смены адреса. Хранилище привязано к адресу и браузерному контексту, поэтому новый адрес не покажет проекты старого адреса автоматически. Проекты на Mac также не появляются на телефоне без переноса резервной копией.

**iPhone:** откройте ссылку в Safari → «Поделиться» → «На экран Домой» → включите «Открывать как веб-приложение», если этот переключатель показан → «Добавить». Запускайте с новой иконки. В некоторых версиях Safari «Поделиться» находится внутри меню страницы. [Инструкция Apple](https://support.apple.com/en-gb/guide/iphone/iphea86e5236/ios).

**Android:** откройте ссылку в Chrome → меню ⋮ → «Установить и создать ярлык» / «Установить приложение» → подтвердите установку. Название пункта зависит от версии Chrome. [Инструкция Google](https://support.google.com/chrome/answer/9658361?co=GENIE.Platform%3DAndroid&hl=ru).

Первую проверку выполните онлайн. Создайте и сохраните проект, откройте 3D, добавьте нужные предметы, затем закройте приложение, включите авиарежим и откройте его с иконки. Офлайн доступны оболочка и уже подготовленные ресурсы; новый ранее не загруженный предмет может потребовать сеть. Safari и установленная PWA могут иметь отдельные хранилища: переносите проект экспортом и импортом `.interiors`.

Для проверки офлайн используется production сборка. Обычный development запуск намеренно удаляет service worker и его кэши; он подходит для разработки интерфейса, но не для демонстрации офлайн-PWA. На телефоне адрес `localhost` обозначает сам телефон. HTTP адрес компьютера в локальной сети также не заменяет HTTPS для service worker. [Ограничения service worker](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API).

### Сценарий первой проверки

1. Нажмите «Новый проект», задайте название и создайте проект.
2. Оставьте стартовые 4000 × 3000 × 2600 мм либо задайте свои размеры. Нажмите «Создать контур» и дождитесь «Сохранено».
3. Переключите «План / 3D», проверьте обзор, панораму и масштаб.
4. В «Предмет» выберите мебель, дождитесь подготовки и подтвердите размещение. Переместите и поверните предмет; сравните результат через undo/redo.
5. Выберите стену и добавьте дверь или окно. Проверьте тот же проем в 3D.
6. В меню проекта скачайте `.interiors`, вернитесь к списку, закройте и откройте приложение. Затем выполните офлайн-проверку и импорт резервной копии как нового проекта.

### Что именно запущено

Работает настоящий редактор из `apps/web/dist` с постоянным локальным сохранением на устройстве. Его обслуживает существующий PWA сервер на Mac, `127.0.0.1:4175`; внешний HTTPS дает Cloudflare Tunnel.

Для каталога используется существующая неизменяемая тестовая выдача metadata и реальных GLB, а не запущенный Kotlin/PostgreSQL сервис. Каталог содержит 12 моделей и 20 ресурсов: восемь моделей мебели и четыре демонстрационных предмета других категорий, включая настенное бра. Это небольшой проверочный набор, не готовая большая библиотека интерьеров.

В стандартной сборке обнаружена ошибка упаковки этого режима: сервер объявляет четыре `evidence-*.glb`, но они отсутствуют в `dist/catalog` и отвечают 404. Для текущего запуска четыре уже существующих файла скопированы из backend resources в выходную папку сборки после проверки SHA-256. Все 20 ресурсов теперь отдаются полным GET с правильными хэшами. Однако этот обход не исправляет отдельную ошибку частичной загрузки маленьких GLB: она описана ниже. Для первой проверки используйте обычную мебель из каталога или габаритный блок. Исходники не изменены; следующая сборка удалит временные копии.

### Подтвержденные дефекты каталога

Зеленая регрессия не покрывает все комбинации расширенного каталога. Дополнительная проверка выявила следующие ошибки:

1. **Маленькие GLB не проходят подготовку через текущий fixture сервер.** При выборе настенного бра браузер отправляет `Range: bytes=0-1048575`, а сервер отвечает HTTP 416, поскольку указанный конец больше длины файла. [rangeFor](/Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor/apps/web/scripts/serve-pwa-e2e.mjs:148) отвергает такой запрос; [загрузчик](/Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor/apps/web/src/ui/preloaded-glb-resource.ts:84) всегда начинает с 1 MiB. Файлы четырех демонстрационных моделей меньше 1 MiB. Наблюдаемый результат: «Не удалось подготовить предмет для офлайн. Проект не изменён». Копирование ресурсов исправляет 404, но не этот 416. Нужен согласованный сценарий короткого файла и end-to-end регрессия.
2. **Настенная привязка каталожного предмета теряется в UI dispatch.** Envelope объявляет `anchorClass: wall`, но [startPreloadedCatalogPlacement](/Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor/apps/web/src/ui/AppShell.tsx:7482) не передает anchorClass, а подтверждение идет в `createCustomGlbFloorItem`. Это подтверждено цепочкой вызовов в коде; полный браузерный путь постановки бра сейчас раньше блокируется описанным 416. После починки загрузки нужно проверить именно wall-hosted размещение, save/reopen и backup, а не засчитывать наличие настенной модели в manifest как работающую функцию.
3. **Карточки жестко показывают «Мебель» и «На полу».** [AppShell.tsx](/Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor/apps/web/src/ui/AppShell.tsx:13611) использует эти подписи для разных категорий. Фильтры при этом работают: «Сантехника» действительно оставляет раковину, «Освещение» — бра. Исправлять нужно подписи, а не сам алгоритм фильтрации.

Эти дефекты требуют новых регрессий и исправлений, хотя соответствующие базовые истории уже имеют статус done. Обычная работа с комнатой, 3D и напольной мебелью остается доступна.

## Устройство кода и технический долг

Web stack закреплен: React 19.2.8, TypeScript 7.0.2, Rspack 2.1.8, Three.js 0.185.1, Rstest, Playwright, IndexedDB и собственный service worker. Backend каталога — Kotlin 2.4.10, Ktor 3.5.2, PostgreSQL, Gradle и Flyway. Он публикует каталог и ресурсы; серверного хранения проектов, аккаунтов и синхронизации в Alpha нет.

В коде выделены domain, application, adapters и composition. Миллиметры и граф плана отделены от renderer, а сохранение использует реальные durable/fenced/session-retention обертки. Ручная проверка импортов не обнаружила явных запрещенных связей между этими слоями. Автоматические правила архитектурных границ пока не настроены.

Fallow 3.35.0 проверил текущий `apps/web`, исключая архивные POC, spike, сборку и зависимости. Основные результаты:

- В production TypeScript/TSX — 154 файла и около 60,8 тысячи строк. Это уже значительный объем приложения.
- [AppShell.tsx](/Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor/apps/web/src/ui/AppShell.tsx:5312) — **13 949 строк**. Сам компонент занимает около 8638 строк и содержит 186 hooks, включая 97 state и 35 effect. Здесь сосредоточены многие взаимодействующие режимы редактора.
- [general-wall-project.ts](/Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor/apps/web/src/domain/general-wall-project.ts:1) — 4080 строк; [project-controller.ts](/Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor/apps/web/src/app/project-controller.ts:557) — 3805; RoomScene3d — 1835. Изменения этих узлов требуют особенно узкого среза и регрессии.
- Найдено около **6,94% дублирования**, 4524 строки и 130 групп. В частности, публикация команд повторяет serialize/checksum/revision/save обработку в нескольких use cases. Это риск расхождения поведения, а не 130 установленных ошибок.
- Есть цикл импортов между `webgl2-room-renderer.ts` и `three-webgl2-room-renderer.ts`. Его следует убрать при выделении общих helpers/types; текущий запуск не показал вызванного им отказа.
- Production dead-code анализ дал 182 сигнала, но многие относятся к fixtures, corpus и вручную запускаемым конфигурациям. Автоматически удалять эти файлы нельзя. Неиспользуемых зависимостей и неразрешенных импортов анализ не нашел.

Статические оценки сложности и CRAP частично используют оценочное покрытие. Их нельзя трактовать как число багов или отсутствие тестов: свежие 1754 теста проходят.

Отдельная задача — проверить завершенность перехода к каноническому PlanGraph kernel. Новый `materializeInitialWallSegment` вызывается corpus модулями, а production use case по-прежнему идет через `addGeneralWallToProject` в `general-wall-project.ts`. Наличие нового файла и зеленого corpus не означает, что весь пользовательский редактор уже переведен на него. Это архитектурная миграция, не доказательство отсутствия работающих стен или основание автоматически отменять READY.

## Как повторить запуск

Из корня репозитория собрать закрепленными версиями инструментов:

```sh
cd /Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor
npx --yes --package=node@24.19.0 --package=pnpm@11.20.0 pnpm run build
cp apps/catalog-control-plane/src/main/resources/catalog/evidence-assets/evidence-*.glb apps/web/dist/catalog/
```

Последняя строка — временный обход установленной ошибки fixture упаковки. После ее постоянного исправления ручное копирование нужно убрать.

В одном терминале запустить production PWA сервер:

```sh
cd /Users/romanzheltov/Desktop/frontentd-projects/InteriorsEditor/apps/web
npx --yes --package=node@24.19.0 node scripts/serve-pwa-e2e.mjs
```

В другом терминале:

```sh
cloudflared tunnel --url http://127.0.0.1:4175 --no-autoupdate --protocol http2
```

Открыть новый HTTPS адрес из вывода на телефоне. При повторном запуске сначала убедиться, что текущие сервер и туннель остановлены: второй сервер на том же порту не запустится. Для завершения процесса в его терминале использовать Ctrl+C. Команда обычного `pnpm` на этом Mac сейчас попадает в старый Corepack и падает; приведенный закрепленный `npx` launcher работает.

Для web проверок использовать закрепленный launcher и существующие scripts. Если PWA сервер уже работает, E2E можно запустить с `PLAYWRIGHT_PWA_BASE_URL=http://127.0.0.1:4175`; иначе тестовая конфигурация поднимет свой сервер. Проверки backend запускаются отдельно из `apps/catalog-control-plane` через `./gradlew test`, после исправления metadata и подготовки Docker.
