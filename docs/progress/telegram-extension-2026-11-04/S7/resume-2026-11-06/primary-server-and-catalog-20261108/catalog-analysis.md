**Текущий контракт каталога допускает не более256 записей.** Строки500/1000 — оценка будущей ёмкости; для такого количества понадобится отдельное изменение протокола/страниц/валидации каталога. Увеличения диска недостаточно.

В нынешней схеме есть отдельные наборы байтов во frontend, серверной папке catalog-assets и PostgreSQL bytea. Frontend использует hardlink-и, поэтому множество путей не означает множество физических копий. Дополнительно на новом VPS оставлены два архива поставки (frontend≈66МБ, backend≈85МБ), каждый также содержит каталог. Истинное физическое потребление, WAL, версии и архивы следует брать из отдельного серверного аудита; размер одной GLB-копии нельзя выдавать за расход всего VPS.

Для грубого планирования100 моделей текущего среднего размера:3 активных набора≈2.57ГБ; если сохранять оба архива поставки на VPS, около5 наборов≈4.29ГБ до WAL/старых версий/бэкапов. Архивы с уже сжатыми PNG/JPEG часто уменьшаются слабо. Это модель ёмкости, не измеренный коэффициент PostgreSQL.

Разумная будущая схема: один адресуемый по SHA256 набор GLB/превью в объектном хранилище, на VPS метаданные и API. Перенос должен заменить сохранение тяжёлых байтов в БД и поставках, а не добавить ещё одну полную копию. Старые версии, на которые ссылаются существующие проекты, сохраняются. Проекты и переносимые резервные копии пользователя остаются локальными; их не надо загружать в S3 ради каталога.

## Память телефона: размер файла и размер сцены различаются

Все8 GLB содержат49.17Мп изображений. Логический RGBA8-объём пикселей — **187.59МиБ**; типовая оценка текстур при полном mip-chain — **250.11МиБ**. Это расчёт по заголовкам изображений, не измерение RSS/VRAM. Геометрия, временный decode, GLB-буферы, canvas и render targets добавляются отдельно. [Формула и различие размера JPEG/декодированной текстуры в Three.js](https://threejs.org/manual/pages/textures.html).

Существенная особенность текущего редактора: основная3D-комната использует neutral-clay проекции. cloneRuntimeRootAsNeutralClay клонирует геометрию каждого экземпляра и заменяет материалы на однотонные без текстур. Поэтому цифру250МиБ нельзя называть фактическим расходом GPU-текстур основной комнаты. Она относится к textured preview/original-material path и будущему текстурному рендеру. При этом loadCustomGlbRuntime уже декодирует изображения, а materializeGlbTextureSources создаёт canvas-backed пиксели и закрывает ImageBitmap. Эти исходные пиксели остаются в renderer cache; их реальное размещение между RAM/GPU зависит от браузера и здесь не профилировалось.

Hash-keyed cache повторно использует decode одного ресурса, но геометрия в основной комнате клонируется по экземплярам. Поэтому нельзя обещать, что60 одинаковых предметов стоят в памяти как один: draw calls, треугольники и клонированные геометрические массивы растут с количеством размещений.

Один набор геометрических accessor/index-данных всех8 моделей≈6.21МиБ. Сумма массивов при клонировании каждого примитива≈14.24МиБ для одного экземпляра каждого предмета, без служебных объектов и дальнейших копий. Это оценка объявленных массивов, не замер видеопамяти.

Самый наглядный случай — single-bed.glb: файл3.16МБ, текстур нет, но4 примитива ссылаются на общие полные массивы87627 вершин. После независимого geometry.clone() по примитивам получается около11.03МиБ массивов на экземпляр. Полезно отдельно проверить уплотнение используемых вершин каждого примитива/переиндексацию, сохраняя границы материалов, UV и normals. Грубое уменьшение числа треугольников без измерений здесь не первый шаг.

Каталог не нужно целиком декодировать/помещать в GPU. Превью в списке малы; полноценные ресурсы загружаются по потребности проекта. Сотни записей в каталоге не равны сотням одновременно видимых моделей. Ориентир существующей RS-2 —60 экземпляров,750k видимых triangles,250 draw calls и128МиБ GPU resources; документ прямо называет это инженерной диагностикой, не отдельным release-gate.

## Конкретные возможности уменьшения

1. **Без потери пикселей:** scandinavian-closet.glb содержит10 PNG, но только3 уникальных SHA256 изображения (группы6+2+2). Избыточный image payload8946728 байт. Теоретическое удаление дублированных payload даёт около3.97МБ вместо12.91МБ до изменений JSON/выравнивания. Это обнаруженная возможность≈69% для одного файла, не выполненная оптимизация. Переназначение image/texture-ссылок должно сохранять sampling/material semantics и пройти валидаторы.
2. **Уменьшение реальных размеров текстур:** например, у dining-armchair четыре2048² карты. Перевод всех четырёх в1024² уменьшает логический объём пикселей в4 раза: оценка RGBA8+мипы85.33→21.33МиБ. Качество для мебели требуется сравнить в приложении; это расчёт, не готовый результат.
3. **Выбор кодека по назначению:** JPEG подходит для непрозрачной цветной фотографической карты при приемлемом качестве; PNG сохраняет альфу и точность normal/ORM-масок. Уменьшать качество normal/roughness/metalness карт тем же JPEG-пресетом, что albedo, опасно. Перекодирование без изменения width/height уменьшает диск/трафик, но само по себе не уменьшает декодированные RGBA-пиксели.
4. **Геометрия по профилю:** удалить действительно неиспользуемые данные, точные дубликаты и неиспользуемые вершины примитивов; отдельно оценить нужность декоративных деталей. Сохранить масштаб, опору, up/front, source bounds, silhouette, material/UV/normal seams и канонические размеры/footprint в мм.

## Совместимость будущего скилла

Сейчас оба продуктовых allowlist допускают только KHR_materials_unlit и KHR_texture_transform. Draco, Meshopt, KTX2/BasisU и mesh quantization не являются готовым переключателем: нужны отдельные изменения admission/runtime/decoder/backup/security и проверки. Обычный GLTFLoader в проекте не регистрирует соответствующие декодеры. [Требования GLTFLoader к декодерам](https://threejs.org/docs/pages/GLTFLoader.html).

Оба текущих header reader умеют распознавать WebP, включая KotlinCatalogMediaValidator.imageDimensions; это не означает поддержку корректного расширения EXT_texture_webp в продуктовом allowlist. Для обычного GLB-профиля следует использовать PNG/JPEG. Khronos требует EXT_texture_webp для WebP-варианта; оно сейчас не разрешено. [EXT_texture_webp](https://raw.githubusercontent.com/KhronosGroup/glTF/main/extensions/2.0/Vendor/EXT_texture_webp/README.md).

Не запускать generic gltf-transform optimize вслепую: официальный пример включает Draco и WebP, которые несовместимы с текущим allowlist. Сначала inspect, затем выбранные совместимые преобразования в отдельный выходной файл. [Официальный CLI](https://gltf-transform.dev/cli).

Текущие hard limits:25МиБ входа,250k triangles,300k уникальных POSITION-вершин,128 mesh primitives,256nodes,32materials,16textures,4096 на сторону изображения,48Мп суммарно. Значения берутся из продукта и не меняются для прохождения оптимизированного файла. Новые цели1–3МБ/512–1024px не заменяют эти ограничения.

Изменённый GLB получает новый hash/version и новый результат admission. Старые bytes/hash не перезаписывать и не удалять: они остаются ресурсами уже сохранённых проектов, portable backup и exact repair.
