## Проверка и выборочное восстановление

1. Сверить cipher SHA256. Расшифровать OpenSSL 3 CMS с `-decrypt -binary -inform DER -recip recipient.pem -inkey restore-key.pem` в закрытом recovery-каталоге на защищённом носителе. Проверить нулевой exit code и GCM authentication. Для временного plaintext использовать `umask 077`; при ошибке частичный результат не использовать. В текущей подготовке незашифрованный архив на Mac не записывался.
2. SHA256 расшифрованного tar.gz должен быть `eb9a2b3eaa53da94f178ca619d1cdf9470068d3a5b2a3922664b0f7243d366a3`. Первый payload `retirement-metadata/manifest.json` должен иметь SHA256 `13168803dc99f25547f6ff7d67ae5ff5f830a05c51155d5e7883567444c8bca9`. До выполнения восстановленных файлов сверить все размеры, SHA256, modes, UID/GID и ссылки. Не извлекать слепо в `/`: абсолютные symlinks из старого `/etc` требуют review и установки package-owned targets.
3. Это не образ ОС. Версии пакетов записаны в `retirement-metadata/packages.tsv`, сведения о платформе — в `snapshot.json`. Нужны совместимые Nginx, Java 17, Docker и **Certbot**. Проверить timer, webroot, renewal configuration и Nginx reload deploy hook. Старые netplan, hostname, machine-id, shadow/passwd и SSH host keys нужны как recovery material, но их нельзя автоматически копировать поверх нового NL-сервера.
4. Из основного backup получить offline PG image с закреплённой identity `sha256:a02db8cac496f15b094798a38254f14d6e00741f709360e5e00bb6668ea31636`. Образ предназначен для **linux/amd64**: нужна совместимая архитектура или отдельно проверенная эмуляция. Один успешный `docker load` на ARM не доказывает, что сервер БД запустится.
5. Создать **свежий отдельный PG volume**. Для инициализации выбрать bootstrap admin с именем, которого нет в dump: это предотвращает конфликт `CREATE ROLE` с уже существующим `interiors_catalog_admin`. Сначала восстановить globals/roles, затем `interiors_catalog.dump` через PostgreSQL 18 `pg_restore --create` в этом изолированном cluster. Не использовать production volume. Дополнительный `postgres.dump` сохранён для полноты, но default БД уже существует после init: не применять к ней `--create` без отдельного решения о пересоздании изолированной default БД. Пользовательских таблиц в ней при проверке не было.
6. Сохранённые env находятся в `/etc/interiors-editor/catalog`; роли и password hashes должны им соответствовать. Исходный порт PG — loopback `127.0.0.1:55432`. При выборе другого свободного loopback-порта согласованно изменить container publish и JDBC URL во всех трёх файлах: `runtime.env`, `migration.env`, `publish.env`. Каталог запускается только с `runtime.env` и SELECT-only ролью, а не с migration/publish credentials.
7. Выборочно восстановить application releases, catalog-assets, frontend, current symlink, system user и права. Проверить `nginx -t` и TLS paths. Каталог должен иметь envelope SHA256 `f25189ad2126866c6f44e851a4bfa458d4501a3e25f8b28e9c43c1e2b958648a`. Проверить resource GET/HEAD/Range, правила Web service worker и отсутствие Telegram service worker, а также старт служб. HTTP01 challenge и Certbot renewal проверить на конечном домене после запланированного DNS-переключения.
8. Только после успешного isolated restore планировать production cutover. В текущей подготовке прошли полная криптографическая/file-manifest проверка и `pg_restore --list`; полного восстановления БД или ОС не выполнялось. Пользовательские Projects и portable backup остаются на устройствах — этот VPS их не принимал.
