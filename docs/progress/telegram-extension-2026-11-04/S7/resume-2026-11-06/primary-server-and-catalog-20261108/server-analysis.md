Frontend содержит100 логических путей каталога, но только20 разных inode и68,699,401 байт уникальных тел. Одинаковые релизы/поверхности уже объединены hardlink: считать их пятью физическими копиями нельзя. Backend хранит отдельный набор20 файлов; ещё одна копия находится в PostgreSQL BYTEA. Таким образом, **активное хранение — примерно3 объёма каталога**, установочные архивы и резервные копии добавляются отдельно. PostgreSQL использует [TOAST для больших значений](https://www.postgresql.org/docs/18/storage-toast.html), поэтому точный размер базы отличается от суммы GLB.

При текущем среднем весе мебели около8.575МБ100 моделей — около0.86ГБ одной копии, порядка2.6ГБ в трёх активных хранилищах, без старых версий/WAL/архивов/backup. Для500 моделей это уже около4.3ГБ одной копии или12.9ГБ в трёх; на текущий диск вместе с ОС это не поместится. Это прогноз ёмкости, не обещание поддержки500 элементов: действующая схема ограничивает одну публикацию256 элементами.

Для планирования оставлять свободными не менее20–25% корневого раздела (примерно3ГиБ), дополнительно учитывать backup и временный рост WAL при массовой публикации. В PostgreSQL сейчас shared_buffers128МиБ, work_mem4МиБ, max_connections100, min_wal_size80МиБ и max_wal_size1ГиБ; последний является мягким ориентиром, не жёстким ограничением размера диска. [Настройки ресурсов PostgreSQL](https://www.postgresql.org/docs/18/runtime-config-resource.html).

## Что означает рост каталога для RAM и CPU

3D рендерится Three.js/WebGL2 на телефоне/компьютере пользователя: см. apps/web/src/adapters/renderer/three-webgl2-room-renderer.ts и apps/web/src/ui/RoomScene3d.tsx. Сервер не строит кадры3D и не требует GPU. Тяжёлые модели могут тормозить телефон даже при достаточно мощном сервере.

На сервере Nginx раздаёт приложение, Java/API и PostgreSQL обслуживают каталог. Полный GET читает GLB целиком в JVM ByteArray (JdbcCatalogRepository.resourceBytes → CatalogHttp.serveResource/respondBytes); скачивания крупных моделей требуют оперативной памяти. Range выполняет SQL substring и возвращает только запрошенный отрезок. Четыре Hikari-соединения ограничивают одновременные обращения к базе, но не число пользователей/уже отправляемых HTTP-тел. Точный коэффициент временных копий и безопасная одновременная нагрузка не измерялись.

При старте каталог последовательно проверяет все ресурсы; весь каталог не сохраняется целиком в постоянной JVM-памяти. Само увеличение количества моделей не требует равного увеличения RAM на размер всех GLB; важны текущие запросы, декодирование на клиенте и временные буферы.

## Рекомендация по эксплуатации

- Сейчас оставить существующий сервер основным: наблюдения и пользовательское подтверждение показывают, что текущий сценарий работает.
- Для уверенного запаса при том же стеке Java+PostgreSQL разумный следующий минимум —2ГБ RAM. Это рекомендация по запасу, а не обязательное условие текущей работы.
- Для расширения аудитории и каталога планировать2vCPU/4ГБ RAM; диск20–30ГБ имеет смысл только при сознательном локальном хранении моделей и версий. Не покупать этот запас вместо устранения лишних копий или выбора S3.
- При росте каталога выносить подготовленные модели/превью в объектное хранилище, сохраняя проверку hash/ETag/медиа/Range и неизменность ранее опубликованных ресурсов; S3 пока не подключён и требует отдельной реализации адаптера.
- Оптимизацию моделей и сборки выполнять на Mac/отдельном рабочем окружении. Не запускать Blender/массовую конвертацию на рабочем1ГБ VPS.
- Сигналы для пересмотра тарифа: повторяющееся снижение MemAvailable ниже100–150МиБ, устойчивый swap I/O/PSI, ошибки OOM, высокая загрузка CPU или сокращение свободного диска до планового резерва. Это эксплуатационные ориентиры, не новые продуктовые hard limits.
