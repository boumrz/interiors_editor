# Проверка самостоятельной полезности Alpha

Подготовлено 24 октября 2026. Статус: **протокол готов, сессии не проведены**.
Связи: CAP-1–CAP-11; PRD UJ-1–UJ-6 и SM-1–SM-6; NFR-17–21/23/25;
roadmap G-8/G-9. Alpha+ GLB не требуется для этого исследования.

## Участники и подготовка

Первая диагностическая когорта — пять людей без CAD-подготовки, которые
самостоятельно планируют ремонт или расстановку мебели. Включить пользователей
iPhone и Android. Такая небольшая выборка выявляет проблемы; ее проценты
не доказывают спрос или надежность для всей аудитории.

Подготовить production PWA на стабильном на время сессии HTTPS origin,
синтетический план комнаты/квартиры с заданными размерами и мебелью,
пустой профиль без важных проектов, резервный `.interiors` и список известных
ограничений. Участник может пользоваться собственным планом только по желанию;
копирование проекта исследователем не требуется.

Объяснить: проверяется приложение, правильных ответов от человека не ждут;
можно остановиться в любой момент. Получить согласие на заметки. Запись экрана,
аудио и сохранение файлов — только с отдельным согласием; по умолчанию их нет.
Не записывать имена, адреса, геометрию жилья, filename и model bytes в analytics.
Использовать обозначения P01–P05. Удалить контактные сведения после организации
сессии, а сроки хранения анонимных заметок согласовать до исследования.

В начале записать app build, catalog version, телефон, browser/PWA context,
размер текста и наличие ограничения движения. NFR-15 исторически принят на
двух устройствах; это исследование не возвращает снятую benchmark matrix.

## Сценарий без подсказок

Сказать: «Проверьте на телефоне, поместится ли мебель и будет ли удобно пройти.
Сделайте план, которому сможете доверять, и сохраните возможность продолжить».
Не произносить названия кнопок и не показывать порядок действий.

1. Создать проект и комнату по выданным внутренним размерам. Проверить показанные
   размеры; добавить вторую комнату или перегородку по задаче.
2. Добавить дверь/окно, кровать, шкаф и еще один предмет; оценить проход.
   Переместить и повернуть предмет. Отменить одну правку и вернуть ее.
3. Посмотреть тот же проект в 3D, найти выбранный предмет и вернуться на план.
   Назвать решение о расстановке или конкретную обнаруженную проблему.
4. Закрыть приложение и открыть проект снова. Включить авиарежим, изменить
   один предмет, сохранить, закрыть и повторно открыть. Проверить изменение.
5. Экспортировать `.interiors`, импортировать его как новый проект и проверить
   размеры/предметы. Важные исходные данные не удалять ради этого шага.
6. При возможности установить PWA и перенести тестовый проект через backup.
   Спросить, ожидает ли человек общих проектов между браузером и иконкой.

Для основной метрики SM-1 измерять шаги 1–3 до первого полезного результата,
предельное время 15 минут. Дополнительные offline/backup шаги учитывать
отдельно, чтобы не менять смысл метрики после получения результатов.

Исследователь молчит и записывает события. Если человек просит помощь,
зафиксировать момент и необходимость подсказки до ответа. После существенной
подсказки задача перестает считаться самостоятельным завершением, но сессию
продолжить для диагностики. При риске потери пользовательских данных остановить
действие; использовать только подготовленный тестовый проект.

## Критерии и запись результата

PRD provisional targets: ≥80% выполняют основной сценарий самостоятельно
за ≤15 минут; ≥70% называют конкретное решение/найденную проблему. Для пяти
участников оба порога требуют минимум четыре успешных сессии. Порог не менять
после начала когорты. При иной выборке считать по фактическому знаменателю.

| Поле | Значение для каждой сессии |
| --- | --- |
| Код | P01–P05 |
| Build/context | Версия, телефон, браузер или standalone |
| Самостоятельно за 15 минут | Да/нет, время, первая потребовавшая помощь точка |
| Полезное решение | Содержание решения без адреса/геометрии проекта |
| Offline continuity | Open/edit/save/reopen: pass/fail и stable reason |
| Backup roundtrip | Pass/fail; сохранились ли контрольные размеры/предметы |
| Доступность | Затруднение касания, крупный текст, focus или жест |
| Ошибка | Шаг, наблюдаемое поведение, severity, ожидаемое поведение |

Пустая форма намеренно не содержит вымышленных PASS. Итоговую запись сохранить
в отдельном датированном research report; не менять исторические acceptance.

В конце задать четыре вопроса: «Какое решение вы приняли?», «Где перестали
доверять размерам или сохранению?», «Что оказалось непонятным?», «Когда вы
воспользуетесь этим снова?». Отдельно проверить понимание локальности данных
и резервной копии, не подсказывая ответ.

## Разбор и решение

Потеря/ложное сохранение данных, невозможный recovery, privacy leak или
неверные канонические размеры — critical и останавливают расширение когорты.
Невозможность закончить core flow без помощи — high. Визуальные неудобства
с доступным обходом фиксируются отдельно. Для каждого finding указать
CAP/FR/NFR, воспроизведение, одного implementation owner и проверяемый результат.

Показать фактические числители и знаменатели, времена и число подсказок;
описать ограничения выборки. Сравнить с заранее заданными SM-1/SM-2.
Затем Product Owner решает: исправить проблемы, повторить ограниченную когорту
или разрешить приглашенную Alpha. Метрика не заменяет technical regression.
Рассылка приглашений и сообщение участникам этим протоколом не выполняются.
